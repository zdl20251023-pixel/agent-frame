| 问题           | 具体表现                                          | 改进动作                                 |
| ------------ | --------------------------------------------- | ------------------------------------ |
| 1. 前置判断不足    | 遇到优先级、方案、技术问题时，容易直接进入确认或请教，缺少先自我拆解和初步结论。      | 所有问题先补齐“目标、方案、风险、工时、需要确认点”，再去请教。     |
| 2. 技术短板      | 涉及 Redis、MySQL、表结构、排行榜等后端设计时，对方案优劣和实现风险判断不够稳。 | 优先补 Redis，再结合当前项目补 MySQL 和 Web 后端通识。 |
| 3. AI 使用方式不当 | 遇到需求或方案设计时，容易先让 AI 从 0 生成，再反向理解和修正。           | 先自己写初稿和判断，再让 AI 查缺补漏、反证和优化表达。        |
| 4. 优先级判断不稳   | 多任务并行时，容易先问怎么排，而不是先判断工作量、交付影响和是否能并行。          | 多任务并行时，先评估工作量、影响范围、交付风险，再判断优先级。      |
| 5. 做事容易做大做偏  | 做文档或方案时，容易先追求完整体系，没有先锁定当前最关键交付。               | 先确认核心目标和最小交付结果，再决定是否扩展细节。            |
| 6. 沟通表达不直接   | 同步问题时，背景和解释偏多，结论、请求和下一步动作不够前置。                | 沟通时先说结论，再说依据，最后说需要确认什么。              |
| 7. 问问题缺少判断   | 请教时容易只抛出疑问，没有同步自己的判断、依据和备选方案。                 | 请教前先说明“我的判断是什么、依据是什么、不确定点是什么”。       |
| 8. 技术学习缺少闭环  | 技术短板通常在项目中暴露后才临时补，没有形成固定学习节奏和项目验证。            | 每月业余时间学习一个技术点，比如7月份redis，做一个分享。      |
| 9. 缺少多想一步的习惯 | 做一个动作前，容易只看到当前动作本身，没有先想清楚目的、风险和后续影响。          | 每次行动前先问自己：目的是什么、下一步是什么、风险是什么。        |
