# 基于表设计本质维度的深度判定：分开 vs 合并方案

**表设计的本质 = 核心事实源清晰，字段归属清晰，约束表达清晰，生命周期清晰；然后再根据查询路径和写入，有控制地做反范式。**

我们将复式扑克中参赛进度与手牌记录的设计（**分开方案**：一主 N 从；**合并方案**：单表 + JSON）代入这 5 个终极维度进行“审判”：

---

### 1. 核心事实源清晰
*   **分开方案**：用户在一手牌中赢了多少（`win_loss_bb`）、是否打完（`status`），是业务中**客观发生的一局比赛结果**。将每一个独立的事实沉淀在 `user_hand_record` 明细表的一行中，事实源极度清晰，具备完美的独立追溯能力。
*   **合并方案**：将 10 个彼此独立的对局事实，强行打包成一个 JSON 字符串存入 `user_entry`。这模糊了单手牌作为“独立事实”的地位，事实数据沉没在半结构化的长文本中。一旦因为 Bug 导致数据损坏，极难精准定位、修复和回查单手事实。

### 2. 字段归属清晰
*   **分开方案**：单手成绩 `win_loss_bb` 强依赖于具体的题目 `hand_id`，它理所当然归属于以 `hand_id` 为核心的明细表中；而总成绩 `total_win_loss_bb` 依赖于整个活动，归属于总表 `user_entry`。两张表各司其职，字段界限泾渭分明。
*   **合并方案**：总活动的属性与单手牌的属性被迫揉捏在同一个表的一行里。数据库 Schema 层面上彻底丧失了对单手牌字段的定义能力，所有的单手牌属性都被迫降级成了应用程序内部的解析逻辑。

### 3. 约束表达清晰（极其致命！）
*   **分开方案**：能完美利用 MySQL 强大的原生约束。例如，利用唯一索引 `UNIQUE KEY (entry_id, order_no)` 就能确保同一人在同一次比赛中，绝对不会产生两个“第 1 手”；`UNIQUE KEY (entry_id, hand_id)` 确保绝对不会重复分配同样的牌。数据库的强约束给业务兜了死底。
*   **合并方案**：JSON 数组内部**无法建立任何数据库级别的唯一性约束**。如果游戏服并发异常，导致同一个 `hand_id` 在 JSON 数组里被写入了两次，数据库根本无从拦截，直接造成严重的数据污染。

### 4. 生命周期清晰
*   **分开方案**：`user_entry` 的生命周期贯穿整个活动（从参加到活动截止）。而 `user_hand_record` 的生命周期是极短的单手牌（从开始发牌到单局结算）。两者生命周期截然不同。单局结算时，通过主键 `id` 独立更新自己，互相之间毫无干扰。
*   **合并方案**：把生命周期各异的 10 手牌强行绑定在一起。这意味着每次结算第 3 手牌时，都要把已经固定的第 1、2 手牌以及还未发生的第 4~10 手牌全部读出、替换、再全部覆盖写回。生命周期极度耦合，极易引发并发覆盖灾难。

### 5. 根据查询路径和写入路径，有控制地做反范式
*   反范式绝不能以“牺牲核心事实查询能力与写入安全性”为代价。
*   **在查询路径上**：如果采用**合并方案（JSON）**，其唯一的收益是“前端查询用户进度时少做一次表关联”。但惨痛的代价是**彻底废掉了管理后台基于 `hand_id` 的聚合查询路径**。MySQL 无法通过 JSON 高效执行 `SELECT AVG(win_loss_bb) WHERE hand_id = ?`，这使得运营的教学统计分析完全瘫痪。
*   **在写入路径上**：**合并方案**让每次单手牌结算变成了一个极度脆弱的“读-改-写”循环（取出完整 JSON -> 内存修改当前手 -> 序列化全量覆盖），在分布式网络下极易发生数据覆盖冲突；而**分开方案**在写入路径上极其优雅，单局结束只需执行原子级的 `UPDATE user_hand_record SET status=?, win_loss_bb=? WHERE id=?`，利用行锁保障绝对安全，性能极高。
*   **正确的反范式做法**：底层数据必须采用**分开方案**，以保全纯粹的事实源、安全的原子级写入路径，以及复杂的 SQL 聚合能力。对于前端高频的进度查询，如果遇到瓶颈，应当在 **Redis** 缓存层将 `user_entry` 和 10 条 `hand_record` 组装成 JSON 快照返回（即**读模型反范式**），而底层的 MySQL 必须坚守范式底线。
