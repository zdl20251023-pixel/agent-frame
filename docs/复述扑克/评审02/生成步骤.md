对，一次性生成完整文档确实容易出问题，尤其这次有三个硬约束：

1. **必须沿用你定好的 6-ai 模板框架，一级、二级标题不能少、不能改。**
2. **必须参考 7.15 PRD 和已有详细设计文档，不能自己随便补规则。**
3. **目标不是搬运 03，而是压缩重构成研发设计稿。**

我建议按 **“先搭骨架 → 再分章节生成 → 每轮校验 → 最后合并”** 的方式做。

## 一、生成前的资料优先级

后面生成时，内容来源优先级建议固定：

| 优先级 | 资料                                   | 用途                                         |
| --- | ------------------------------------ | ------------------------------------------ |
| P0  | `6-ai练习场优化01设计-框架.md`                | 固定文档框架，一级/二级标题不删不改                         |
| P1  | `04-复式 PvE 排名赛场 PRD｜7.15 交付范围初版.md`  | 判断 7.15 需求范围、主流程、验收边界                      |
| P2  | `03-复式扑克 PvE 排名赛 7.15 研发设计文档-详细版.md` | 提取已有研发设计结论、表结构、事务、幂等、Redis/MySQL/Worker 方案 |
| P3  | 排行榜实现方案 / 补充说明                       | 只在排行榜、Redis、最终结算章节引用                       |

这样可以避免我凭空补规则。比如 PRD 明确本期做 6 个核心模块：活动配置、用户参赛与手牌分配、PvE 对局与恢复、每手计分、当前榜/最终榜、截止结算；同时明确 Phase 2 的统计看板、动作分布、EV loss、好友榜、高级风控等不进 7.15 范围。

已有详细设计文档已经明确 7.15 使用 8 张核心表、MySQL 事实源、Redis 只做缓存/结算锁、当前榜动态查询、最终榜冻结、活动进度恢复但不恢复单手中途状态、以及 join/start/submit 幂等策略。

排行榜实现方案再补充排行榜专项规则：完成 N 手才入榜，当前榜不落库 `rank_no`，最终榜落库 `rank_no` 并冻结，排序口径是 `total_score DESC, complete_time ASC`。

## 二、推荐生成计划

### 第 0 步：先生成“最终文档目录骨架”

只生成完整目录，不写正文。

目的：

```text
确认 6-ai 模板基础标题没有少
确认新增的小节放在正确位置
确认不会一开始就跑偏
```

输出内容：

```text
完整 Markdown 标题目录
一级标题、二级标题完全保留
只在二级标题下面扩展三级标题
```

你确认后，再进入正文生成。

范围：

```text
# 一、背景介绍
# 二、参考方案介绍
```

本轮目标：

```text
把需求范围和核心设计原则讲清楚
把表结构设计放进去
不要写接口时序图
不要写太多实现细节
```

必须包含：

```text
7.15 做什么 / 不做什么

8 张核心表清单
表关系图
表结构设计
核心约束

```

控制方式：

```text
背景介绍压缩，不照搬 PRD
表结构设计可以详细
重复解释全部压缩成表格
```

这一轮最容易检查：**表结构是否完整、核心范围是否跑偏。**

### 第 2 步：生成第 3 章

范围：

```text

```

本轮目标：

```text
重点生成后台角度接口时序图
用户角度接口时序图
Worker 角度时序图
```

必须包含三类图：

```text
后台角度：
- 后台创建手牌
- 后台创建牌局包
- 后台创建活动
- 后台发布活动

用户角度：
- 用户进入活动 / resume
- 用户参加活动 / join
- 用户开始当前手
- 用户提交每手结果
- 用户查看当前榜
- 用户查看最终榜
- 用户断线恢复

Worker 角度：
- 活动截止后最终榜结算
```

要求：

```text
全部使用 Mermaid sequenceDiagram
每张图后只补 3～5 条关键说明
不写大段解释
```

这一轮单独生成的好处是：你可以重点检查 **后台视角和用户视角是否分清楚**。
