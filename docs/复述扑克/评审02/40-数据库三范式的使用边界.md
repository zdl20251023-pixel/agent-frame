## 关键结论

**实际业务开发中，MySQL 表设计要“默认尊重三范式”，但不能“机械追求三范式”。**

更专业的说法是：

**核心交易数据、事实数据、状态数据，优先按 3NF 建模；面向高频读取、历史快照、排行榜、统计报表、搜索筛选、活动配置、审计日志等场景，可以有控制地反范式设计。**

3NF 的价值是降低冗余、避免插入异常、更新异常、删除异常。Oracle 数据仓库文档也明确把规范化的目标描述为“让每个事实只存一处”，从而避免冗余和增删改异常；IBM 文档也把 1NF、2NF、3NF 作为关系模型表结构细化过程来说明。([Oracle Docs][1])

但 3NF 不是性能最优模型。IBM 文档也明确提醒，3NF 会带来更多表，如果 join 很多，SQL 性能可能下降，设计时要在冗余数据和未完全规范化表数量之间做平衡。([IBM][2])

---

## 一、3范式在业务开发里的定位

我会把它定位成：

> **3NF 是业务库表设计的“默认起点”，不是最终教条。**

也就是说，刚开始设计业务表时，不应该先想着“为了查询方便把所有字段塞一张表里”。应该先问：

这个字段到底属于哪个实体？
这个字段是否依赖当前表的主键？
这个字段是否只是另一个非主键字段的附属信息？
这个字段是否需要随着源数据变化而同步变化？
这个字段是否必须保留当时快照？

微软的数据库规范化说明里也提到，前三个规范化规则满足后，一般就可以认为达到了第三范式，并且第三范式通常是多数应用所需的最高规范化水平；但它也承认现实场景不一定能完美遵守。([Microsoft Learn][3])

所以，业务开发里比较成熟的原则是：

**先按 3NF 建核心模型，再根据明确的访问模式做有理由的反范式。**

---

## 二、三范式到底解决什么问题？

### 1NF：字段要原子化

例如不要在一个字段里存：

```text
user_ids = "1,2,3,4"
```

更合理的是拆成关联表：

```text
team_member
- team_id
- user_id
```

原因是逗号拼接字段不利于索引、查询、约束和后续维护。IBM 对 1NF 的描述也是每个属性在每一行里只能有一个值。([IBM][4])

---

### 2NF：非主键字段要依赖整个主键

这个主要出现在联合主键表里。

例如：

```text
order_item
- order_id
- sku_id
- sku_name
- qty
```

如果主键是：

```text
(order_id, sku_id)
```

那么 `qty` 依赖的是 `order_id + sku_id`，合理。

但 `sku_name` 只依赖 `sku_id`，不依赖 `order_id`。严格按 2NF，它应该放在 `sku` 表里。

不过注意：**订单明细里的 sku_name 有时反而应该保留，因为它可能是下单时的商品名称快照。** 这就是实际业务里不能机械套范式的典型例子。

---

### 3NF：非主键字段不要依赖另一个非主键字段

例如：

```text
user
- id
- province_code
- province_name
```

如果 `province_name` 由 `province_code` 决定，那么 `province_name` 不直接依赖 `user.id`，而是依赖 `province_code`。严格 3NF 下，应该是：

```text
user
- id
- province_code

province
- code
- name
```

3NF 的核心就是减少“传递依赖”。Oracle 对 3NF schema 的描述是经典关系数据库建模技术，用规范化最小化数据冗余。([Oracle Docs][5])

---

## 三、哪些表应该尽量遵守 3NF？

### 1. 核心业务实体表

比如：

```text
user
product
order
activity
coupon
wallet
account
match
```

这些表是系统事实源，后续很多逻辑都依赖它们。

这种表如果字段混乱、冗余严重，后面会产生大量问题：

一个字段多个地方存，更新容易漏；
业务规则变化时，不知道哪个字段才是准的；
数据修复成本高；
后续拆服务、做报表、做审计都困难。

---

### 2. 状态流转表

例如：

```text
order.status
activity.status
match.status
payment.status
```

状态字段必须有清晰归属，不能到处复制。

比如不要这样设计：

```text
order
- id
- status

payment
- id
- order_id
- order_status
- payment_status
```

`order_status` 应该属于 `order`。`payment` 只需要表达支付自己的状态。

如果确实要在 `payment` 里保存订单状态，那必须明确它是：

```text
order_status_snapshot
```

并且说明它是某个时间点的快照，不是当前订单状态。

---

### 3. 金额、库存、账户余额等强一致数据

例如：

```text
wallet.balance
order.total_amount
payment.amount
stock.available_count
```

这些字段不能随意冗余。

如果多个地方都存余额、库存、金额，又没有严格的一致性机制，就会出现非常严重的数据问题。

这类数据的原则是：

**事实源只能有一个。冗余字段必须有明确的生成规则、修复规则、校验规则。**

---

### 4. 后续可能被多个模块复用的数据

比如：

```text
user_profile
user_level
product_category
activity_config
drill_config
```

这种数据如果一开始为了方便塞进某张业务表，后续多个模块都要用时，就会很难维护。

---

## 四、哪些场景可以不严格遵守 3NF？

### 场景 1：历史快照

这是业务开发里最常见、最合理的反范式。

例如订单明细：

```text
order_item
- order_id
- sku_id
- sku_name_snapshot
- sku_price_snapshot
- qty
```

严格 3NF 下，`sku_name` 和 `sku_price` 应该来自 `sku` 表。

但订单系统必须保留下单当时的商品名称和价格。否则商品改名、改价后，历史订单就被污染了。

这种不是“设计不规范”，而是**业务事实要求保留历史快照**。

判断标准：

> 这个字段要表达“当前值”，还是“当时值”？

如果是当前值，应该关联查询。
如果是当时值，可以冗余为快照字段。

---

### 场景 2：高频列表页 / 管理后台列表页

例如后台订单列表需要展示：

```text
order_id
user_name
phone
order_amount
pay_status
shipping_status
created_at
```

严格 3NF 可能要 join：

```text
order
user
payment
shipping
```

如果这个列表访问频率高、数据量大、分页复杂，可以在订单表或订单扩展表里冗余部分展示字段。

但这里要注意：

**不能为了少写 join，一开始就乱冗余。**

更合理的做法是：

第一版按规范化设计；
发现列表页确实慢；
用 EXPLAIN、慢 SQL、QPS、响应时间证明瓶颈；
再增加冗余字段或汇总表。

MySQL 官方文档说明外键可以跨表引用并帮助保持相关数据一致，说明关系型设计本身是支持拆表和引用约束的。([MySQL][6])

---

### 场景 3：统计表 / 汇总表 / 排行榜表

例如：

```text
user_daily_stat
- user_id
- stat_date
- total_games
- total_score
- win_count

leaderboard_result
- activity_id
- user_id
- total_score
- rank_no
```

这些表本质上不是原始事实源，而是**计算结果表**。

它们天然会冗余，因为它们是为了查询性能服务的。

例如排行榜不可能每次请求都实时扫描所有手牌分数再排序。合理做法是：

原始事实存在明细表；
排行榜结果存在结果表或缓存；
结果表有明确计算时机；
必要时支持重算。

这种反范式是合理的。

---

### 场景 4：读多写少的配置表

例如活动配置：

```text
activity_config
- activity_id
- title
- start_at
- end_at
- hand_count
- reward_config_json
- display_config_json
```

严格来说，复杂配置也可以拆很多表。

但如果某些配置：

变更频率低；
主要是整体读取；
不需要复杂条件查询；
不参与强一致关系；
后台配置和前端展示按整体 JSON 使用；

那么适度用 JSON 字段是可以的。

但 MySQL 官方文档提醒，JSON 列不能像普通列一样直接索引；如果要索引 JSON 中的某个标量值，通常需要通过生成列提取后建索引。([MySQL][7])

所以我的建议是：

**不会查询、不会排序、不会 join 的配置，可以 JSON；需要查询、筛选、排序、关联的字段，应该独立成列。**

---

### 场景 5：日志、审计、事件流水

例如：

```text
operation_log
event_log
payment_callback_log
match_action_log
```

日志表经常会冗余大量上下文：

```text
user_id
user_name
request_payload
response_payload
ip
device
operator_name
```

这是合理的，因为日志的目标不是严格消除冗余，而是方便排查问题、还原现场。

日志表通常关注：

可追溯；
不可轻易修改；
写入简单；
查询按时间、用户、业务 id 定位。

它不一定要完全 3NF。

---

## 五、反范式不是乱设计，要满足 5 个条件

只要你要冗余字段，我建议必须回答 5 个问题：

### 1. 冗余字段的事实源是谁？

例如：

```text
order.user_name_snapshot
```

事实源是：

```text
user.name
```

但是订单里的字段是下单时快照，不跟随用户名称变更。

如果说不清事实源，字段就危险。

---

### 2. 这个字段是当前值，还是历史快照？

命名上最好直接表达出来：

```text
sku_name_snapshot
price_snapshot
user_level_at_join
config_snapshot
```

不要模糊命名成：

```text
sku_name
price
user_level
```

因为后续维护的人不知道它到底要不要同步。

---

### 3. 什么时候写入？什么时候更新？

例如排行榜表：

```text
leaderboard_result.total_score
leaderboard_result.rank_no
```

需要明确：

每手完成后是否更新总分？
活动截止后是否冻结排名？
是否允许重算？
重算是否覆盖旧数据？
并发情况下谁负责最终写入？

---

### 4. 如果数据不一致，以谁为准？

例如：

```text
order.total_amount
order_item.sum(price * qty)
```

如果两边不一致，到底谁是事实源？

成熟设计里必须明确：

`order_item` 是事实源，`order.total_amount` 是冗余汇总；
或者 `order.total_amount` 是结算事实，明细只做展示；
或者两者都不允许不一致，必须事务内一起写。

---

### 5. 有没有校验和修复机制？

比如：

定时校验；
管理后台修复；
重算脚本；
数据对账任务；
唯一索引；
事务保护；
版本号；
updated_at 对比。

没有修复机制的冗余字段，后期很容易变成脏数据来源。

---

## 六、MySQL 表设计里，3NF 和性能之间怎么取舍？

### 1. 不要用“少 join”作为唯一理由反范式

MySQL 是关系型数据库，join 是正常能力，不是洪水猛兽。

MySQL 官方文档明确支持外键，外键用于跨表引用并帮助保持相关数据一致。([MySQL][6])

很多时候性能差不是因为 3NF，而是因为：

索引没建好；
字段类型不合理；
分页方式不合理；
where 条件没命中索引；
join 顺序和数据量不合理；
一次查太多列；
冷热数据没拆；
把后台复杂筛选和前台高频接口混在一起。

所以第一反应不应该是“把表合并”，而是先看：

```sql
EXPLAIN
慢 SQL
索引选择性
返回行数
扫描行数
QPS
P95 / P99 响应时间
```

---

### 2. MySQL 的索引成本也要考虑

反范式常常会让表变宽、索引变多。

InnoDB 的二级索引记录会包含对应行的主键列，所以主键设计、索引数量、索引列长度都会影响存储和维护成本。([MySQL][8])

这意味着：

字段越多，不一定越快；
索引越多，写入越慢；
宽表会影响缓存命中；
大字段和热点字段混在一起会拖慢常用查询。

所以反范式不是“字段越全越好”，而是“围绕明确查询模式做最小冗余”。

---

### 3. JSON 字段要谨慎

JSON 适合：

低频配置；
扩展属性；
第三方回调原文；
前端展示配置；
不常参与搜索的附加信息。

JSON 不适合：

高频 where 条件；
高频排序；
强约束字段；
需要 join 的字段；
金额、状态、库存等核心字段。

因为 MySQL JSON 列不能直接像普通列一样索引，需要借助生成列或多值索引等方式。([MySQL][7])

---

## 七、几个具体业务例子

### 例子 1：用户表和部门表

不推荐：

```text
user
- id
- name
- department_id
- department_name
```

更推荐：

```text
user
- id
- name
- department_id

department
- id
- name
```

原因：`department_name` 依赖 `department_id`，不是直接依赖 `user.id`。

但是，如果你要做审计日志，可以这样：

```text
operation_log
- id
- operator_user_id
- operator_name_snapshot
- department_name_snapshot
- action
- created_at
```

因为日志要保留当时上下文。

---

### 例子 2：订单和商品

商品表：

```text
sku
- id
- name
- current_price
```

订单明细：

```text
order_item
- id
- order_id
- sku_id
- sku_name_snapshot
- unit_price_snapshot
- qty
```

这里 `sku_name_snapshot` 和 `unit_price_snapshot` 虽然冗余，但合理。

因为订单明细要记录“下单那一刻”的商品名称和价格。

---

### 例子 3：排行榜

原始成绩表：

```text
match_hand_score
- id
- activity_id
- user_id
- hand_id
- score
- finished_at
```

排行榜结果表：

```text
leaderboard_result
- activity_id
- user_id
- total_score
- rank_no
- is_final
- finalized_at
```

`total_score` 是从多条手牌分数汇总来的，严格来说是冗余计算结果。

但排行榜接口需要快速查询排名，所以这个反范式合理。

关键是要明确：

`match_hand_score` 是事实源；
`leaderboard_result` 是结果源；
活动未结束时可以动态更新；
活动结束后冻结最终榜；
必要时可以从事实源重算。

---

### 例子 4：活动配置

如果活动配置简单，推荐拆字段：

```text
activity
- id
- name
- start_at
- end_at
- status
- hand_count
```

如果奖励配置复杂但不常查询，可以：

```text
activity
- id
- name
- start_at
- end_at
- status
- reward_config_json
```

但如果经常按奖励类型筛选活动，例如：

```sql
where reward_type = 'cash'
```

那 `reward_type` 就不应该只藏在 JSON 里，应该独立成列。

---

## 八、我的工程判断标准

实际开发里，我会这样判断：

| 场景         | 建议                |
| ---------- | ----------------- |
| 核心业务表      | 尽量 3NF            |
| 金额、库存、余额   | 严格控制事实源，尽量不要冗余    |
| 状态字段       | 明确归属，不要多表乱放       |
| 订单、合同、支付记录 | 可以保留历史快照          |
| 排行榜、统计、报表  | 可以反范式，明确可重算       |
| 管理后台列表     | 先规范化，性能证明后再冗余     |
| 高频前台接口     | 可以为查询路径建立读模型      |
| 日志、审计、回调原文 | 可以宽表或 JSON        |
| 配置扩展字段     | 低频可 JSON，高频查询要独立列 |
| 多对多关系      | 通常用中间表，不建议逗号拼接    |

---

## 九、最终建议

对你这种实际 Web 后端业务开发，尤其是 MySQL，我建议采用这个原则：

> **主业务模型按 3NF 设计，保证事实清晰；读性能模型允许反范式，保证查询高效；所有冗余字段必须说明来源、写入时机、一致性策略和修复方式。**

不要走两个极端：

**极端 1：完全不管范式。**
结果是表越来越乱，字段来源不清，后期维护灾难。

**极端 2：机械追求 3NF。**
结果是表太碎、join 太多、接口复杂、性能不好、研发效率低。

更成熟的做法是：

**写入侧偏规范化，读取侧可反范式。**

也就是：

核心事实源：清晰、稳定、少冗余；
查询结果层：为了性能可以冗余；
历史快照层：为了业务真实性可以冗余；
日志审计层：为了排查问题可以冗余。

这才是实际业务开发里比较专业、可落地的 MySQL 表设计方式。
