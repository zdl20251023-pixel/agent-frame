## Q1：为什么排行榜要以 MySQL 为事实源？

因为排行榜结果涉及入榜资格、总分、当前榜、最终榜、截止冻结等业务状态，必须可持久化、可复查、可事务保证。

MySQL 负责：

```text
1. 保存 leaderboard_result 事实数据
2. 保证同一用户同一活动不重复入榜
3. 保证最终榜 rank_no 可复查
4. 保证 activity.status 和榜单冻结状态一致
```

Redis 只做性能优化，不能作为唯一事实源。
如果 Redis 丢失、过期、重启，排行榜仍然可以从 MySQL 恢复。

---

## Q2：Redis 在这个方案里到底做什么？

Redis 只做两类事情：

```text
1. 排行榜查询缓存
2. 防止多个服务同时结算同一个活动
```

排行榜查询缓存包括：

```text
当前榜分页缓存
最终榜分页缓存
我的排名缓存，可选
```

防止多个服务同时结算同一个活动，是通过 Redis 活动结算锁实现。

Redis 不做：

```text
不判断用户是否完成 N 手
不判断用户是否入榜
不保存最终可信 rank_no
不替代 MySQL 最终结算
不在 MySQL 事务提交前更新缓存
```

---

## Q3：Redis 为什么能防止多个服务同时结算同一个活动？

活动截止后，可能有多个无状态服务实例同时扫描到同一个活动需要结算。

例如：

```text
server-1 扫描到 activityId = 1001 需要结算
server-2 也扫描到 activityId = 1001 需要结算
server-3 也扫描到 activityId = 1001 需要结算
```

如果没有控制，可能出现：

```text
重复计算最终排名
重复写入 rank_no
重复更新 finalized_at
结算状态互相覆盖
```

Redis 的做法是：

```text
结算前先尝试写入一个 lock key。
写入成功的服务获得结算权。
写入失败的服务说明别人正在结算，直接跳过。
```

示例 key：

```text
duplicate:leaderboard:finalize-lock:{activityId}
```

含义：

```text
同一个 activityId，同一时间只允许一个结算任务执行。
```

Redis 锁只是辅助。最终正确性仍然由 MySQL 的 `activity.status`、`select for update` 和事务兜底。

---

## Q4：什么是按 activity_id 加锁？

按 `activity_id` 加锁，就是最终结算时以活动为粒度做并发控制。

示例：

```text
活动 1001 结算时，加锁：duplicate:leaderboard:finalize-lock:1001
活动 1002 结算时，加锁：duplicate:leaderboard:finalize-lock:1002
```

效果：

```text
同一个活动不能被多个任务同时结算。
不同活动可以并行结算。
```

这样不会让所有活动都排队，只限制同一个活动的重复结算。

---

## Q5：Redis 结算锁里的 token 是什么？

`token` 是当前结算任务生成的随机字符串，用来标识“这把锁属于谁”。

它不是用户登录 token，也不是接口鉴权 token。
它只是当前这一次结算任务的锁持有者标识。

示例：

```text
activityId = 1001
token = "server-2:worker-1:20260715120000:random-abc123"
```

Redis 中保存：

```text
duplicate:leaderboard:finalize-lock:1001 = "server-2:worker-1:20260715120000:random-abc123"
```

---

## Q6：token 怎么生成？保存在哪里？

token 由服务端生成随机值。

建议组成：

```text
serverId + workerId + timestamp + randomUUID
```

TypeScript 示例：

```ts
const token = `${serverId}:${workerId}:${Date.now()}:${crypto.randomUUID()}`
```

保存位置：

```text
1. Redis lock key 的 value 中
2. 当前结算任务的内存变量中
```

Redis 中：

```text
duplicate:leaderboard:finalize-lock:{activityId} = token
```

当前任务内存中也保留同一个 token，用于释放锁时校验。

---

## Q7：为什么释放 Redis 锁时要校验 token？

因为不能直接删除锁。

错误做法：

```text
DEL duplicate:leaderboard:finalize-lock:{activityId}
```

可能出现的问题：

```text
server-1 获取锁，token = A
server-1 执行时间过长，锁过期
server-2 获取新锁，token = B
server-1 执行结束，如果直接 DEL，会把 server-2 的锁删掉
```

正确做法：

```text
释放锁时先判断 Redis 当前 value 是否等于当前任务 token。
只有相等，才允许删除。
```

伪代码：

```text
if redis.get(lockKey) == currentTaskToken:
    redis.del(lockKey)
else:
    不删除
```

生产实现建议用 Lua 脚本保证“判断 + 删除”是原子操作：

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
else
  return 0
end
```

## Q8：Redis 锁已经有了，为什么 MySQL 还要兜底？

因为 Redis 锁不是绝对可靠的业务事实源。

可能出现：

```text
Redis 锁过期
Redis 短暂不可用
任务执行时间超过锁时间
服务重启
锁释放失败
```

所以 MySQL 仍然必须做最终兜底：

```text
select activity for update
判断 activity.status 是否已经 finalized
最终一步才更新 activity.status = finalized
```

这样即使 Redis 锁异常，也不会破坏最终榜正确性。

---

## Q9：当前榜缓存什么时候生成？

当前榜缓存不是用户入榜时生成的，而是在用户查询当前榜时生成的。

流程：

```text
用户请求当前榜
-> 后端查 Redis
-> Redis 没有缓存
-> 后端查 MySQL
-> 按 total_score DESC, complete_time ASC 计算当前榜
-> 写入 Redis
-> 返回给用户
```

也就是：

```text
第一次查询时生成缓存。
后续用户查询同一页时，优先读 Redis。
```

当前榜分页缓存是所有用户共用的，不是每个用户单独一份。

---

## Q10：为什么最后一手完成后要失效当前榜缓存？

因为当前榜可能变化了。

例如 Redis 里原来缓存的是：

```text
第 1 名：A，95 分
第 2 名：B，90 分
第 3 名：C，85 分
```

这时候用户 D 完成 N 手，总分 98 分。

MySQL 真实排名变成：

```text
第 1 名：D，98 分
第 2 名：A，95 分
第 3 名：B，90 分
第 4 名：C，85 分
```

如果不失效当前榜缓存，前端继续读 Redis，就会看到旧榜。

正确顺序：

```text
MySQL 事务提交成功
-> 失效 Redis 当前榜缓存
-> 下一次查询当前榜时，从 MySQL 重建缓存
```

不能在 MySQL 事务提交前更新或失效 Redis，避免事务回滚后缓存和数据库不一致。

---

## Q11：当前榜缓存为什么用 version 方式失效？

因为当前榜分页缓存可能有多个 key：

```text
page 1
page 2
page 3
...
```

如果用通配符删除：

```text
KEYS duplicate:leaderboard:current:{activityId}:*
```

线上可能阻塞 Redis，不推荐。

version 方式只需要递增一个版本号，就能让所有旧分页缓存失效。

---

## Q12：version 是什么？

`version` 是某个活动当前榜缓存的版本号。

它不是业务排名，不是数据库字段，也不参与排行榜计算。
它只是 Redis 里的一个数字，用来区分“旧缓存”和“新缓存”。

当前榜版本 key：

```text
duplicate:leaderboard:current:{activityId}:version
```

示例：

```text
duplicate:leaderboard:current:1001:version = 3
```

表示：

```text
活动 1001 当前榜缓存目前使用第 3 版。
```

---

## Q13：version 怎么来？怎么计算？保存在哪里？

version 保存在 Redis。

第一次使用时，如果 Redis 里没有 version，可以默认初始化为 `1`。

查询当前榜时：

```text
1. 读取 duplicate:leaderboard:current:{activityId}:version
2. 如果不存在，则设置为 1
3. 使用当前 version 拼接分页缓存 key
```

当前榜分页 key：

```text
duplicate:leaderboard:current:{activityId}:v:{version}:page:{page}:size:{pageSize}
```

示例：

```text
duplicate:leaderboard:current:1001:v:3:page:1:size:20
```

当当前榜可能变化时，递增 version：

```text
INCR duplicate:leaderboard:current:{activityId}:version
```

如果原来：

```text
version = 3
```

递增后：

```text
version = 4
```

后续查询会使用新 key：

```text
duplicate:leaderboard:current:1001:v:4:page:1:size:20
```

旧缓存：

```text
duplicate:leaderboard:current:1001:v:3:page:1:size:20
```

不会再被命中，等待 TTL 自动过期。

---

## Q14：当前榜分页缓存是所有用户共用，还是每个用户一份？

当前榜分页缓存是所有用户共用的。

例如：

```text
duplicate:leaderboard:current:1001:v:3:page:1:size:20
```

所有用户查看活动 1001 当前榜第 1 页，都可以共用这份缓存。

不是这样：

```text
duplicate:leaderboard:current:1001:user:888:page:1:size:20
duplicate:leaderboard:current:1001:user:999:page:1:size:20
```

排行榜列表本身和用户无关，所以应该共用。

---

## Q15：最终榜分页缓存是什么时候生成？

最终榜分页缓存也是用户查询时生成。

流程：

```text
用户第一次查询最终榜
-> Redis miss
-> 查 MySQL
-> 写入 Redis
-> 返回给用户
```

7.15 第一版不在结算完成时主动提前生成最终榜缓存。

原因：

```text
最终榜结算流程只负责生成和冻结最终排名。
缓存可以等用户真正查询时再生成，减少结算流程复杂度。
```

也就是说：

```text
不是结算完成后马上把最终榜前几页写入 Redis。
而是用户第一次打开最终榜时，再从 MySQL 查询并写入 Redis。
```

---

## Q16：为什么最终榜缓存正常情况下不失效？

因为最终榜是冻结结果。

最终榜生成后：

```text
rank_no 已写入
is_final = 1
finalized_at 已写入
activity.status = finalized
```

正常业务流程不再修改最终榜。

所以最终榜缓存可以长期有效。
只有后台人工重算或修复最终榜时，才需要主动删除最终榜缓存。

---

## Q17：我的排名缓存有什么用？

前端页面可能需要展示：

```text
我的总分
我的当前排名
我的最终排名
我的完成状态
```

即使排行榜第一页没有我，也可能需要展示“我的结果”。

例如我排第 320 名，排行榜第一页只显示 1-20 名。
这时需要单独查我的排名。

---

## Q18：我的排名缓存是所有用户都提前缓存吗？

不是。

推荐：

```text
谁查询，缓存谁。
```

例如只有用户 888 打开页面，才写：

```text
duplicate:leaderboard:my:current:1001:888
```

如果用户 999 没打开页面，就不缓存用户 999。

7.15 第一版可以先不做“我的当前排名缓存”，直接查 MySQL。
如果后续压力变大，再增加缓存。

## Q19：我的榜单结果和我的当前排名有什么区别？

查我的榜单结果：

```sql
SELECT *
FROM duplicate_match_leaderboard_result
WHERE activity_id = ?
  AND user_id = ?;
```

这个可以查到：

```text
我的总分
我的完成时间
我是否已经进入榜单
最终榜阶段的 rank_no
```

这个查询性能较好，因为可以使用：

```text
uk_activity_user(activity_id, user_id)
```

但当前榜阶段 `rank_no` 不落库。
所以“我的当前排名”需要额外实时计算。

## Q20：为什么我的当前排名可能有性能问题？

当前榜阶段，`rank_no` 不落库。

要查我的当前排名，需要计算有多少人排在我前面：

```sql
SELECT COUNT(*)
FROM duplicate_match_leaderboard_result
WHERE activity_id = ?
  AND is_final = 0
  AND (
    total_score > ?
    OR (total_score = ? AND complete_time < ?)
  );
```

然后：

```text
我的当前排名 = 前面人数 + 1
```

这个在用户量较小时可以接受。
如果单活动完赛用户很多，且很多用户频繁查“我的当前排名”，MySQL 压力会升高。

7.15 默认策略：

```text
我的榜单结果：必做。
我的最终排名：必做，因为最终榜 rank_no 已落库。
我的当前排名：默认不在列表接口中自动计算；仅当产品明确需要展示，或用户主动查看“我的排名”时再实时计算。
```

## Q21：最终榜我的排名为什么性能更好？

因为最终榜已经写入 `rank_no`。

查询我的最终排名只需要：

```sql
SELECT rank_no, total_score
FROM duplicate_match_leaderboard_result
WHERE activity_id = ?
  AND user_id = ?;
```

这个查询可以使用：

```text
uk_activity_user(activity_id, user_id)
```

所以性能较好。

## Q22：活动截止后，结算任务靠什么触发？

7.15 暂按 **定时扫描 Worker** 设计。

流程：

```text
独立 worker 进程每分钟扫描 MySQL
-> 找到 end_time <= now 且 status 可结算的活动
-> 按 activity_id 获取 Redis 结算锁
-> 获取成功后执行最终榜结算
-> 获取失败则跳过
```

扫描条件建议：

```text
扫描 end_time <= now 且 status = published 的活动。
如果系统存在 ended 中间态，也允许扫描 status IN ('published', 'ended')。
不使用 status != finalized 这种宽泛条件。
```

示例查询：

```sql
SELECT id
FROM duplicate_match_activity
WHERE end_time <= NOW()
  AND status IN ('published', 'ended')
LIMIT 100;
```

具体 status 枚举以活动表最终定义为准，不能扫描 `draft`、`disabled`、`cancelled` 等非上线活动。

## Q23：为什么无状态 Web 后端需要 Worker？

Web 后端是无状态服务，不能依赖某台 Web 机器“记住某个活动什么时候截止”。

如果没有 Worker，活动截止后可能没人触发结算。

Worker 的职责是：

```text
定时扫描已到期活动
触发最终榜结算
处理未完成用户 expired
冻结最终榜
```

推荐：

```text
Web API 处理用户请求
Worker 处理定时结算
```

7.15 暂定：

```text
定时扫描 Worker 为主。
后台手动触发为补偿。
用户访问懒触发暂不作为主方案。
```

## Q24：用户访问时懒触发结算可以吗？

可以作为补充，不建议作为主方案。

懒触发是指：

```text
用户打开活动页面或排行榜时
后端发现 now >= activity.end_time 且 activity.status != finalized
于是触发结算
```

问题是：

```text
如果没人访问，活动就不会及时结算。
```

所以 7.15 推荐：

```text
定时扫描 Worker 为主。
后台手动触发为补偿。
用户访问懒触发暂不作为主方案。
```

---

## Q25：后台手动触发结算有什么用？

后台手动触发用于补偿和测试。

用途：

```text
测试环境手动结算
线上 Worker 异常后的补偿
数据修复后的重新触发
运营或管理员确认异常后手动处理
```

它不应该替代定时 Worker，但建议保留作为补偿入口。

---

## Q26：为什么 activity.status = finalized 必须最后更新？

因为前端和业务逻辑会把 `activity.status = finalized` 当成最终榜已生成的信号。

如果先更新：

```text
activity.status = finalized
```

但此时：

```text
rank_no 还没写完
is_final 还没更新完整
finalized_at 还没写完
```

前端会认为最终榜已经完成，但数据实际不完整。

所以必须：

```text
先完成最终榜数据写入
再更新 activity.status = finalized
```

---

## Q27：结算阶段为什么还要兜底补齐 leaderboard_result？

正常情况下，用户完成第 N 手时已经生成 `leaderboard_result`。

但可能出现异常：

```text
hand_score 已写入
entry 已 completed
但 leaderboard_result 因异常没有写入
```

所以最终结算阶段做一次兜底补齐。

定位：

```text
这是补偿机制，不是主流程。
```

补齐时仍然必须满足入榜规则：

```text
entry.status = completed
entry.completed_hand_count = activity.play_hand_count
hand_score_count = activity.play_hand_count
entry.complete_time < activity.end_time
```

---

## Q28：最终榜是不是复制一份新数据？

7.15 第一版不是。

7.15 第一版不保留历史当前榜快照。

活动进行中：

```text
leaderboard_result.is_final = 0
leaderboard_result.rank_no = NULL
```

活动结算后：

```text
leaderboard_result.is_final = 1
leaderboard_result.rank_no = 最终排名
leaderboard_result.finalized_at = 冻结时间
```

也就是说：

```text
最终榜不是新增一套榜单数据。
最终榜是将当前已完成用户的榜单结果冻结。
```

活动 `finalized` 后，不再提供当前榜语义，前端应查询最终榜。

如果后续需要保留“截止前最后一次当前榜快照”，需要新增快照表或结算记录表，7.15 第一版不做。

---

## Q29：为什么当前榜不落库 rank_no？

因为当前榜会动态变化。

每新增一个完赛用户，已有用户排名都可能变化。
如果每次都批量更新所有人的 `rank_no`，写入成本高。

当前榜只是暂定排名，所以查询时实时计算即可。

最终榜是冻结结果，所以最终结算时写入 `rank_no`。

---

## Q30：为什么最终榜要落库 rank_no？

因为最终榜需要稳定、可复查、可展示。

最终榜生成后：

```text
用户第几名
总分多少
完成时间
冻结时间
```

都应该固定下来。

所以最终榜结算时写入：

```text
rank_no
is_final = 1
finalized_at
```

---

## Q31：最后一手完成时，为什么要在事务里校验 activity 状态和截止时间？

因为用户提交最后一手时，活动可能已经截止或正在结算。

如果不校验，可能出现：

```text
活动已经截止
用户仍然完成最后一手
用户被写入当前榜
同时 Worker 正在生成最终榜
```

所以完成手牌事务里必须检查：

```text
activity 是否还有效
now 是否小于 activity.end_time
activity 是否已经 finalized
```

7.15 第一版采用严格截止口径：

```text
以服务端执行计分事务时的时间为准。
如果 now >= activity.end_time，则拒绝继续计分。
```

---

## Q32：用户已经开始最后一手，但提交时超过截止时间，算不算完成？

7.15 第一版建议不算。

采用严格截止口径：

```text
以服务端执行计分事务时的时间为准。
如果 now >= activity.end_time，则不允许继续完成手牌。
```

如果产品希望支持“已开始手牌允许宽限提交”，需要新增宽限期规则，7.15 第一版暂不支持。

---

## Q33：什么是深分页？

普通分页通常使用：

```sql
SELECT *
FROM duplicate_match_leaderboard_result
WHERE activity_id = ?
  AND is_final = 0
ORDER BY total_score DESC, complete_time ASC
LIMIT ? OFFSET ?;
```

例如：

```text
第 1 页：LIMIT 20 OFFSET 0
第 2 页：LIMIT 20 OFFSET 20
第 1000 页：LIMIT 20 OFFSET 19980
```

`OFFSET` 越大，MySQL 需要跳过的数据越多。

MySQL 不是直接跳到第 1000 页。
它通常需要先找到并跳过前 19980 条，再返回后面的 20 条。

所以深分页会越来越慢。

---

## Q34：什么是游标分页？

游标分页不使用 `OFFSET`，而是用上一页最后一条数据作为下一页查询起点。

当前榜排序规则是：

```text
total_score DESC
complete_time ASC
```

假设第一页最后一名是：

```text
total_score = 88.5
complete_time = 2026-07-15 12:30:00
id = 5008
```

下一页查询时，不说“跳过前 20 条”，而是说：

```text
从 88.5 分、12:30:00 之后继续查。
```

示例 SQL 思路：

```sql
SELECT *
FROM duplicate_match_leaderboard_result
WHERE activity_id = ?
  AND is_final = 0
  AND (
    total_score < ?
    OR (total_score = ? AND complete_time > ?)
    OR (total_score = ? AND complete_time = ? AND id > ?)
  )
ORDER BY total_score DESC, complete_time ASC, id ASC
LIMIT ?;
```

这里加 `id` 是为了在 `total_score` 和 `complete_time` 都相同的情况下，保证排序稳定。

优点：

```text
不需要跳过大量 OFFSET 数据。
越往后翻页，性能更稳定。
适合排行榜列表继续加载。
```

缺点：

```text
不方便直接跳到第 100 页。
前端需要带上上一页最后一条记录的 cursor。
实现比普通分页复杂。
```

7.15 第一版建议先用普通分页，后期数据量大再考虑游标分页。

---

## Q35：Redis Sorted Set 是什么？

Redis Sorted Set 是 Redis 的有序集合，适合做实时排行榜。

它的基本结构：

```text
member：用户或榜单结果标识
score：用于排序的分数
```

示例：

```text
ZADD duplicate:leaderboard:current:1001 965000000 user:11
ZADD duplicate:leaderboard:current:1001 942000000 user:22
```

查询前 20 名：

```text
ZREVRANGE duplicate:leaderboard:current:1001 0 19 WITHSCORES
```

查询用户排名：

```text
ZREVRANK duplicate:leaderboard:current:1001 user:11
```

---

## Q36：为什么 7.15 第一版不直接用 Redis Sorted Set 做主排行榜？

因为当前排序不是只有总分，还要处理同分时按完成时间升序：

```text
total_score DESC
complete_time ASC
```

Redis Sorted Set 只有一个 score 排序值。
如果要同时表达“分数越高越靠前”和“完成时间越早越靠前”，需要把两个排序条件编码成一个综合 score。

这会引入额外复杂度：

```text
分数精度怎么放大？
complete_time 怎么转换？
同分同时间怎么处理？
Redis 排名和 MySQL 排名如何保持完全一致？
最终榜冻结时如何保证可复查？
```

所以 7.15 第一版不建议 Redis Sorted Set 作为主榜单。

---

## Q37：后期什么情况下考虑 Redis Sorted Set？

如果出现以下情况，可以考虑：

```text
单活动完赛用户很多
当前榜访问频率很高
我的当前排名查询压力明显
MySQL 实时排序和 COUNT 成为瓶颈
```

后期方案可以是：

```text
MySQL 仍保存 leaderboard_result 事实数据。
Redis Sorted Set 维护当前榜快速排名。
最终榜结算仍以 MySQL 为准，或以 MySQL 校验 Redis 结果后冻结。
```

即使使用 Redis Sorted Set，也不建议让 Redis 成为唯一事实源。

---

## Q38：Redis 删除或 version 递增失败怎么办？

如果用户完成 N 手后，MySQL 已经写入新榜单结果，但 Redis version 递增失败，可能短时间看到旧榜。

处理方式：

```text
当前榜缓存设置较短 TTL。
即使 version 递增失败，旧缓存也会自动过期。
过期后，下一次查询会从 MySQL 重建缓存。
```

核心原则：

```text
Redis 失败不影响业务正确性。
最多影响短时间展示的新鲜度。
```

---

## Q39：什么是 TTL？为什么依赖 TTL？

TTL 是 Redis key 的过期时间。

例如当前榜缓存 TTL 设置为 30 秒：

```text
30 秒后自动过期。
```

如果缓存失效操作失败，旧缓存最多保留到 TTL 结束。
过期后，下一次查询会重新从 MySQL 查询并生成新缓存。

所以 Redis 缓存不是永久数据，而是可过期、可重建的临时数据。

---

## Q40：为什么 Redis 不能在 MySQL 事务提交前更新？

因为 MySQL 事务可能回滚。

如果事务提交前先更新或失效 Redis，可能出现：

```text
Redis 已经认为榜单变了
但 MySQL 事务最终回滚
```

这会导致缓存和数据库状态不一致。

正确顺序：

```text
MySQL 事务提交成功
-> 再更新或失效 Redis 缓存
```

---

## Q41：当前榜和最终榜缓存分别怎么存？

当前榜分页缓存 key：

```text
duplicate:leaderboard:current:{activityId}:v:{version}:page:{page}:size:{pageSize}
```

最终榜分页缓存 key：

```text
duplicate:leaderboard:final:{activityId}:page:{page}:size:{pageSize}
```

缓存内容可以是 JSON：

```json
{
  "activityId": 1001,
  "type": "current",
  "page": 1,
  "pageSize": 20,
  "list": [
    {
      "rankNo": 1,
      "userId": 11,
      "totalScore": 96.5,
      "completeTime": "2026-07-15 12:10:00"
    }
  ]
}
```

---

## Q42：当前榜缓存和最终榜缓存有什么区别？

当前榜缓存：

```text
活动进行中使用
会随着新用户完赛变化
TTL 应较短
用户入榜后需要失效
```

最终榜缓存：

```text
活动结算完成后使用
结果已冻结
正常情况下不失效
后台人工重算或修复时才删除
```

---

## Q43：当前榜为什么用 version，最终榜为什么不用 version？

当前榜会频繁变化，分页 key 可能较多，用 version 可以整体失效旧缓存。

最终榜冻结后正常不变化。
只在后台人工重算或修复时才需要删除缓存。
因此最终榜第一版可以不用 version，直接删除明确的最终榜缓存 key 或按内部工具处理。

---

## Q44：如果活动结算时 Redis 锁过期了怎么办？

Redis 锁过期后，可能有其他任务获得新锁。

所以 MySQL 仍然必须做兜底：

```text
select activity for update
判断 activity.status 是否已经 finalized
最终一步才更新 activity.status = finalized
```

如果一个任务已经完成结算并把 activity 更新为 finalized，后续任务即使拿到锁，也会发现状态已 finalized，然后跳过。

---

## Q45：为什么结算任务要先把未完成用户更新为 expired？

因为活动截止后，未完成用户不能再继续挑战，也不能进入最终榜。

结算时将未完成用户更新为 `expired`，可以明确区分：

```text
已完成并入榜用户
未完成且过期用户
```

这样后续查询用户状态时更清楚。

---

## Q46：完成 N 手但 hand_score 数量不足，为什么不入榜？

排行榜总分来自每手计分结果。
如果 `hand_score_count` 不等于 `play_hand_count`，说明计分数据不完整。

即使 `entry.completed_hand_count` 看起来完成了，也不能入榜。

入榜必须同时满足：

```text
entry.completed_hand_count = activity.play_hand_count
hand_score_count = activity.play_hand_count
```

这是为了防止脏数据进入排行榜。

---

## Q47：为什么需要唯一约束？

唯一约束用于防止重复计分和重复入榜。

需要：

```sql
UNIQUE KEY uk_hand_score_user_hand (user_hand_id);
UNIQUE KEY uk_leaderboard_entry (entry_id);
UNIQUE KEY uk_leaderboard_activity_user (activity_id, user_id);
```

作用：

```text
一个 user_hand 只能有一条计分记录。
一个 entry 只能生成一条榜单结果。
同一用户在同一活动只能有一条榜单结果。
```

这样即使前端重复提交或服务端重试，也不会重复入榜。

---

## Q48：最后一手重复提交怎么办？

处理方式：

```text
如果 user_hand 已 completed，返回已有 hand_score，不重复计分。
如果 leaderboard_result 已存在，返回已有榜单结果，不重复入榜。
```

依赖：

```text
状态判断
MySQL 事务
唯一约束
```

---

## Q49：hand_score 写入成功但入榜失败怎么办？

最后一手计分和入榜建议放在同一个 MySQL 事务中。

如果入榜失败：

```text
整体事务回滚。
hand_score 不应单独成功。
```

这样避免出现：

```text
手牌已计分
entry 已完成
但排行榜没有结果
```

如果极端情况下出现遗漏，最终结算阶段还有 `leaderboard_result` 兜底补齐机制。

---

## Q50：为什么当前榜深分页和我的当前排名都是后期优化点？

因为 7.15 第一版更重要的是业务正确性和交付闭环。

当前榜深分页问题：

```text
OFFSET 越大，查询越慢。
```

我的当前排名问题：

```text
需要实时 COUNT 有多少人排在我前面。
```

这两个在用户量较小时可接受。
如果后期单活动用户量和访问量上升，再考虑：

```text
限制最大翻页深度
游标分页
Redis Sorted Set
排名快照表
异步批量计算当前排名
```

---

## Q51：7.15 第一版明确不做哪些复杂方案？

7.15 第一版不做：

```text
Redis Sorted Set 作为主排行榜
全量用户当前排名缓存
排名快照表
历史当前榜快照
复杂宽限期提交机制
最终榜缓存预热
复杂异步消息队列
```

保留后期扩展空间，但不放进第一版主流程。

## Q52：评审时可以怎么一句话总结这个方案？

可以这样说：

```text
排行榜正确性放在 MySQL，当前榜按完成用户实时排序，最终榜在活动截止后由定时 Worker 结算并冻结。Redis 只做分页缓存和活动结算锁，不做事实源。7.15 第一版先保证入榜口径、最后一手事务、最终结算幂等和缓存可失效，后续用户量变大再考虑 Redis Sorted Set 或排名快照。
```
