# 复式 PvE 排名赛场 PRD｜7.15 交付范围初版

## 1. 需求目标

请用简短说明讲清楚：这个需求为谁解决什么问题，完成后希望达到什么结果。

* 目标用户 / 使用对象：

  本期主要面向三类对象：

  1. 用户端玩家：参与 PvE 扑克排名赛活动，完成后台配置的 N 手挑战，获得每手得分和排名反馈。
  2. 运营 / 管理后台使用者：配置 PvE 排名赛活动，包括活动时间、牌局包、用户需要完成的手数、必选手 / 随机手策略、计分规则等。
  3. 研发 / 测试 / 后续数据分析使用者：需要基于活动、参赛、手牌分配、计分、榜单、结算、恢复等主链路，完成 7.15 版本交付和验收。

* 当前问题：

  当前 PvE（AI 练习场）对局更偏单人练习，用户完成一手牌后缺少和其他用户横向比较的竞争反馈，也缺少活动化的参与、排名和结算闭环。

  具体问题包括：

  1. PvE（AI 练习场）对局缺少比赛感，用户不知道自己相对其他玩家打得好不好。
  2. 单手结果只有输赢或收益反馈，不足以支撑“同题竞技”体验。
  3. 没有完整的活动流程，无法支持用户报名、完成挑战、查看当前排名、活动截止后查看最终排名。
  4. 用户中途离开后，需要能恢复本次活动进度，避免挑战过程丢失。
  5. 后台需要具备最小活动配置能力，不能完全依赖写死逻辑。

* 目标结果：

  在 7.15 节点完成 Phase 0 + Phase 1 范围，交付一个可演示、可内测的 PvE 排名赛活动闭环。

  用户参加活动后，系统根据后台配置分配 N 手牌；用户逐手完成 PvE 对局；每手结束后展示 raw 结果和 0-100 分；用户完成全部 N 手后可以查看当前排名；活动截止后系统生成最终排名；用户中途离开后可以恢复活动进度。

* 本期做什么：

  本期聚焦 Phase 0 + Phase 1，完成 6 个核心模块：

  1. 活动配置
     后台可配置 PvE 排名赛活动，包括活动基础信息、活动时间、牌局包、用户实际挑战手数 `play_hand_count`、必选手 / 随机手策略、计分规则等。

  2. 用户参赛与手牌分配
     用户参加活动后，服务端创建或返回唯一有效参赛记录，并根据活动配置生成本次挑战的 N 手牌 assignment。assignment 生成后持久化，用户刷新、退出、换设备后不重新分配。

  3. PvE 对局与恢复
     用户按照分配的手牌顺序逐手完成 PvE 对局。用户中途离开后，再次进入活动时可恢复到当前进度。

  4. 每手计分
     每手结束后，系统计算并展示 raw 结果和 0-100 分。分数需要支持参考分、暂定分、最终分等状态。

  5. 当前榜 / 最终榜
     用户完成后台配置的 N 手挑战后，可以查看当前排名。活动截止前排名为暂定；活动截止并完成结算后，用户查看最终排名。

  6. 截止结算
     活动到达截止时间后，系统锁定有效完成用户，重新计算最终成绩，生成最终榜单结果。

* 本期不做什么：

  本期不展开 Phase 2 及后续能力，以下内容暂不作为 7.15 主交付范围：

  1. 后台完整数据统计看板。
  2. 每手详细统计分析。
  3. 决策点正确率。
  4. 动作分布分析。
  5. EV loss 计算。
  6. Top / Bottom 用户分群对比。
  7. 自动生成教学素材。
  8. 好友榜、私房挑战、徽章体系。
  9. 高级风控和复杂作弊识别。
  10. 多座位轮转、团队赛、直播裁判等高级复式玩法。

* 主要影响范围：

  1. 用户端：新增 PvE 排名赛活动入口、挑战流程、每手结果反馈、当前排名、最终排名、恢复入口。
  2. 管理后台：新增或补充活动配置能力，支持配置牌局包、挑战手数、活动时间、计分规则等。
  3. 服务端逻辑：新增活动、参赛、手牌分配、对局推进、计分、榜单、结算、恢复相关逻辑。
  4. 数据存储：需要保存活动配置、用户参赛记录、手牌分配结果、每手结果、得分快照、榜单结果、恢复进度等关键数据。
  5. 测试验收：重点验收主流程是否可跑通，包括配置活动、用户参加、完成 N 手、每手计分、查看当前榜、截止后最终榜、离开恢复。

## 2. 主流程

按照范围从大到小说明流程：先写整体流程，再写各功能模块流程，最后标出会影响研发实现的关键节点。

* 整体流程：

  本期主流程是一个完整的 PvE 排名赛活动闭环：

  ```text
  后台配置活动
    ↓
  发布 PvE 排名赛活动
    ↓
  用户进入活动
    ↓
  用户点击开始 / 继续挑战
    ↓
  服务端创建或返回用户参赛记录
    ↓
  服务端根据活动配置分配 N 手牌
    ↓
  用户逐手完成 PvE 对局
    ↓
  每手结束后展示 raw 结果和 0-100 分
    ↓
  用户完成 N 手后查看当前排名
    ↓
  活动截止
    ↓
  系统执行最终结算
    ↓
  用户查看最终排名
  ```

* 模块流程：

  * 模块 1：活动配置

    ```text
    管理后台进入活动配置
      ↓
    创建 / 编辑 PvE 排名赛活动
      ↓
    选择或绑定牌局包
      ↓
    配置用户实际挑战手数 play_hand_count
      ↓
    配置必选手 / 随机手策略
      ↓
    配置活动开始时间、截止时间、计分规则
      ↓
    发布活动
    ```

    说明：

    1. 用户实际挑战手数不是写死的 10，而是后台配置项 `play_hand_count`。
    2. 当前业务默认可以是 15 选 10，但系统设计要支持 N 手配置。
    3. 活动发布后，用户端才能看到并参与活动。
    4. 牌局包总手数必须大于或等于用户实际挑战手数。
    5. 必选手数量不能大于用户实际挑战手数。

  * 模块 2：用户参赛与手牌分配

    ```text
    用户进入活动详情
      ↓
    用户点击开始挑战
      ↓
    服务端判断用户是否已有有效 attempt
      ↓
    如果没有，则创建新的 ParticipantAttempt
      ↓
    服务端根据活动配置生成 N 手 AttemptHandAssignment
      ↓
    保存 hand_id、display_order、source 等分配结果
      ↓
    返回用户当前挑战进度
    ```

    说明：

    1. 同一用户同一活动只能有一个有效参赛记录。
    2. 手牌分配由服务端完成，不能由客户端随机。
    3. assignment 一旦生成必须持久化。
    4. 用户刷新、退出、换设备后，继续读取同一份 assignment。
    5. `display_order` 可以随机，但计分和统计应基于底层 `hand_id`。

  * 模块 3：PvE 对局与恢复

    ```text
    用户进入当前待完成手牌
      ↓
    客户端拉取当前手牌可见状态
      ↓
    用户提交动作
      ↓
    服务端校验动作合法性
      ↓
    服务端推进 AI 行动和牌局状态
      ↓
    本手结束后进入结果页
      ↓
    用户点击下一手
      ↓
    继续完成后续手牌
    ```

    恢复流程：

    ```text
    用户中途离开
      ↓
    再次进入活动
      ↓
    服务端读取 attempt、assignment、已完成手牌和当前进度
      ↓
    返回当前应继续的手牌或结果页
    ```

    说明：

    1. 用户端展示进度时，应展示第 X / N 手，而不是写死第 X / 10 手。
    2. N 来自活动配置 `play_hand_count`。
    3. 本期至少需要支持基础进度恢复，包括已完成几手、当前应继续哪一手、是否已完成全部挑战。
    4. 如果活动已经截止，需要根据截止规则判断用户是否还能继续。

  * 模块 4：每手计分

    ```text
    用户完成一手 PvE 对局
      ↓
    服务端结算本手 raw 结果
      ↓
    服务端计算本手 0-100 分
      ↓
    保存本手得分快照
      ↓
    用户端展示本手结果
      ↓
    用户进入下一手或查看进度
    ```

    说明：

    1. raw 结果用于表示本手净收益，例如赢 / 亏多少 BB。
    2. 0-100 分用于表示用户在同题或可比较手牌中的相对表现。
    3. 活动进行中，分数可以是参考分或暂定分。
    4. 活动最终结算后，分数更新为最终分。
    5. 总分按用户本次 assignment 中 N 手得分聚合，不写死 10 手平均。

  * 模块 5：当前榜 / 最终榜

    当前榜流程：

    ```text
    用户完成 N 手挑战
      ↓
    系统聚合用户本次 N 手得分
      ↓
    用户进入当前榜
      ↓
    展示当前总分、当前排名、样本量 / 更新时间等信息
      ↓
    明确标记当前排名为暂定
    ```

    最终榜流程：

    ```text
    活动截止并完成结算
      ↓
    系统生成最终榜单
      ↓
    用户进入最终榜
      ↓
    展示最终总分、最终排名、最终结果
    ```

    说明：

    1. 当前榜只用于活动进行中的即时反馈。
    2. 当前榜不能表达为最终排名。
    3. 最终榜在活动截止并结算后生成。
    4. 进入当前榜和最终榜的前提是用户完成 `activity.play_hand_count` 手。

  * 模块 6：截止结算

    ```text
    活动到达截止时间
      ↓
    活动状态进入结算中
      ↓
    系统锁定有效完成用户集合
      ↓
    过滤未完成 N 手或截止后完成的用户
      ↓
    重新计算每个有效用户最终得分
      ↓
    生成最终榜单结果
      ↓
    活动状态更新为已结算
      ↓
    用户端开放最终排名
    ```

    说明：

    1. N 取活动配置 `play_hand_count`。
    2. 未完成 N 手的用户不进入最终主榜。
    3. 截止前完成 N 手的用户进入最终结算。
    4. 最终榜单需要与活动中的当前榜区分。
    5. 最终榜单生成后，应作为最终排名结果展示。

* 关键节点：

  1. `play_hand_count` 是配置项
     用户实际需要完成的手数不能写死为 10。所有进度、完成判断、入榜条件、结算条件都应基于 `activity.play_hand_count`。

  2. 用户 join 后必须生成并保存 assignment
     用户参加活动后，服务端需要生成本次挑战的 N 手牌分配结果，并持久化保存。后续恢复、计分、结算都依赖这份 assignment。

  3. assignment 不能重复随机
     用户刷新、退出、重新进入、换设备后，不应重新抽手牌。系统必须读取已有分配结果。

  4. 每手结束必须有结果反馈
     每手完成后，需要展示 raw 结果和 0-100 分。这是用户感知 PvE 比赛价值的核心反馈。

  5. 当前榜和最终榜必须区分
     活动进行中展示当前榜 / 暂定榜；活动截止并结算后展示最终榜。活动未截止前不能把当前榜描述为最终排名。

  6. 完成条件统一为 `completed_hand_count == play_hand_count`
     用户是否完成挑战、是否进入当前榜、是否进入最终结算，都应基于该条件判断。

  7. 活动截止会影响用户继续挑战和最终入榜
     活动截止后，未完成用户是否允许继续、是否能查看已完成结果、是否进入最终榜，需要在后续规则章节进一步明确。

  8. 恢复能力是本期主流程能力
     用户中途离开后，再次进入活动，需要能恢复到当前挑战进度，不能丢失已完成手牌和已生成 assignment。

  9. Phase 2 内容不进入本期主流程
     后台详细统计、决策点正确率、EV loss、动作分布、分群分析、教学素材生成等内容，不作为 7.15 主流程交付范围。

### 3.1 用户端涉及范围

本期用户端主要新增或调整以下能力：

1. 活动入口
   用户可以从指定入口看到 PvE 排名赛活动，并进入活动详情或挑战流程。

2. 活动详情 / 规则说明
   展示活动名称、活动时间、挑战手数、参与状态、截止时间等基础信息。挑战手数应展示为后台配置的 N 手，不写死 10 手。

3. 开始 / 继续挑战
   用户首次进入可开始挑战；已参与未完成时，可继续挑战；已完成时可查看当前排名或最终排名。

4. 挑战进度展示
   用户在挑战过程中需要看到当前进度，例如第 X / N 手。N 取活动配置 `play_hand_count`。

5. PvE 对局过程
   用户按照分配的手牌逐手完成 PvE 对局。对局本身优先复用已有 AI 练习场 / PvE 对局能力。

6. 每手结果页
   每手结束后展示 raw 结果和 0-100 分，并展示分数状态，例如参考分、暂定分或最终分。

7. 当前排名页
   用户完成 N 手后展示当前排名和当前总分，并明确标记为暂定排名。

8. 最终排名页
   活动截止并完成结算后，展示最终排名和最终总分。

9. 恢复入口
   用户中途离开后，再次进入活动时，需要能恢复到当前挑战进度或结果页。

### 3.2 管理后台涉及范围

本期管理后台主要新增或补充以下能力：

1. 活动配置
   后台可配置 PvE 排名赛活动基础信息，包括活动名称、活动时间、活动状态等。

2. 牌局包选择
   后台可选择或绑定本次活动使用的牌局包。

3. 挑战手数配置
   后台可配置用户实际需要完成的手数 `play_hand_count`。当前默认业务形态可以是 15 选 10，但 10 不能写死。

4. 必选手 / 随机手策略配置
   后台可配置哪些手牌为必选手，哪些手牌进入随机池，或至少支持本期确定的最小配置方案。

5. 计分规则配置
   后台可配置或指定本次活动使用的计分规则，例如 raw 结果 + 0-100 分。

6. 活动发布
   后台配置完成后，可发布活动，发布后用户端可见。

7. 活动状态管理
   后台或系统需要支持活动未开始、进行中、结算中、已结算等基础状态。

8. 最终结算触发
   活动截止后，系统自动或后台手动触发最终结算。具体触发方式后续在规则或技术方案中确认。

### 3.3 配置项 / 配置表涉及范围

本期需要明确以下核心配置对象，字段命名可由研发最终确定：

1. 活动配置
   包括 `activity_id`、`activity_name`、`start_time`、`end_time`、`status`、`scoring_mode` 等。

2. 牌局包配置
   包括 `hand_pack_id`、候选手牌列表、牌局包版本等。

3. 挑战手数配置
   包括 `play_hand_count`，用于控制用户本次活动需要完成几手。

4. 必选手配置
   包括 `required_hand_ids`，用于控制每个用户必须被分配到的手牌。

5. 随机策略配置
   包括 `sampling_policy`，用于控制剩余手牌如何从牌局包中分配。

6. 展示顺序配置
   包括 `shuffle_policy` 或 `display_order` 生成规则，用于控制用户看到的手牌顺序。

7. 计分配置
   包括 `scoring_mode`、`score_type`、是否启用 `baseline_reference` / `human_provisional` / `final` 等。

### 3.4 服务端逻辑涉及范围

本期服务端需要支持以下主链路逻辑：

1. 活动查询
   用户端可以查询当前可参与的 PvE 排名赛活动。

2. 活动参与
   用户点击开始挑战后，服务端创建或返回用户在该活动下的有效 attempt。

3. 手牌分配
   服务端根据活动配置生成 N 手牌 assignment，并持久化保存。

4. 进度恢复
   用户重新进入活动时，服务端返回当前 attempt、assignment、已完成手数、当前应继续的手牌或结果页。

5. PvE 对局推进
   服务端接收用户动作，校验合法性，推进 PvE 对局状态，并完成本手结算。该部分优先复用已有 PvE 对局能力。

6. 每手计分
   每手结束后，服务端计算 raw 结果和 0-100 分，并保存得分快照。

7. 总分聚合
   用户完成 N 手后，服务端按本次 assignment 中的 N 手得分聚合当前总分。

8. 当前排名
   用户完成 N 手后，服务端返回当前排名结果。活动未截止前，该排名为暂定。

9. 截止结算
   活动到达截止时间后，服务端锁定有效完成用户，重新计算最终分，生成最终榜单。

10. 最终排名
    活动结算完成后，用户端可查询最终排名结果。

### 3.5 其他系统 / 第三方涉及范围

以下能力是否属于本需求新增，需研发进一步确认：

1. PvE 对局引擎
   如果已有 AI 练习场对局能力，本期优先复用；如果不满足比赛活动恢复和结算要求，需要评估改造范围。

2. AI 策略服务
   本期默认复用已有 AI 行动能力，不新增复杂 AI 策略配置；是否需要锁定 AI 版本由研发评估。

3. 牌局结算能力
   本期需要能得到每手 raw 结果；如已有结算能力可复用，需确认输出是否满足计分要求。

4. 消息通知能力
   最终排名是否需要主动通知用户，当前暂不作为主流程必做项，后续确认。

5. 数据导出 / BI
   Phase 2 详细统计不进入本期主范围。本期如需基础数据排查，可由研发评估是否提供最小导出或后台查询。

### 3.6 已有数据 / 历史流程涉及范围

本期可能影响或复用以下已有数据与流程，需研发评估：

1. 现有 AI 练习场对局数据
   本期 PvE 排名赛可能复用 AI 练习场对局能力，但活动参赛、排名、结算应与普通练习场区分。

2. 现有手牌 / 牌局定义
   如果已有手牌定义或牌局素材，需要确认是否可直接作为 hand_pack 使用。

3. 现有用户进度数据
   如果已有练习场进度保存能力，需要评估是否能复用到活动 attempt 和 assignment 恢复中。

4. 现有排行榜能力
   如果已有排行榜能力，需要评估是否支持当前榜 / 最终榜区分，以及是否支持活动截止后的冻结结果。

5. 历史普通 PvE 流程
   本期新增 PvE 排名赛不应影响用户原有普通 AI 练习场流程。普通练习场与活动挑战需要在入口、状态、记录和排名上做区分。

## 4. 关键规则

请按“业务范围 → 功能模块 → 具体对象 → 主规则 → 子规则 → 特殊情况 → 处理结果”的顺序说明，避免规则散着写。

### 规则 1：活动配置规则

* 规则对象：

  * 业务范围：PvE 排名赛活动配置
  * 功能模块：活动配置
  * 具体对象：Activity、Hand Pack、Activity Hand Policy

* 主规则：

  后台需要支持配置一场 PvE 排名赛活动。活动配置决定用户端是否可参与、用户需要完成几手、从哪个牌局包分配手牌、使用什么计分规则、活动何时截止以及截止后如何结算。

* 子规则：

  1. 活动需要配置基础信息，包括活动名称、活动开始时间、活动截止时间、活动状态。
  2. 活动需要绑定一个牌局包 hand_pack。
  3. 活动需要配置用户实际挑战手数 `play_hand_count`。
  4. `play_hand_count` 是配置项，不能在前端、服务端、计分、榜单、结算逻辑中写死为 10。
  5. 当前默认业务形态可以是“15 选 10”，但系统规则应表达为“候选手牌数 `pack_total_hands`，用户实际挑战手数 `play_hand_count`”。
  6. 活动需要支持配置必选手 `required_hand_ids`。
  7. 活动需要支持配置随机策略 `sampling_policy`。
  8. 活动需要支持配置展示顺序策略 `shuffle_policy`。
  9. 活动需要配置计分规则 `scoring_mode`。
  10. 活动发布前，牌局包总手数必须大于或等于 `play_hand_count`。
  11. 活动发布前，必选手数量不能大于 `play_hand_count`。
  12. 活动发布后，用户端才能看到并参与该活动。

* 特殊情况：

  1. 如果牌局包总手数小于 `play_hand_count`，活动不允许发布。
  2. 如果必选手数量大于 `play_hand_count`，活动不允许发布。
  3. 如果活动已经发布，是否允许修改关键配置需要研发和 CTO 进一步确认。

* 处理结果：

  1. 配置合法时，活动可以发布。
  2. 配置不合法时，后台需要阻止发布，并提示具体原因。
  3. 用户端所有挑战手数展示、进度判断、完成判断、榜单入榜和结算判断，都以活动配置的 `play_hand_count` 为准。

### 规则 2：用户参赛规则

* 规则对象：

  * 业务范围：用户参加 PvE 排名赛活动
  * 功能模块：用户参赛与手牌分配
  * 具体对象：ParticipantAttempt

* 主规则：

  用户点击参加活动后，服务端需要创建或返回该用户在当前活动下的唯一有效参赛记录。用户不能因为重复点击、刷新页面、重新进入活动而生成多个有效参赛记录。

* 子规则：

  1. 用户首次点击开始挑战时，服务端创建 ParticipantAttempt。
  2. 如果用户已经存在当前活动下的有效 ParticipantAttempt，再次点击开始或继续挑战时，应返回已有 attempt。
  3. attempt 需要记录用户所属活动、用户 ID、当前状态、当前进度、完成时间、总分等必要信息。
  4. 用户未完成挑战时，再次进入活动应展示继续挑战入口。
  5. 用户完成挑战后，再次进入活动应展示当前排名或最终排名入口。
  6. 活动截止后，用户是否还能继续未完成挑战，需要按截止规则处理。

* 特殊情况：

  1. 用户重复点击开始挑战。
  2. 用户多设备进入同一活动。
  3. 用户参加后未开始第一手就离开。
  4. 用户已完成挑战后再次进入活动。
  5. 活动截止后用户再次进入活动。

* 处理结果：

  1. 重复点击开始挑战不创建新的有效 attempt。
  2. 用户重新进入活动时，系统返回已有 attempt 和当前挑战进度。
  3. 已完成用户进入排名相关页面。
  4. 未完成用户进入继续挑战流程或截止后的不可继续状态。

### 规则 3：手牌分配规则

* 规则对象：

  * 业务范围：用户挑战手牌生成
  * 功能模块：用户参赛与手牌分配
  * 具体对象：AttemptHandAssignment

* 主规则：

  用户成功参加活动后，服务端需要根据活动配置生成本次挑战的 N 手牌 assignment。N 等于 `activity.play_hand_count`。assignment 生成后必须持久化，后续不能因为刷新、退出、换设备、重新进入活动而重新随机。

* 子规则：

  1. 手牌分配由服务端完成，不能由客户端随机。
  2. 分配数量必须等于 `activity.play_hand_count`。
  3. `required_hand_ids` 中的手牌必须被分配给用户。
  4. 除必选手外，其余手牌按 `sampling_policy` 从可选池中分配。
  5. 每条 assignment 需要记录 `attempt_id`、`hand_id`、`display_order`、`source` 等信息。
  6. `source` 用于区分该手牌来自必选手还是随机池。
  7. `display_order` 用于控制用户实际游玩顺序。
  8. `display_order` 可以随机，但计分、榜单、结算应按底层 `hand_id` 进行。
  9. assignment 一旦生成，后续恢复、计分、榜单、结算都必须基于同一份 assignment。

* 特殊情况：

  1. 用户 join 后立即退出。
  2. 用户刷新页面后重新进入活动。
  3. 用户换设备继续挑战。
  4. 用户已有 assignment，但活动配置发生变化。
  5. 可选池数量不足以补齐 `play_hand_count`。

* 处理结果：

  1. 用户 join 后立即退出，assignment 仍然保留。
  2. 用户重新进入活动时，读取已有 assignment，不重新随机。
  3. 如果可选池不足，活动配置应在发布前被拦截。
  4. 如果活动发布后配置变化影响已生成 assignment，需要作为待确认点单独处理，不在本期默认支持动态变更。

### 规则 4：PvE 对局规则

* 规则对象：

  * 业务范围：用户逐手完成 PvE 挑战
  * 功能模块：PvE 对局与恢复
  * 具体对象：HandAttempt、ActionEvent、GameSnapshot

* 主规则：

  用户按照 assignment 中的 `display_order` 逐手完成 PvE 对局。每手对局由服务端控制牌局状态、合法动作、AI 行动、结算结果和进度流转。

* 子规则：

  1. 用户每次进入挑战时，系统根据当前进度返回当前应进行的手牌。
  2. 用户端展示进度时，应展示第 X / N 手。
  3. N 来自 `activity.play_hand_count`。
  4. 用户提交动作时，服务端需要校验动作合法性。
  5. 服务端推进 AI 行动和牌局状态。
  6. 一手牌结束后，系统进入本手结果与计分流程。
  7. 当前手完成后，用户才能进入下一手。
  8. 每手之间应相互独立，不应因为上一手输赢影响下一手初始条件。
  9. 活动进行中，用户侧不应泄露未来牌面、AI 隐藏手牌、其他用户完整打法等可能影响公平性的内容。

* 特殊情况：

  1. 用户在对局中途离开。
  2. 用户动作提交后网络中断。
  3. 用户在结果页离开。
  4. 用户多设备同时打开同一手牌。
  5. 活动截止时用户正在进行某一手。

* 处理结果：

  1. 用户重新进入时，系统根据恢复规则返回当前手牌、结果页或活动完成状态。
  2. 已完成手牌不重复结算。
  3. 未完成手牌是否允许继续，需要根据活动截止状态判断。
  4. 对局中涉及幂等、动作重复提交、多设备冲突等技术细节，后续在技术详设中补充。

### 规则 5：恢复规则

* 规则对象：

  * 业务范围：用户中途离开后继续活动
  * 功能模块：PvE 对局与恢复
  * 具体对象：ParticipantAttempt、AttemptHandAssignment、HandAttempt、GameSnapshot

* 主规则：

  用户中途离开后，再次进入活动时，系统需要恢复用户当前挑战进度，不能丢失已生成 assignment、已完成手牌、当前手牌状态和已获得分数。

* 子规则：

  1. 用户恢复时，服务端先查询当前活动下的有效 attempt。
  2. 服务端读取该 attempt 对应的 assignment。
  3. 服务端判断用户已完成多少手。
  4. 如果用户未完成 N 手，返回当前应继续的手牌或结果页。
  5. 如果用户已完成 N 手，返回当前排名或最终排名入口。
  6. 如果活动已截止，系统需要根据截止规则判断用户是否还能继续未完成挑战。
  7. 恢复进度中的 N 统一取 `activity.play_hand_count`。
  8. 本期至少需要支持基础进度恢复：已完成几手、当前第几手、当前应继续还是查看结果。

* 特殊情况：

  1. 用户 join 后尚未开始第一手就离开。
  2. 用户完成一手后停留在结果页离开。
  3. 用户完成部分手牌后离开。
  4. 用户完成全部 N 手后离开。
  5. 活动截止后用户再进入。

* 处理结果：

  1. 未开始第一手的用户恢复到第 1 手或开始挑战状态。
  2. 停留在结果页离开的用户恢复到结果页或下一手入口。
  3. 部分完成用户恢复到当前待完成手牌。
  4. 全部完成用户进入排名页。
  5. 活动截止后未完成用户是否可继续，按截止规则处理。

### 规则 6：每手计分规则

* 规则对象：

  * 业务范围：用户每手 PvE 对局结果反馈
  * 功能模块：每手计分
  * 具体对象：HandAttempt、ScoreSnapshot

* 主规则：

  用户每完成一手牌，系统需要计算并展示本手 raw 结果和 0-100 分。每手分数需要保存为得分快照，用于用户结果页展示、总分聚合、当前榜、最终榜和后续追溯。

* 子规则：

  1. raw 结果表示本手净收益，建议用 BB 作为单位。
  2. 0-100 分表示用户在同 `hand_id` 或可比较手牌中的相对表现。
  3. 每手结果页至少展示 raw 结果、0-100 分、分数状态。
  4. 分数状态包括参考分、暂定分、最终分。
  5. 活动进行中，如果真人样本不足，可以展示参考分或暂定分。
  6. 活动未截止前，用户看到的分数可能随样本变化。
  7. 活动最终结算后，应生成最终分。
  8. 每手得分需要和 `hand_id`、`attempt_id`、`score_type`、`cohort_size`、`calculated_at` 等信息关联。
  9. 用户总分按本次 assignment 中 N 手得分聚合，不写死为 10 手平均。

* 特殊情况：

  1. 本手完成后样本不足。
  2. 本手计分失败。
  3. 活动中分数发生变化。
  4. 活动最终结算后分数与活动中暂定分不同。
  5. 用户完成部分手牌但未完成全部 N 手。

* 处理结果：

  1. 样本不足时，用户侧应明确分数为参考或暂定。
  2. 计分失败时，需要保留本手结果，并进入待重算或异常处理。
  3. 活动最终结算后，用户侧展示最终分。
  4. 未完成全部 N 手的用户，不进入当前完成榜和最终主榜。

### 规则 7：总分聚合规则

* 规则对象：

  * 业务范围：用户活动成绩计算
  * 功能模块：每手计分、当前榜 / 最终榜
  * 具体对象：ParticipantAttempt、ScoreSnapshot

* 主规则：

  用户活动总分由本次 assignment 中 N 手得分聚合得到。N 等于 `activity.play_hand_count`。只有用户完成全部 N 手后，才可以生成活动总分并进入当前榜。

* 子规则：

  1. 用户总分只统计该用户本次 assignment 中的手牌。
  2. 用户总分不统计未被分配给该用户的手牌。
  3. 用户总分不统计未完成手牌。
  4. MVP 阶段默认每手权重一致。
  5. 如后续支持不同手牌权重，应由活动配置控制。
  6. 当前榜使用活动中的暂定分聚合。
  7. 最终榜使用最终结算后的最终分聚合。
  8. 完成条件统一为 `completed_hand_count == activity.play_hand_count`。

* 特殊情况：

  1. 用户只完成部分手牌。
  2. 某一手暂时只有参考分。
  3. 活动最终结算后，某些手牌分数发生变化。
  4. 活动配置中的 `play_hand_count` 不是 10。

* 处理结果：

  1. 未完成全部 N 手时，不生成当前榜排名。
  2. 完成全部 N 手后，生成当前总分。
  3. 活动截止并结算后，生成最终总分。
  4. 所有总分计算均基于 `play_hand_count`，不写死 10。

### 规则 8：当前榜规则

* 规则对象：

  * 业务范围：活动进行中排名反馈
  * 功能模块：当前榜 / 最终榜
  * 具体对象：Leaderboard、ParticipantAttempt

* 主规则：

  用户完成 `activity.play_hand_count` 手后，可以查看当前排名。活动截止前，当前榜仅表示当前完成用户中的暂定排名，不能表达为最终排名。

* 子规则：

  1. 当前榜只统计已完成 N 手的用户。
  2. N 等于 `activity.play_hand_count`。
  3. 当前榜展示当前总分、当前排名、参与样本量或更新时间等信息。
  4. 当前榜必须明确标记为暂定排名。
  5. 当前榜不应使用“最终排名”“已锁定”“保证第 X 名”等文案。
  6. 活动进行中，后续用户完成挑战后，当前榜可能变化。
  7. 如果当前分数使用参考分或暂定分，用户侧需要能感知该状态。
  8. 未完成 N 手的用户不进入当前完成榜。

* 特殊情况：

  1. 用户刚完成 N 手，但榜单仍在更新。
  2. 当前榜样本量较少。
  3. 用户分数使用参考分。
  4. 活动已截止但最终结算未完成。

* 处理结果：

  1. 当前榜展示为暂定。
  2. 榜单更新时间或样本量应尽量展示。
  3. 活动已截止但未结算完成时，不应直接展示最终排名。
  4. 最终结算完成后，用户进入最终榜。

### 规则 9：最终榜规则

* 规则对象：

  * 业务范围：活动截止后最终排名
  * 功能模块：当前榜 / 最终榜、截止结算
  * 具体对象：LeaderboardSnapshot

* 主规则：

  活动截止并完成最终结算后，系统生成最终榜。最终榜只统计截止前完成 `activity.play_hand_count` 手且符合入榜条件的用户。最终榜生成后作为活动最终排名结果展示。

* 子规则：

  1. 最终榜在活动截止后生成。
  2. 最终榜需要基于最终结算结果。
  3. 最终榜只统计完成 N 手的用户。
  4. N 等于 `activity.play_hand_count`。
  5. 用户 `completed_at` 需要小于或等于 `activity.end_time`。
  6. 未完成 N 手的用户不进入最终主榜。
  7. 最终榜需要和活动中的当前榜区分。
  8. 最终榜生成后，用户侧展示最终排名、最终总分、最终结果。
  9. 最终榜结果应支持后续追溯到用户 assignment、每手得分和结算结果。

* 特殊情况：

  1. 活动截止时用户未完成 N 手。
  2. 活动截止时用户刚完成但结算未完成。
  3. 最终结算失败。
  4. 用户存在异常参赛记录或疑似作弊。
  5. 当前榜排名和最终榜排名不同。

* 处理结果：

  1. 未完成 N 手的用户不进入最终主榜。
  2. 结算未完成时，用户侧展示结算中或暂不展示最终榜。
  3. 结算失败时，活动状态进入异常或待重试状态。
  4. 当前榜和最终榜不一致时，以最终榜为准。

### 规则 10：截止结算规则

* 规则对象：

  * 业务范围：活动截止后的成绩结算
  * 功能模块：截止结算
  * 具体对象：Activity、ParticipantAttempt、ScoreSnapshot、LeaderboardSnapshot

* 主规则：

  活动到达截止时间后，系统进入结算流程。结算流程需要锁定有效完成用户，重新计算最终分，生成最终榜单，并将活动状态更新为已结算。

* 子规则：

  1. 活动到达 `end_time` 后，未参加用户不能再参加。
  2. 活动到达 `end_time` 后，已参加但未完成 N 手的用户默认不进入最终主榜。
  3. N 等于 `activity.play_hand_count`。
  4. 截止前完成 N 手的用户进入最终结算候选。
  5. 系统按每个用户的 assignment 聚合最终分。
  6. 系统根据最终分生成最终榜单。
  7. 最终榜单生成后，活动状态更新为已结算。
  8. 最终结算结果应与活动中的当前榜区分。
  9. 最终结算应支持重试或异常处理，具体方式由技术详设确认。

* 特殊情况：

  1. 活动截止时有用户正在对局。
  2. 活动截止时有用户已完成部分手牌。
  3. 结算任务执行失败。
  4. 结算过程中发现部分得分缺失。
  5. 结算后发现异常用户。

* 处理结果：

  1. 未完成 N 手的用户不进入最终主榜。
  2. 已完成 N 手且完成时间符合要求的用户进入最终结算。
  3. 结算失败时，不展示最终榜或展示结算异常状态。
  4. 结算成功后，用户侧开放最终排名。
  5. 异常用户处理规则如需纳入本期，需要在待确认点中进一步确认。

### 规则 11：防泄题与展示规则

* 规则对象：

  * 业务范围：活动进行中的公平性保护
  * 功能模块：PvE 对局与恢复、当前榜 / 最终榜
  * 具体对象：用户端展示内容、复盘内容、排名内容

* 主规则：

  活动进行中，用户侧不应展示会影响比赛公平性的内容。包括未来牌面、AI 隐藏手牌、其他用户完整打法、高分用户具体行动线等。

* 子规则：

  1. 用户在对局中只能看到当前应可见的牌局信息。
  2. 用户每手结束后，可以看到自己的 raw 结果和分数。
  3. 活动进行中，当前排名可以展示，但必须标记为暂定。
  4. 活动进行中，不展示其他用户完整牌谱和完整行动线。
  5. 活动进行中，不展示未来公共牌。
  6. 活动进行中，不展示 AI 未公开隐藏手牌。
  7. 活动最终结算后，是否开放完整复盘和隐藏信息，需要根据本期范围确认；如未纳入 7.15 主流程，则不作为本期强制能力。

* 特殊情况：

  1. 用户完成某一手后想立即复盘。
  2. 用户查看当前榜时想看高分用户打法。
  3. 用户分享当前成绩。
  4. 活动已截止但最终结算未完成。

* 处理结果：

  1. 活动进行中只展示不泄题的反馈内容。
  2. 当前榜不暴露具体牌面和其他用户完整打法。
  3. 完整复盘是否开放，后续在范围或待确认点中明确。
  4. 分享内容如纳入本期，需要避免包含具体牌面和隐藏信息。

### 规则 12：Phase 2 能力排除规则

* 规则对象：

  * 业务范围：7.15 交付边界
  * 功能模块：整体范围控制
  * 具体对象：Phase 2 及后续能力

* 主规则：

  7.15 当前只交付 Phase 0 + Phase 1，不把 Phase 2 及后续能力纳入本期主流程、验收标准和强制实现范围。

* 子规则：

  1. 后台完整数据统计看板不纳入本期主范围。
  2. 每手详细统计分析不纳入本期主范围。
  3. 决策点正确率不纳入本期主范围。
  4. 动作分布分析不纳入本期主范围。
  5. EV loss 计算不纳入本期主范围。
  6. Top / Bottom 用户分群对比不纳入本期主范围。
  7. 自动生成教学素材不纳入本期主范围。
  8. 好友榜、私房挑战、徽章体系不纳入本期主范围。
  9. 高级风控和复杂作弊识别不纳入本期主范围。
  10. 多座位轮转、团队赛、直播裁判等高级复式玩法不纳入本期主范围。

* 特殊情况：

  1. 如果研发实现主流程时顺带产生基础数据，可保留数据结构或日志，但不承诺后台完整展示。
  2. 如果 CTO 或产品临时要求加入 Phase 2 能力，需要重新评估范围和排期。
  3. 如果某个 Phase 2 能力是 Phase 1 必须依赖，需要单独标记为技术依赖，而不是默认纳入产品范围。

* 处理结果：

  1. 本期评审和验收聚焦活动配置、用户参赛、手牌分配、PvE 对局、恢复、每手计分、当前榜、最终榜、截止结算。
  2. 超出 Phase 0 + Phase 1 的内容进入待确认点或后续版本规划。
  3. 避免因为后台统计、教学分析、复杂风控等内容影响 7.15 主链路交付。

## 5. 验收标准

请说明本次需求需要验收哪些范围、哪些主流程场景算通过，以及哪些情况不能算通过。

### 5.1 验收范围

* 用户端：

  需要验收。

  验收范围包括：

  1. 用户可以看到并进入 PvE 排名赛活动。
  2. 用户可以开始或继续挑战。
  3. 用户可以按照后台配置的 `play_hand_count` 完成 N 手 PvE 对局。
  4. 用户端进度展示为第 X / N 手，N 不能写死为 10。
  5. 每手完成后，用户可以看到 raw 结果和 0-100 分。
  6. 用户完成 N 手后，可以查看当前排名。
  7. 当前排名需要明确标记为暂定排名。
  8. 活动截止并完成结算后，用户可以查看最终排名。
  9. 用户中途离开后，再次进入可以恢复活动进度。

* 管理后台：

  需要验收。

  验收范围包括：

  1. 后台可以配置 PvE 排名赛活动基础信息。
  2. 后台可以配置活动开始时间和截止时间。
  3. 后台可以绑定或选择牌局包。
  4. 后台可以配置用户实际挑战手数 `play_hand_count`。
  5. 后台可以配置或指定本期使用的必选手 / 随机手策略。
  6. 后台可以配置或指定本期计分规则。
  7. 后台可以发布活动。
  8. 活动发布后，用户端可以看到并参与活动。

* 配置项 / 配置表：

  需要验收。

  验收范围包括：

  1. 活动配置中存在 `play_hand_count`，且该值参与用户进度、完成判断、入榜判断和结算判断。
  2. 活动配置中存在 `hand_pack` 或等价牌局包配置。
  3. 活动配置中存在活动开始时间、截止时间、活动状态。
  4. 活动配置中存在计分规则或计分模式配置。
  5. 如果本期支持必选手 / 随机手配置，需要验收 `required_hand_ids`、`sampling_policy` 或等价配置是否生效。

* 服务端逻辑：

  需要验收。

  验收范围包括：

  1. 用户参加活动时，服务端创建或返回唯一有效 attempt。
  2. 服务端根据 `play_hand_count` 生成 N 手 assignment。
  3. assignment 生成后持久化，用户刷新、退出、换设备后不重新分配。
  4. 服务端支持 PvE 对局推进和本手结算。
  5. 服务端支持每手 raw 结果和 0-100 分计算。
  6. 服务端支持用户完成 N 手后的当前排名计算。
  7. 服务端支持活动截止后的最终结算。
  8. 服务端支持用户中途离开后的进度恢复。

* 其他系统 / 第三方：

  待确认。

  验收范围包括：

  1. 如复用已有 PvE / AI 练习场对局能力，需要验收本需求接入后不影响原有普通练习流程。
  2. 如复用已有 AI 行动能力，需要验收活动对局中 AI 行动可以正常推进。
  3. 如复用已有牌局结算能力，需要验收每手可稳定产出 raw 结果。
  4. 消息通知、BI 导出、完整数据看板不作为 7.15 必须验收范围。

### 5.2 主流程验收场景

| 主流程场景                     | 操作 / 条件                                                   | 预期结果                                                      |
| ------------------------- | --------------------------------------------------------- | --------------------------------------------------------- |
| 场景 1：后台配置活动               | 后台创建 PvE 排名赛活动，配置活动时间、牌局包、`play_hand_count`、计分规则等信息，并发布活动 | 活动发布成功，用户端可见该活动                                           |
| 场景 2：`play_hand_count` 生效 | 后台配置 `play_hand_count = N`，用户进入活动                         | 用户端展示挑战总手数为 N，进度展示为第 X / N 手，不写死 10                       |
| 场景 3：用户首次参加活动             | 用户点击开始挑战                                                  | 服务端创建 ParticipantAttempt，并根据活动配置生成 N 手 assignment         |
| 场景 4：重复点击开始挑战             | 同一用户在同一活动中重复点击开始 / 重新进入活动                                 | 系统返回已有有效 attempt，不创建多个有效参赛记录                              |
| 场景 5：手牌分配持久化              | 用户开始挑战后退出、刷新或换设备重新进入                                      | 系统读取原有 assignment，用户分配到的 N 手牌不变化                          |
| 场景 6：用户完成一手 PvE 对局        | 用户进入某一手牌并完成对局                                             | 系统完成本手结算，生成 raw 结果和 0-100 分，用户端可查看本手结果                    |
| 场景 7：用户逐手完成挑战             | 用户按照分配顺序完成全部 N 手牌                                         | 系统记录 `completed_hand_count = play_hand_count`，用户挑战状态变为已完成 |
| 场景 8：完成后查看当前排名            | 用户完成 N 手后进入排名页                                            | 用户可以看到当前总分、当前排名，并且页面明确标记为暂定排名                             |
| 场景 9：当前榜不等于最终榜            | 活动尚未截止，用户查看排名                                             | 页面不出现“最终排名”“已锁定”“保证第 X 名”等表达                              |
| 场景 10：活动截止结算              | 活动到达截止时间，系统执行最终结算                                         | 系统锁定截止前完成 N 手的用户，重新计算最终成绩，生成最终榜单                          |
| 场景 11：查看最终排名              | 活动已截止且结算完成，用户进入活动结果页                                      | 用户可以查看最终总分和最终排名                                           |
| 场景 12：未完成用户不进最终主榜         | 用户在活动截止前未完成 N 手                                           | 用户不进入最终主榜，可查看已完成进度或截止说明，具体展示以后续规则为准                       |
| 场景 13：中途离开恢复              | 用户完成部分手牌后退出，再次进入活动                                        | 系统恢复到当前应继续的手牌、结果页或当前进度，不丢失已完成记录                           |
| 场景 14：完成后恢复               | 用户完成 N 手后退出，再次进入活动                                        | 系统展示当前排名或最终排名入口，不要求用户重新挑战                                 |
| 场景 15：普通 PvE 流程不受影响       | 用户进入原有 AI 练习场普通对局                                         | 普通 PvE 对局流程不被本次排名赛活动影响                                    |

### 5.3 不通过情况

* 活动配置中 `play_hand_count` 未生效，用户端或服务端仍写死为 10。
* 用户参加活动后，没有生成 N 手 assignment。
* 用户刷新、退出或换设备后，assignment 被重新随机。
* 同一用户同一活动下产生多个有效 attempt。
* 用户未完成 `play_hand_count` 手，却进入当前榜或最终主榜。
* 用户完成 `play_hand_count` 手后，无法查看当前排名。
* 活动未截止时，页面把当前排名展示为最终排名。
* 每手完成后，没有展示 raw 结果。
* 每手完成后，没有展示 0-100 分。
* 用户中途离开后，再次进入无法恢复挑战进度。
* 活动截止后，系统无法生成最终排名。
* 最终排名包含未完成 `play_hand_count` 手的用户。
* 后台配置活动后，用户端无法看到或参与活动。
* 本需求影响了原有普通 AI 练习场流程，导致普通 PvE 无法正常使用。
* 将 Phase 2 能力作为 7.15 必须验收项，导致主流程交付范围扩大。

## 7. 异常处理

请说明已知的主要异常；不要求一次性覆盖所有异常，开发过程中发现未覆盖异常时，由研发记录并和产品确认处理效果。

### 7.1 已知异常

| 异常发生位置 | 异常情况                         | 处理方式                             | 用户 / 系统表现                      |
| ------ | ---------------------------- | -------------------------------- | ------------------------------ |
| 活动配置   | 牌局包总手数小于 `play_hand_count`   | 后台阻止发布活动，并提示配置不合法                | 后台展示错误提示；活动不能发布                |
| 活动配置   | 必选手数量大于 `play_hand_count`    | 后台阻止发布活动，并提示必选手数量超过用户实际挑战手数      | 后台展示错误提示；活动不能发布                |
| 活动配置   | 未配置活动开始时间或截止时间               | 后台阻止发布活动                         | 后台提示补充活动时间                     |
| 活动配置   | 未绑定牌局包                       | 后台阻止发布活动                         | 后台提示请选择牌局包                     |
| 活动配置   | `play_hand_count` 未配置或配置为非法值 | 后台阻止发布活动                         | 后台提示挑战手数配置错误                   |
| 活动配置   | 活动已发布后尝试修改关键配置               | 默认不允许直接修改关键配置；如需调整，建议复制活动重新发布    | 后台提示已发布活动关键配置不可修改              |
| 活动入口   | 活动未开始                        | 用户不能开始挑战                         | 用户端展示活动未开始或开始时间                |
| 活动入口   | 活动已截止                        | 用户不能新参加活动                        | 用户端展示活动已截止；如已完成可查看排名           |
| 活动入口   | 活动不存在或已下线                    | 用户不能进入活动                         | 用户端展示活动不存在、已下线或不可参与            |
| 用户参赛   | 用户重复点击开始挑战                   | 服务端返回已有有效 attempt，不创建新 attempt   | 用户继续进入同一挑战进度                   |
| 用户参赛   | 用户多设备同时进入活动                  | 以服务端最新 attempt 状态为准              | 用户端展示最新进度；必要时提示状态已更新           |
| 用户参赛   | 用户 join 后立即退出                | attempt 和 assignment 保留          | 用户再次进入时显示继续挑战，进度为 0 / N 或第 1 手 |
| 手牌分配   | assignment 生成失败              | 不进入对局；服务端返回错误并记录日志               | 用户端提示开始失败，可重试                  |
| 手牌分配   | 用户已存在 assignment，但再次进入活动     | 读取已有 assignment，不重新随机            | 用户看到的手牌进度和上次保持一致               |
| 手牌分配   | 可选池不足以补齐 `play_hand_count`   | 原则上发布前拦截；如运行时发现，阻止开始挑战并记录异常      | 用户端提示活动配置异常，无法开始               |
| PvE 对局 | 拉取当前手牌状态失败                   | 客户端允许重试；服务端记录异常                  | 用户端提示加载失败，可重新进入或刷新             |
| PvE 对局 | 用户提交非法动作                     | 服务端拒绝该动作，不推进牌局                   | 用户端提示当前动作不可用，并刷新最新合法状态         |
| PvE 对局 | 用户动作提交后网络中断                  | 客户端重试；服务端按幂等规则处理                 | 用户端恢复后展示服务端确认后的最新状态            |
| PvE 对局 | 用户重复提交同一动作                   | 服务端根据 `request_id` 或等价幂等机制识别重复请求 | 不重复写入动作，不重复推进牌局                |
| PvE 对局 | AI 行动推进失败                    | 当前手进入异常或待重试状态；服务端记录日志            | 用户端提示对局处理中或稍后重试                |
| PvE 对局 | 本手结算失败                       | 本手进入待结算或异常状态；服务端记录并支持重试          | 用户端提示结算中，不直接进入下一手或结果页          |
| PvE 对局 | 用户在对局中途离开                    | 保存服务端已确认进度                       | 用户再次进入时恢复当前手牌或最新确认状态           |
| PvE 对局 | 用户在结果页离开                     | 已完成手牌和得分保留                       | 用户再次进入时恢复结果页或下一手入口             |
| 进度恢复   | 用户重新进入时找不到有效 attempt         | 如果用户未开始过，展示开始挑战；如果数据异常，提示无法恢复    | 用户端展示开始入口或异常提示                 |
| 进度恢复   | 找到 attempt 但缺少 assignment    | 视为数据异常；阻止继续挑战并记录日志               | 用户端提示挑战数据异常，请稍后重试              |
| 进度恢复   | 已完成手数与 assignment 数量不一致      | 以服务端记录为准，进入异常排查；不自动重置 assignment | 用户端提示进度异常或返回可恢复的最新状态           |
| 每手计分   | raw 结果计算失败                   | 不生成有效分数；记录异常，支持重算                | 用户端提示结果计算中或异常                  |
| 每手计分   | 0-100 分计算失败                  | 保留 raw 结果，分数进入待计算 / 待重试状态        | 用户端可展示 raw 结果，分数显示计算中          |
| 每手计分   | 样本不足                         | 展示参考分或暂定分                        | 用户端明确标记为参考 / 暂定，不展示为最终分        |
| 每手计分   | 活动中暂定分后续变化                   | 以最新计算结果或结算结果为准                   | 用户端当前榜可能变化；最终榜以结算后为准           |
| 当前榜    | 用户未完成 N 手尝试查看当前榜             | 不返回当前排名                          | 用户端提示完成全部挑战后查看排名               |
| 当前榜    | 当前榜计算失败                      | 返回榜单计算中或重试                       | 用户端提示排名计算中                     |
| 当前榜    | 活动未截止但页面展示最终排名文案             | 视为验收不通过；前端文案需修正                  | 用户端必须展示当前 / 暂定排名               |
| 截止结算   | 活动截止时用户未完成 N 手               | 默认不进入最终主榜                        | 用户端展示未完成或截止说明                  |
| 截止结算   | 活动截止时用户正在对局                  | 默认按未完成处理，是否允许完成当前手需待确认           | 用户端展示截止状态或按确认规则处理              |
| 截止结算   | 结算任务执行失败                     | 活动进入结算异常或待重试状态；后台 / 服务端支持重试      | 用户端展示结算中或暂不可查看最终排名             |
| 截止结算   | 部分用户得分缺失                     | 缺失数据进入异常处理；不应生成错误最终榜             | 系统阻止最终榜发布或标记结算异常               |
| 最终榜    | 最终榜生成失败                      | 不开放最终排名；记录异常并重试结算                | 用户端展示结算中 / 稍后查看                |
| 最终榜    | 最终榜包含未完成 N 手用户               | 视为严重错误；需要重新结算                    | 最终榜不可发布或需要回滚重算                 |
| 最终榜    | 当前榜排名和最终榜排名不同                | 正常情况，以最终榜为准                      | 用户端展示最终排名，并与当前榜区分              |
| 防泄题    | 活动进行中展示未来牌面、AI 隐藏手牌或其他用户完整打法 | 视为严重问题；需要立即修复展示逻辑                | 用户端不应出现泄题内容                    |
| 旧流程影响  | 普通 AI 练习场无法正常使用              | 回归修复，排名赛活动与普通练习场流程隔离             | 普通练习场应保持原有可用状态                 |
