## 2. 核心设计决策类

### Q1：为什么 7.15 阶段选择 MySQL 作为唯一事实源？

结论：因为用户参赛、手牌分配、计分、恢复、排行榜、最终结算都需要持久化、可事务保证、可复查，MySQL 更适合作为事实源。

说明：
7.15 的核心风险不是查询慢，而是比赛结果不一致，例如重复计分、重复入榜、服务重启后进度丢失、最终榜和计分结果不一致。MySQL 可以通过事务、行锁、唯一约束和持久化记录保证这些关键数据的正确性。

研发口径：

```text
所有比赛事实数据以 MySQL 为准。
Redis、前端缓存、服务端内存都不能作为最终判断依据。
```

---

### Q2：为什么 Redis 不能作为排行榜事实源？

结论：Redis 可以提升查询性能，但不适合承载最终可信比赛结果。

说明：
Redis 数据可能过期、被淘汰、被清空、重启丢失，也不适合作为最终榜排名的唯一依据。如果 Redis 作为事实源，一旦缓存异常，就可能导致排行榜结果丢失或不可复查。

研发口径：

```text
Redis 只做当前榜分页缓存、最终榜分页缓存、可选我的排名缓存和活动结算锁。
leaderboard_result 才是排行榜事实源。
```

---

### Q3：为什么 7.15 只恢复活动进度，不恢复单手中途牌局？

结论：因为单手中途恢复需要保存动作日志和牌局快照，明显超出 7.15 的交付范围。

说明：
如果要恢复到 flop、turn、river 或某个行动点，需要保存公共牌、底池、筹码、当前行动方、用户每一步动作、AI 每一步动作等状态。当前 7.15 的目标是 PvE 排名赛闭环，不是完整牌局恢复或回放系统。

研发口径：

```text
7.15 恢复到当前未完成手牌。
如果该手未完成，下次从这手开头重新打。
```

---

### Q4：为什么当前榜和最终榜要分开设计？

结论：因为当前榜是活动进行中的动态排名，最终榜是活动截止后的冻结排名，两者语义不同。

说明：
当前榜会随着新用户完赛不断变化，不能提前固定 `rank_no`。最终榜在活动截止后生成，应写入固定排名，方便用户复查和后续问题排查。

研发口径：

```text
当前榜动态查询，不落库 rank_no。
最终榜结算后写入 rank_no、is_final、finalized_at。
```

---

## 3. 排行榜设计类

### Q5：为什么当前榜不提前落库 rank_no？

结论：因为当前榜排名会持续变化，提前落库会带来频繁更新和一致性成本。

说明：
如果每个用户完成 N 手后都更新所有人的当前排名，会导致大量写操作。当前榜只是活动进行中的临时排名，按排序条件实时查询即可。

研发口径：

```text
当前榜查询时按 total_score DESC、complete_time ASC 动态排序。
rank_no 只在最终榜阶段写入。
```

---

### Q6：为什么最终榜必须冻结 rank_no？

结论：因为活动结束后，排名需要稳定、可复查、可展示。

说明：
最终榜是活动结果，应在截止结算后固定下来。用户后续查看第几名时，不应该因为查询时机、缓存状态或后续异常数据变化导致排名变化。

研发口径：

```text
Worker 结算最终榜时写入 rank_no、is_final = 1、finalized_at。
```

---

### Q7：为什么用户必须完成 N 手后才进入排行榜？

结论：为了保证排名口径公平一致。

说明：
如果未完成用户也进入榜单，就会出现完成手数不同的用户互相比较，排名没有公平性。排行榜只能比较完成同一挑战手数的用户。

研发口径：

```text
未完成 N 手用户不进入 current leaderboard，也不进入 final leaderboard。
```

---

### Q8：排行榜排序规则为什么是 total_score DESC、complete_time ASC？

结论：总分优先，同分时完成时间早者优先。

说明：
这是 7.15 第一版最简单、可解释、可实现的排序口径。更复杂的 tie-breaker 可以后续扩展，但不建议在 7.15 第一版引入。

研发口径：

```text
ORDER BY total_score DESC, complete_time ASC
```

---

### Q9：total_score 聚合规则是否确定为 AVG(hand_score.score)？

结论：当前建议是 AVG，但最终需要产品或计分规则确认。

说明：
单手 `score` 是 0-100，如果取平均值，`total_score` 也保持在 0-100 区间，便于展示和理解。但如果产品明确要总和、加权、去最高最低分等规则，应以产品规则为准。

研发口径：

```text
默认建议 total_score = AVG(hand_score.score)。
最终以产品确认的计分规则为准。
```

---

### Q10：如果产品后续调整计分规则，排行榜字段是否需要调整？

结论：如果只是聚合方式变化，字段大概率不变；如果出现多套规则版本，需要扩展规则版本字段或规则表。

说明：
7.15 当前只需要保存单手分数和活动总分。如果后续不同活动使用不同计分规则，需要能追溯当时使用的规则版本。

研发口径：

```text
7.15 不做复杂计分规则版本。
后续多规则时再扩展 scoring_rule_id 或 scoring_rule_version。
```

---

## 4. 事务与一致性类

### Q11：为什么最后一手计分和入榜必须放在同一个事务？

结论：为了避免计分、完成状态、榜单结果三者不一致。

说明：
最后一手完成时，需要同时完成 `hand_score` 写入、`user_hand` 完成、`entry` 完成、`leaderboard_result` 写入。如果这些操作拆开，可能出现手牌已计分但没入榜，或者已入榜但计分不完整。

研发口径：

```text
最后一手 submit hand 内，计分、entry completed、leaderboard_result 必须同事务提交。
```

---

### Q12：为什么完成 N 手不能只看 completed_hand_count？

结论：因为 `completed_hand_count` 是进度字段，不能单独证明计分记录完整。

说明：
如果某些异常导致 `completed_hand_count` 被更新，但 `hand_score` 缺失，直接入榜会导致总分和排名不可信。所以入榜前需要校验实际计分记录数量。

研发口径：

```text
entry.completed_hand_count = play_hand_count
且 hand_score_count = play_hand_count
才允许入榜。
```

---

### Q13：为什么重复提交要返回已有计分结果，而不是直接报错？

结论：因为重复提交通常来自正常网络重试或客户端未收到响应，不应该让用户感知为失败。

说明：
如果第一次提交已经成功，但客户端没收到响应，用户再次提交时，返回已有结果可以让前端继续推进，不会重复计分，也不会产生错误体验。

研发口径：

```text
重复 submit 查询已有 hand_score 返回。
如果最后一手已入榜，同时返回榜单入口。
```

---

### Q14：Redis 锁已经有了，为什么 MySQL 还要做最终兜底？

结论：Redis 锁只能减少并发结算，不能保证最终正确性。

说明：
Redis 锁可能过期、释放失败、服务重启、任务执行超时。最终能判断活动是否已结算、最终榜是否已冻结的，必须是 MySQL 状态和事务。

研发口径：

```text
Redis 锁负责减少重复执行。
MySQL select for update + activity.status = finalized 负责最终兜底。
```

---

### Q15：如果 hand_score 写入成功但 leaderboard_result 缺失，应该如何处理？

结论：正常设计下不应发生；如果异常历史数据出现，最终结算阶段可以兜底补齐。

说明：
最后一手计分和入榜必须同事务提交，因此不应留下 `hand_score` 成功但 `leaderboard_result` 缺失的半完成数据。兜底补齐只作为异常补偿，不是主流程。

研发口径：

```text
主流程：最后一手同事务写 leaderboard_result。
补偿流程：Worker 结算时校验完整条件后补齐缺失 leaderboard_result。
```

---

## 5. 断线 / 重启 / 继续类

### Q16：resume 接口为什么只根据 MySQL 状态判断下一步？

结论：因为 MySQL 是唯一可靠的恢复依据。

说明：
前端状态可能丢失或不可信，服务端内存会因为重启丢失，Redis 也不是活动进度事实源。只有 MySQL 保存了用户是否参赛、分配了哪些手牌、完成了哪些手牌、是否入榜。

研发口径：

```text
resume 查询 activity、entry、user_hand、hand_score、leaderboard_result 后返回 nextAction。
```

---

### Q17：服务端重启后为什么还能恢复用户进度？

结论：因为关键进度都落在 MySQL 中，不依赖服务端内存。

说明：
用户参赛记录在 `user_entry`，分配手牌在 `user_hand`，计分结果在 `hand_score`，榜单结果在 `leaderboard_result`。服务重启后重新查询即可恢复。

研发口径：

```text
服务端重启不影响活动进度恢复。
```

---

### Q18：最后一手提交成功但客户端没收到响应，怎么恢复？

结论：再次 resume 或 submit 时返回已有完赛结果和榜单入口。

说明：
如果事务已经提交，`entry.status = completed`，`hand_score` 和 `leaderboard_result` 都存在。客户端没收到响应不影响服务端事实数据。

研发口径：

```text
resume 查询 entry completed + leaderboard_result 存在后，返回 show_current_rank 或 show_final_rank。
```

---

### Q19：多设备同时提交同一手牌，怎么保证不会重复计分？

结论：通过事务锁和 `hand_score.user_hand_id` 唯一约束兜底。

说明：
两个设备同时提交时，只有一个请求能成功写入 `hand_score`。另一个请求遇到状态已完成或唯一键冲突后，查询已有结果返回。

研发口径：

```text
同一 user_hand 只允许一条 hand_score。
```

---

### Q20：playing 状态到底表示什么？

结论：`playing` 只表示用户进入过该手，不表示能恢复到单手中途状态。

说明：
`playing` 用于区分用户是否已经进入当前手，便于恢复、统计、排查问题。但 7.15 不保存单手牌中途状态，所以不能恢复到某个具体行动点。

研发口径：

```text
user_hand.status = playing 且无 hand_score 时，下次从当前手开头重新打。
```

---

### Q21：为什么 resume 接口原则上只读？

结论：避免用户刷新或反复进入页面时意外改变服务端状态。

说明：
resume 调用频率可能很高，如果它承担写操作，容易造成状态误推进。写操作应由 join、start hand、submit hand 分别承担。

研发口径：

```text
resume 只返回 nextAction。
状态推进由 join、start hand、submit hand 完成。
```

---

### Q22：用户未完成但活动已截止时，resume 是否更新 entry 为 expired？

结论：不建议由 resume 更新；resume 返回 `activity_expired`，批量更新由 Worker 最终结算处理。

说明：
resume 是只读接口，保持职责清晰。未完成用户过期状态由最终结算统一处理，可以避免零散写入导致状态口径不一致。

研发口径：

```text
resume 遇到截止未完成返回 activity_expired。
Worker 结算阶段将未完成用户更新为 expired。
```

---

### Q23：为什么不做复杂多设备会话锁？

结论：因为 7.15 当前目标是保证最终数据正确，不是限制设备操作。

说明：
多设备会话锁需要设备身份、抢占规则、踢出机制、锁续期等逻辑，会明显增加复杂度。7.15 只需要保证同一手不重复计分、同一活动不重复入榜。

研发口径：

```text
允许多设备打开。
通过事务和唯一约束保证最终结果正确。
```

---

### Q24：截止前进入手牌，截止后提交，为什么不计分？

结论：因为 7.15 采用严格截止口径，以服务端提交计分事务时间为准。

说明：
如果允许截止后提交，会引入宽限期、已开始手牌判定、最终结算延迟等新规则。7.15 第一版先保持简单清晰。

研发口径：

```text
now >= activity.end_time 时，不生成 hand_score，不推进进度，不入榜。
```

---

## 6. 活动截止与最终结算类

### Q25：为什么以服务端提交计分事务时间判断是否截止？

结论：因为客户端时间不可信，服务端事务时间是统一口径。

说明：
客户端时间可能不准或被篡改。使用服务端事务时间可以保证所有用户按同一标准判断是否截止。

研发口径：

```text
提交计分时，服务端判断 now < activity.end_time 才允许计分。
```

---

### Q26：截止前进入手牌，截止后提交，为什么不计分？

结论：同 Q24，严格截止口径下，提交时间超过截止时间就不计分。

研发口径：

```text
进入时间不作为计分依据。
提交计分事务时间才是截止判断依据。
```

---

### Q27：为什么 activity.status = finalized 要最后更新？

结论：因为 `finalized` 是最终榜已生成的信号，必须等榜单数据完整后再更新。

说明：
如果提前把 activity 更新为 finalized，但 rank_no、is_final、finalized_at 还没写完，前端可能认为最终榜已完成，实际榜单却不完整。

研发口径：

```text
先写最终榜数据，再更新 activity.status = finalized。
```

---

### Q28：Worker 重复执行最终结算，怎么处理？

结论：Redis 锁减少重复执行，MySQL 状态最终兜底。

说明：
多个 Worker 可能同时扫描到同一个活动。先用 Redis lock 降低并发，再在 MySQL 事务中锁定 activity 并判断是否 finalized。

研发口径：

```text
获取 Redis 锁 -> select activity for update -> 判断 finalized -> 执行结算。
```

---

### Q29：活动状态枚举是否需要 ended？

结论：不一定需要，取决于是否要显式表达“已截止但未结算”。

说明：
如果不设计 ended，可以用 `end_time <= now AND status = published` 表示可结算活动。如果设计 ended，可以让状态更清晰，但会多一个状态流转。

研发口径：

```text
是否增加 ended 需要评审确认。
Worker 扫描条件以最终状态枚举为准。
```

---

### Q30：Worker 扫描活动时，status 条件应该怎么写？

结论：应扫描“可结算状态”，不要用 `status != finalized` 这种宽泛条件。

说明：
`status != finalized` 可能把 draft、disabled、cancelled 等不应结算的活动扫进去，风险较大。

研发口径：

```sql
WHERE end_time <= NOW()
  AND status IN (<可结算状态>)
```

---

### Q31：为什么用户访问时懒触发结算不适合作为主方案？

结论：因为如果没有用户访问，活动就不会及时结算。

说明：
最终榜结算是活动生命周期的一部分，不应依赖用户是否访问页面。懒触发可以作为补充，但不适合作为主流程。

研发口径：

```text
Worker 定时扫描为主。
用户访问懒触发最多作为补偿。
```

---

### Q32：后台手动触发结算是否必须做？

结论：建议保留，但可作为补偿入口，不一定是 7.15 主流程强依赖。

说明：
手动触发适用于测试环境、Worker 异常、数据修复后重新触发等场景，有利于线上运维和问题处理。

研发口径：

```text
定时 Worker 是主方案，后台手动结算是补偿方案。
```

## 7. 表结构与数据模型类

### Q33：为什么 7.15 使用 8 张核心表就够？

结论：8 张表已经覆盖活动配置、牌局包、用户参赛、手牌分配、计分、排行榜和结算状态。

说明：
7.15 不做动作日志、牌局快照、排名历史快照、复杂计分规则版本，所以不需要额外表。

研发口径：

```text
8 张表支撑 7.15 主闭环。
复杂回放、快照、规则版本后续再扩展。
```

---

### Q34：为什么 activity 只绑定 hand_pack_id，不直接绑定 hand_id 或 drill_id？

结论：活动绑定的是牌局包，牌局包再关联多手牌，手牌再关联 drill_id。

说明：
这样可以支持一个活动配置一组候选手牌，一个手牌被多个牌局包复用，一个牌局包被多个活动复用，结构更灵活。

研发口径：

```text
activity -> hand_pack -> hand_pack_item -> hand -> drill_id
```

---

### Q35：为什么 play_hand_count 必须放在 activity，并在 user_entry 保存快照？

结论：activity 是配置源，user_entry 是用户参赛时的执行快照。

说明：
如果后台修改活动配置，已参赛用户的挑战手数不应该被影响。保存快照可以保证用户参赛后流程稳定。

研发口径：

```text
activity.play_hand_count 是配置。
entry.play_hand_count 是用户参赛时快照。
```

---

### Q36：为什么 user_hand 要保存 hand_pack_id、hand_id、order_no、hand_source？

结论：为了记录用户本次实际分配结果，并支持恢复、计分和问题排查。

说明：
`hand_id` 表示打哪手，`order_no` 表示第几手，`hand_source` 表示必选或随机，`hand_pack_id` 表示来源牌包。用户参赛后，以 user_hand 作为实际分配事实。

研发口径：

```text
用户实际打哪些手，以 duplicate_match_user_hand 为准。
```

---

### Q37：为什么 user_entry.status 不增加 finalized？

结论：因为用户参赛状态和活动结算状态不是一回事。

说明：
`user_entry.status` 表达用户个人参赛进度，如 joined、playing、completed、expired。最终榜是否冻结是活动和榜单结果的状态，应由 `activity.status` 和 `leaderboard_result.is_final` 表达。

研发口径：

```text
entry.status = completed 只表示用户完成活动。
activity.status = finalized 才表示最终榜已结算。
```

---

### Q38：为什么 leaderboard_result 同时承载当前榜和最终榜？

结论：因为当前榜和最终榜本质是同一批完赛用户的结果，只是状态不同。

说明：
活动进行中 `is_final = 0`，用于当前榜。活动结算后同一批记录更新为 `is_final = 1`，写入 `rank_no` 和 `finalized_at`，用于最终榜。

研发口径：

```text
同一张 leaderboard_result 表表达两个阶段。
```

### Q39：为什么当前榜和最终榜不是两张表？

结论：7.15 第一版没有保留历史当前榜快照的需求，一张表更简单。

说明：
两张表会带来数据复制和同步问题。当前设计中，最终榜就是对已完赛结果的冻结，不需要复制一份新数据。

研发口径：

```text
7.15 不复制最终榜数据。
如果后续要保留历史快照，再新增表。
```

### Q40：为什么 7.15 不新增结算记录表？

结论：7.15 当前用 activity.status 和 leaderboard_result 字段可以完成结算闭环。

说明：
结算记录表主要用于记录每次结算任务、重算历史、失败原因等。7.15 第一版可以先不做，减少复杂度。

研发口径：

```text
结算记录表作为后续运维增强，不进入 7.15 主流程。
```

## 8. 用户参赛与手牌分配类

### Q41：重复 join 为什么返回已有结果，而不是报错？

结论：重复 join 是正常幂等场景，不应该让用户感知为错误。

说明：
用户可能重复点击、网络重试、多设备同时进入。返回已有 entry 和 user_hand 能保持体验稳定。

研发口径：

```text
重复 join 不重新分配，返回已有参赛结果。
```

---

### Q42：为什么用户参赛后手牌不能重新分配？

结论：为了保证排名赛公平性和恢复稳定性。

说明：
如果每次进入都重新分配手牌，用户挑战内容会变化，计分结果不可比较，也无法稳定恢复。

研发口径：

```text
join 成功后 user_hand 固定。
后续只读取，不重新生成。
```

---

### Q43：必选手和随机候选手如何保证数量合法？

结论：join 前或活动发布前必须校验配置合法。

说明：
必选手数量不能超过 play_hand_count，可用手牌总数必须大于等于 play_hand_count，否则无法生成 N 手牌。

研发口径：

```text
fixed_count <= play_hand_count
available_hand_count >= play_hand_count
```

---

### Q44：为什么 start hand 要把 not_started 改成 playing？

结论：为了记录用户进入过该手，便于恢复和状态判断。

说明：
如果用户进入后退出，下一次 resume 可以知道这手已经开始过，但未完成。由于 7.15 不保存中途状态，仍然从该手开头重新打。

研发口径：

```text
not_started -> playing 表示进入过该手。
playing 不表示中途恢复。
```

---

### Q45：如果牌局包可用手牌数量不足 play_hand_count，join 应该怎么处理？

结论：拒绝 join，并返回活动配置异常。

说明：
如果手牌数量不足，无法保证用户分配到 N 手牌。此时继续创建 entry 会留下不完整数据。

研发口径：

```text
配置不满足时，join 事务不创建 entry、不写 user_hand。
```

---

### Q46：如果后台活动配置后又修改 play_hand_count，已参赛用户是否受影响？

结论：不应影响已参赛用户。

说明：
用户参加活动时，`play_hand_count` 应保存到 user_entry 作为快照。已参赛用户继续按快照完成挑战。

研发口径：

```text
已参赛用户以 entry.play_hand_count 为准。
未参赛用户以最新 activity.play_hand_count 为准。
```

重复点击、网络重试、多设备并发都可能导致重复 submit。唯一约束是最终兜底。

```sql
UNIQUE KEY uk_user_hand(user_hand_id)
```

### Q48：为什么重复 submit 返回已有计分结果，而不是失败？

说明：
第一次提交可能已成功但响应丢失。返回已有结果可以让前端继续流程。

```text
查到已有 hand_score，直接返回已有计分结果。
```

### Q49：为什么完成 N 手不能只看 completed_hand_count？

结论：因为进度字段不能替代计分记录完整性校验。

完成 N 手还必须有 N 条 hand_score，否则 total_score 不可信。

研发口径：

```text
completed_hand_count 和 hand_score_count 双重校验。
```

### Q50：为什么最后一手计分、entry 完成、leaderboard_result 写入必须同事务？

结论：这是保证完赛和入榜一致性的核心事务边界。

说明：
如果拆开提交，会出现计分成功但没入榜、入榜成功但计分不完整等问题。

研发口径：

```text
submit hand 触发结算，分数由服务端生成。
```

### Q52：前端提交的数据中，哪些可以信任，哪些不能信任？

结论：用户身份、活动状态、手牌归属、分数都不能只信前端。

说明：
服务端必须校验当前登录用户、user_hand 归属、entry 归属、activity 状态、是否截止。分数必须由服务端生成。

研发口径：

```text
前端参数只作为请求输入。
业务事实全部由服务端查询和计算。
```

### Q53：如果并发 submit 发生唯一键冲突，接口应该返回什么？

说明：
唯一键冲突说明另一个请求已经成功写入。此时不应直接报错给用户，应返回已有结果。

研发口径：

```text
唯一键冲突 -> rollback -> select existing hand_score -> return existing result。
```

## 11. Redis 缓存与 version 类

### Q60：当前榜缓存什么时候生成？

结论：用户查询当前榜时生成。

说明：
缓存不是入榜时提前生成，而是查询时 Redis miss 后查 MySQL 再写缓存。

研发口径：

```text
query current leaderboard -> Redis miss -> MySQL -> write Redis。
```

---

### Q61：为什么最后一手完成后要失效当前榜缓存？

结论：因为新用户入榜后当前榜可能变化。

说明：
如果不失效缓存，用户可能继续看到旧榜单。

研发口径：

```text
MySQL 事务提交成功后，递增 current leaderboard version。
```

---

### Q62：当前榜缓存为什么用 version 方式失效？

结论：避免使用 KEYS 批量删除大量分页缓存。

说明：
分页缓存可能有很多 key。version 增加后，新查询会使用新 key，旧 key 等 TTL 自动过期。

研发口径：

```text
current:{activityId}:v:{version}:page:{page}:size:{pageSize}
```

---

### Q63：version 是什么？保存在哪里？

结论：version 是当前榜缓存版本号，建议保存在 Redis。

说明：
version 不参与排名计算，只用于区分新旧缓存。

研发口径：

```text
Redis 保存 current leaderboard version。
MySQL 仍是排行榜事实源。
```

---

### Q64：当前榜分页缓存是所有用户共用，还是每个用户一份？

结论：当前榜列表缓存是所有用户共用。

说明：
当前榜列表与用户身份无关，只与活动、页码、页大小和 version 有关。用户维度的是“我的结果”或“我的排名”。

研发口径：

```text
榜单列表缓存按 activity + version + page + pageSize。
```

---

### Q65：最终榜分页缓存什么时候生成？

结论：用户第一次查询最终榜时生成。

说明：
最终结算只负责冻结排名，不负责预热所有分页缓存。

研发口径：

```text
final leaderboard Redis miss 后查 MySQL 并写缓存。
```

---

### Q66：为什么最终榜缓存正常情况下不需要 version？

结论：因为最终榜冻结后正常不变化。

说明：
最终榜的 `rank_no` 已落库，正常查询结果稳定，不需要像当前榜一样频繁失效。

研发口径：

```text
最终榜缓存默认无 version。
```

---

### Q67：后台人工重算或数据修复后，最终榜缓存如何处理？

结论：需要显式删除对应活动的最终榜缓存。

说明：
最终榜默认不变，一旦人为修复或重算，就必须清理旧缓存，避免继续展示旧结果。

研发口径：

```text
重算 / 修复最终榜后，删除 final leaderboard cache。
```

---

### Q68：Redis 删除或 version 递增失败怎么办？

结论：不回滚 MySQL，记录日志并依赖 TTL 或后续重试修复。

说明：
MySQL 已经保存事实数据，Redis 失败只影响缓存新鲜度，不应破坏主流程。

研发口径：

```text
Redis 失败不影响 MySQL 事务结果。
```

---

### Q69：为什么不使用 KEYS 批量删除当前榜缓存？

结论：KEYS 可能阻塞 Redis，线上风险较高。

说明：
分页缓存 key 多时，KEYS 会扫描全库。version 方式更安全。

研发口径：

```text
不用 KEYS 清分页缓存，用 version 失效。
```

---

### Q70：Redis 缓存 TTL 应该怎么设置？

结论：当前榜 TTL 应较短，最终榜 TTL 可较长，具体数值按访问量和实时性要求确认。

研发口径：

```text
当前榜短 TTL。
最终榜长 TTL。
旧 version 缓存靠 TTL 自动释放。
```

## 12. 我的排名与分页性能类

### Q71：我的榜单结果和我的当前排名有什么区别？

结论：我的榜单结果是是否入榜和成绩；我的当前排名是当前榜阶段实时第几名。

说明：
我的榜单结果可以直接通过 activity_id + user_id 查。当前榜不落库 rank_no，所以我的当前排名需要实时计算。

研发口径：

```text
我的结果必做。
我的当前排名按需计算。
```

---

### Q72：为什么我的当前排名可能有性能问题？

结论：因为需要计算有多少人排在我前面。

说明：
当前榜阶段 rank_no 不落库，实时排名通常需要 COUNT 排名前面的用户。单活动用户量大时会有压力。

研发口径：

```text
默认不在列表接口中自动计算我的当前排名。
```

---

### Q73：最终榜我的排名为什么性能更好？

结论：因为最终榜 `rank_no` 已落库。

研发口径：

```text
最终榜阶段按 activity_id + user_id 查询 leaderboard_result，直接读取 rank_no。
```

### Q74：什么是深分页？为什么当前榜深分页有风险？

结论：深分页是 OFFSET 很大的分页查询，MySQL 需要跳过大量数据。

说明：
当前榜如果访问很深页码，查询成本会增加。

研发口径：

```text
7.15 限制 pageSize，深分页记录为性能风险。
```

### Q75：什么是游标分页？后期什么情况下考虑？

结论：游标分页用上一页最后一条数据作为下一页起点，适合大数据量场景。

研发口径：

```text
当 OFFSET 深分页成为瓶颈时，再考虑游标分页。
```

---

### Q76：Redis Sorted Set 是什么？为什么 7.15 第一版不直接用？

结论：Sorted Set 适合实时排行榜，但 7.15 第一版不优先使用。

说明：
当前排序需要 total_score DESC + complete_time ASC，需要复合排序编码。为了避免一致性复杂度，第一版以 MySQL 为事实源。

研发口径：

```text
Sorted Set 是后续性能优化选项，不是 7.15 主方案。
```

---

### Q77：当前榜是否需要限制最大 pageSize？

结论：建议限制。

说明：
限制 pageSize 可以避免单次查询和缓存对象过大。

研发口径：

```text
设置服务端最大 pageSize。
```

---

### Q78：当前榜是否需要限制最大页码？

结论：建议作为评审确认项。

说明：
如果活动规模较小，可以暂不强限制最大页码；如果预期用户量大，应限制或后续上游标分页。

研发口径：

```text
7.15 先限制 pageSize，最大页码按预期活动规模确认。
```

## 13. 截止结算与 Worker 类

### Q79：活动截止后，结算任务靠什么触发？

结论：靠定时 Worker 扫描触发。

研发口径：

```text
Worker 扫描 end_time <= now 且 status 属于可结算状态的活动。
```

### Q80：为什么无状态 Web 后端需要 Worker？

结论：因为 Web 请求处理和定时结算职责不同。

说明：
Web 服务处理用户请求，不适合依赖某台机器内存记住活动截止时间。Worker 可以周期性扫描，保证活动没人访问也能结算。

研发口径：

```text
Web API 处理请求，Worker 处理定时结算。
```

---

### Q81：用户访问时懒触发结算可以吗？

结论：可以作为补充，不建议作为主方案。

研发口径：

```text
没人访问时，懒触发不会发生。
Worker 才是主结算机制。
```

---

### Q82：后台手动触发结算有什么用？

结论：用于测试、补偿、异常修复和运维。

研发口径：

```text
后台手动结算是补偿入口，不替代 Worker。
```

---

### Q83：为什么 activity.status = finalized 必须最后更新？

结论：同 Q27，finalized 是最终榜完成信号，必须最后写。

研发口径：

```text
先写 rank_no / is_final / finalized_at，再更新 activity.status。
```

---

### Q84：结算阶段为什么还要兜底补齐 leaderboard_result？

结论：用于处理极端异常数据，不是主流程。

研发口径：

```text
最后一手入榜是主流程。
Worker 补齐只是异常补偿。
```

---

### Q85：为什么结算任务要先把未完成用户更新为 expired？

结论：为了明确截止后未完成用户不能再继续活动。

说明：
这样用户状态和榜单边界清晰，最终榜只处理 completed 用户。

研发口径：

```text
截止后未完成 entry 更新为 expired，不进榜。
```

---

### Q86：Redis 为什么能防止多个服务同时结算同一个活动？

结论：通过 activity_id 维度的分布式锁减少并发执行。

研发口径：

```text
一个 activity_id 一把 finalize lock。
```

---

### Q87：Redis 结算锁里的 token 是什么？

结论：token 是锁持有者标识。

说明：
释放锁时用 token 判断当前任务是否仍然持有这把锁，避免误删别人的锁。

研发口径：

```text
lock value = token。
释放锁时校验 token。
```

---

### Q88：为什么释放 Redis 锁时要校验 token？

结论：避免旧任务误删新任务持有的锁。

说明：
如果旧任务执行时间过长，锁过期后新任务获得锁，旧任务结束时直接 DEL 会删掉新任务的锁。

研发口径：

```text
使用 Lua 脚本原子判断 token 后删除。
```

---

### Q89：Redis 锁已经有了，为什么 MySQL 还要兜底？

结论：同 Q14，Redis 锁不是最终正确性保证。

研发口径：

```text
Redis 锁减少并发。
MySQL finalized 状态保证最终正确性。
```

---

### Q90：Redis 锁 TTL 应该如何设置？

结论：应大于正常结算耗时，并保留安全边界。

说明：
TTL 太短容易任务未完成锁已过期；TTL 太长会导致异常任务长时间占锁。

研发口径：

```text
按最大预估结算时间设置 TTL，并记录超时告警。
```

---

### Q91：如果 Worker 执行时间超过 Redis 锁 TTL，怎么处理？

结论：MySQL 事务和 finalized 状态兜底，避免重复结算破坏结果。

说明：
即使 Redis 锁过期，另一个 Worker 进入，也会在 MySQL 层判断 activity 是否已经 finalized 或被锁定。

研发口径：

```text
Redis TTL 超时不能破坏最终榜，MySQL 兜底。
```

## 14. 异常场景类

### Q92：重复 join 为什么不能重新分配 user_hand？

结论：重新分配会破坏排名赛公平性和恢复稳定性。

研发口径：

```text
重复 join 只返回已有 user_hand。
```

---

### Q93：重复 start hand 为什么可以直接返回 drillId？

结论：因为 start hand 是幂等进入动作，不应该重复改变事实结果。

研发口径：

```text
playing 状态再次 start，直接返回当前手 drillId。
```

---

### Q94：重复 submit 为什么返回已有 hand_score？

结论：保证网络重试和响应丢失场景下体验稳定。

研发口径：

```text
已有 hand_score 就返回已有结果。
```

---

### Q95：最后一手响应丢失，为什么 resume 能恢复到排行榜？

结论：因为服务端事务已提交，MySQL 中已有 completed entry 和 leaderboard_result。

研发口径：

```text
resume 根据 MySQL 判断完赛状态，不依赖客户端响应。
```

---

### Q96：最后一手事务失败时，为什么要整体回滚？

结论：避免留下半完成数据。

研发口径：

```text
最后一手计分、entry completed、leaderboard_result 同事务成功或同事务失败。
```

---

### Q97：为什么最终结算阶段还需要补齐 leaderboard_result？

结论：作为异常补偿，处理极端数据不一致。

研发口径：

```text
补齐前必须校验 completed、hand_score_count、complete_time。
```

---

### Q98：Redis 缓存失效失败为什么不回滚 MySQL？

结论：Redis 不是事实源，不能因为缓存失败回滚比赛结果。

研发口径：

```text
MySQL 成功即事实成功。
Redis 失败记录日志，依赖 TTL 或重试修复。
```

---

### Q99：为什么 Redis 当前榜缓存需要 TTL？

结论：旧 version 缓存不再命中，但仍占空间，需要自动释放。

研发口径：

```text
所有分页缓存设置 TTL。
```

---

### Q100：如果 data_inconsistent 出现，是否需要后台告警？

结论：建议告警。

说明：
data_inconsistent 表示核心状态不一致，应该进入日志和监控，方便及时修复。

研发口径：

```text
data_inconsistent 记录错误日志，并建议接入告警。
```

## 15. 7.15 不做范围类

### Q101：为什么不恢复 flop / turn / river 中途状态？

结论：因为当前不保存中途牌局状态。

研发口径：

```text
未完成手牌下次从当前手开头重新打。
```

---

### Q102：为什么不保存动作级日志？

结论：动作日志服务于回放、审计、争议复核，超出 7.15 主目标。

研发口径：

```text
7.15 不做完整回放和动作审计。
```

---

### Q103：为什么不做复杂多设备会话锁？

结论：因为唯一约束和事务已经能保证最终数据正确。

研发口径：

```text
不限制设备，只限制数据只能成功一次。
```

---

### Q104：为什么不做截止宽限期？

结论：宽限期会引入复杂时间口径，影响结算边界。

研发口径：

```text
7.15 严格按服务端提交计分事务时间判断。
```

---

### Q105：为什么不使用 Redis Sorted Set 作为主排行榜？

结论：7.15 优先保证正确性，Sorted Set 作为后续性能优化。

研发口径：

```text
MySQL 是排行榜事实源。
Sorted Set 后续按规模评估。
```

---

### Q106：为什么不做排名快照表？

结论：当前榜动态查询，最终榜冻结即可满足 7.15。

研发口径：

```text
需要历史排名变化时，再新增快照表。
```

---

### Q107：为什么不保留历史当前榜快照？

结论：当前无运营复盘排名变化的明确需求。

研发口径：

```text
7.15 只保留当前榜查询和最终榜冻结结果。
```

---

### Q108：为什么最终榜不做缓存预热？

结论：避免增加结算流程复杂度。

研发口径：

```text
最终榜缓存查询时生成。
```

---

### Q109：为什么 7.15 不做复杂异步消息队列？

结论：当前核心流程用 MySQL 事务更直接、更容易保证一致性。

研发口径：

```text
submit hand 主流程同步完成计分和入榜。
Worker 只负责最终结算。
```

---

### Q110：为什么 7.15 不做复杂计分规则版本？

结论：当前只有一套计分口径，先不引入规则版本复杂度。

研发口径：

```text
后续多套计分规则再扩展规则版本。
```

## 16. 研发实现顺序类

### Q111：为什么要先做表结构和约束，再做接口？

结论：核心正确性依赖表结构和唯一约束。

研发口径：

```text
先建表和约束，再实现 join / submit / leaderboard。
```

---

### Q112：为什么 join 和 user_hand 分配要先于 submit hand？

结论：submit hand 必须依赖已经分配好的 user_hand。

研发口径：

```text
没有 user_hand，就无法确定当前手、顺序和计分对象。
```

---

### Q113：为什么 resume / start hand 要在 submit hand 前后一起设计？

结论：三者共同构成活动进度闭环。

说明：
resume 判断下一步，start hand 标记进入当前手，submit hand 完成当前手并推进进度。

研发口径：

```text
resume、start hand、submit hand 要按同一状态机设计。
```

---

### Q114：为什么 Redis 缓存放在核心流程之后实现？

结论：Redis 是性能优化，不是正确性基础。

研发口径：

```text
先跑通 MySQL 正确性，再接入 Redis 缓存。
```

---

### Q115：为什么 Worker 结算要在最后一手入榜之后实现？

结论：最后一手入榜是正常主流程，Worker 是最终冻结和异常补偿。

研发口径：

```text
先保证用户完成 N 手即可入 leaderboard_result。
再做最终榜 Worker 冻结。
```

## 18. 总结

7.15 的核心设计原则可以归纳为：

```text
1. MySQL 是唯一事实源。
2. Redis 只做缓存和结算锁。
3. 用户参赛后生成固定 N 手牌。
4. 每手计分由服务端生成。
5. 同一 user_hand 只能计分一次。
6. 最后一手计分、entry 完成、leaderboard_result 写入必须同事务。
7. 当前榜动态查询，不落库 rank_no。
8. 最终榜截止后冻结 rank_no。
9. 断线恢复只恢复活动进度，不恢复单手中途状态。
10. 7.15 不做复杂回放、快照、宽限期、Sorted Set 主榜和复杂异步链路。
```

这套方案的重点不是把所有未来能力一次性做完，而是在 7.15 范围内把 PvE 排名赛的核心闭环、数据一致性、排行榜正确性和恢复边界做稳定。
