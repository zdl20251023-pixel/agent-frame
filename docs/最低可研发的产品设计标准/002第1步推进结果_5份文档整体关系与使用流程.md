# 5 份文档整体关系与使用流程（轻量版）

## 1. 这套文档要解决什么问题

这套文档不是为了增加流程，也不是为了把 PRD 写得很复杂。

核心目标是：

> 让产品设计在进入研发评估、宣讲和开工前，把主流程、大章节、涉及范围、关键规则、验收标准和待确认项讲清楚，减少研发阶段因为信息缺失导致的返工。

第一版重点控制在轻量可用，不追求细节一次性完整。

简单来说：

1. 前两份文档用于事前预防，确保 PRD 支持研发评估；
2. 后三份文档只在评审被打回、发现关键问题或高频问题时使用；
3. 第一版不追求细节完整，只抓主流程、范围、关键规则、验收标准和待确认项。

---

## 2. 基本原则

### 2.1 第一版只抓研发评估和开工底线

PRD 不要求大而全，也不要求产品一开始把所有细节和异常分支都写完整。

第一版重点判断一件事：

> 这份 PRD 是否已经支持研发评估，并在必要待确认项明确后支持开工。

这里的“可开工”不是指所有细节一次性完备，而是指 PRD 已经足够研发判断改动范围、识别主要风险，并能明确开工前必须确认的问题。

这里的“必要待确认项”，是指会影响主流程、关键规则、验收标准或数据状态的问题。

基础底线包括：

1. 主流程讲清楚；
2. 涉及范围讲清楚；
3. 关键规则和验收标准讲清楚；
4. 影响研发实现或验收的复杂规则，要有清晰例子；
5. 不明确的内容，要标为待确认项。

---

### 2.2 先明确适用范围

这套文档第一版不要求所有需求都完整套用。

**普通小改动、小配置**，不强制套完整流程，只需要说明改动点和验收结果。

**中等及以上需求**，默认使用“开发可开工最低标准”和“宣讲前 Checklist”。

中等及以上需求指：

* 涉及新页面；
* 涉及新流程；
* 涉及多角色；
* 涉及多端；
* 涉及多模块；
* 涉及配置规则；
* 涉及已有流程或已有数据影响；
* 需要研发评估改动范围或技术风险。

**复杂需求**是中等及以上需求里的子集，不是所有中等需求都要补充复杂信息。

复杂需求一般指：

* 规则容易理解偏；
* 涉及多模块协作；
* 涉及核心业务对象和状态；
* 涉及多个系统之间的数据流转；
* 规则会明显影响研发实现或验收结果。

---

### 2.3 大章节必须覆盖完整

细节可以后补，但功能涉及的大范围不能漏。

一个功能点需要说明是否涉及：

* 用户端；
* 管理后台；
* 配置表；
* 服务端接口 / 后台逻辑；
* 其他系统；
* 已有流程；
* 已有数据。

这里不要求产品写完整技术方案、数据迁移方案或接口设计，只要求先说明是否涉及，让研发能够判断改动范围和大致工作量。

---

### 2.4 复杂需求按需补充细节

普通需求不强制展开复杂说明。

如果需求涉及复杂规则、多模块协作或核心业务对象状态，再补充复杂需求信息。

复杂需求补充项包括：

1. 复杂或关键业务规则的典型例子；
2. 多模块之间的关键输入和输出；
3. 核心对象、关键状态，以及不同状态下的页面 / 数据表现。

这些内容不要求写成技术方案，只要能帮助研发理解规则、判断改动范围和避免实现偏差。

普通简单规则不强制写例子，只有容易理解偏、影响研发实现或验收的规则才需要补例子。

复杂需求补充项按需使用，不要求三项全部填写。

---

### 2.5 异常分支允许不完全覆盖，但要有补齐机制

产品只需要先覆盖主要异常和已知异常。

不影响主流程、关键规则和验收标准的异常，可以在开发执行过程中补齐，并和产品确认最终效果。

如果异常会影响核心结果、数据状态、主流程或验收标准，评审前需要说明清楚。

---

### 2.6 不能让研发靠猜

暂时没明确的异常分支、边界规则、特殊配置、复杂业务规则、输入输出或影响范围，需要标为待确认项。

待确认项需要说明负责人和确认节点，例如评审后补齐、开发前确认、联调前确认或验收前确认。

影响主流程、关键规则、验收标准或数据状态的待确认项，需要开发前确认；不影响核心结果的，可以在开发过程中补充确认。

如果主流程、涉及范围、关键规则或验收标准缺失，研发可以先反馈具体缺口，暂不按猜测评估或开工。

---

## 3. 5 份文档的关系

这 5 份文档不是新增审批流，而是一套轻量工具，用来把 PRD 问题尽量前置，并把重复问题沉淀回 Checklist。

整体分成两部分：

```text
事前预防：
1. 开发可开工的产品设计最低标准模板
        ↓
2. 产品设计文档进入宣讲前的 Checklist
        ↓
产品 / 研发宣讲或评审

事后修正：
3. 产品评审后的复盘模板
        ↓
4. 评审问题归因分析模板
        ↓
5. 复盘结果反哺 Checklist 的更新流程
```

### 3.1 事前预防：尽量减少 PRD 被打回

| 文档                     | 作用                                     | 使用方式      |
| ---------------------- | -------------------------------------- | --------- |
| 开发可开工的产品设计最低标准模板       | 定义 PRD 至少写到什么程度，研发才能开始评估，并识别开工前必须确认的问题 | 中等及以上需求使用 |
| 产品设计文档进入宣讲前的 Checklist | 宣讲前检查主流程、大章节、涉及范围、关键规则、验收标准和待确认项是否清楚   | 宣讲前自检使用   |

这两份文档是第一版的重点，目的是把问题尽量挡在正式评审前。

### 3.2 事后修正：只在出现问题时使用

| 文档                     | 作用                                     | 使用方式                  |
| ---------------------- | -------------------------------------- | --------------------- |
| 产品评审后的复盘模板             | 记录评审中卡住的问题、影响和后续修改动作                   | 评审被打回或发现关键问题时使用       |
| 评审问题归因分析模板             | 简单判断问题属于目标、范围、流程、规则、验收、异常、研发风险等哪一类     | 不做复杂分析，只做问题分类         |
| 复盘结果反哺 Checklist 的更新流程 | 把重复出现、影响研发开工、导致 PRD 被打回的问题补回 Checklist | 只更新高频或关键问题，不把每个细节都加进去 |

后三份不是每个需求都必须走，只有评审出现明显问题、被打回，或者发现高频问题时才使用。

### 3.3 使用边界

* 普通小改动、小配置、小需求，不强制套完整流程；
* 中等及以上需求，优先使用前两份；
* 评审通过后，不需要额外做问题记录和问题分类；
* 评审被打回或出现关键问题时，再使用后三份；
* Checklist 只沉淀重复出现、影响研发开工、导致打回的问题，避免越更新越重。

---

## 4. 使用流程

以下是完整使用方式说明，不代表每个需求都必须走完六步。

普通需求重点使用前两步；后三步只在评审被打回、发现关键问题或问题反复出现时使用。

---

### 第一步：产品先按“开发可开工最低标准”准备 PRD

产品在准备 PRD 时，不需要把所有细节都写满，也不要求一次性覆盖所有异常分支。

中等及以上需求先满足基础必填；其中涉及复杂规则、多模块协作或核心业务对象状态的，再按需补充复杂需求信息。

#### 基础必填

| 内容   | 要求                                                         |
| ---- | ---------------------------------------------------------- |
| 需求目标 | 为什么做，解决什么问题                                                |
| 主流程  | 功能大致怎么走                                                    |
| 涉及范围 | 是否涉及用户端、管理后台、配置表、服务端接口、其他系统、已有流程或已有数据；如涉及，只说明影响范围，不要求写技术方案 |
| 关键规则 | 影响研发实现和验收的核心业务规则                                           |
| 验收标准 | 什么情况算完成                                                    |
| 主要异常 | 已知异常、主要异常先写清                                               |
| 待确认点 | 还没完全明确、需要产品或研发确认的点，并说明负责人和确认节点                             |

#### 复杂需求补充

| 补充内容    | 适用场景                   |
| ------- | ---------------------- |
| 复杂规则例子  | 规则容易理解偏、影响研发实现或验收时     |
| 多模块输入输出 | 涉及多个模块、系统或数据流转时        |
| 核心对象和状态 | 涉及订单、用户、任务、配置项等核心业务对象时 |

重点不是写细，而是不能漏大块，不能让研发靠猜。

---

### 第二步：宣讲前用 Checklist 做缺口检查

产品宣讲前，先用 Checklist 检查 PRD 是否有明显缺口。

Checklist 不要求重新写一遍 PRD，只检查是否缺少影响研发评估和开工的关键内容。

| 检查项       | 说明                                  |
| --------- | ----------------------------------- |
| 目标是否清楚    | 是否说明为什么做                            |
| 主流程是否清楚   | 是否能看懂功能怎么走                          |
| 涉及范围是否清楚  | 是否说明用户端、管理后台、配置表、其他系统、已有流程或已有数据是否涉及 |
| 关键规则是否清楚  | 是否说明核心判断和业务规则                       |
| 验收标准是否清楚  | 是否知道做到什么程度算完成                       |
| 主要异常是否有说明 | 不要求全，但已知主要异常要说明                     |
| 待确认点是否标出  | 不清楚的地方要明确标出来，并说明确认节点                |

复杂需求再检查：

| 检查项         | 说明                       |
| ----------- | ------------------------ |
| 复杂规则是否有例子   | 复杂或关键规则是否至少有一个典型例子       |
| 多模块输入输出是否清楚 | 模块之间谁提供数据、谁消费数据、输出什么是否清楚 |
| 核心对象和状态是否清楚 | 对象、状态、状态下展示和操作是否清楚       |

Checklist 的作用不是卡流程，而是帮助产品在宣讲前把大问题先补齐。

Checklist 用来暴露缺口，不作为机械打回标准；是否影响研发评估或开工，由产品和研发根据影响程度判断。

---

### 第三步：进入产品 / 研发宣讲或评审

评审时主要看四类问题：

1. **产品方向和功能范围是否清楚**
   比如目标、范围、涉及模块、大章节是否清楚。

2. **研发是否能够评估改动范围，并判断开工前必须确认的问题**
   比如主流程、关键规则、验收标准、主要风险点是否足够明确。

3. **复杂规则是否容易理解偏**
   如果规则只有抽象描述，研发可能实现偏，需要补典型例子。

4. **复杂需求是否补齐必要信息**
   比如多模块输入输出、核心对象状态、不同状态下的数据表现是否清楚。

异常分支不要求产品一次性全部覆盖。

如果评审时发现异常分支缺失，只要不影响主流程、大范围判断、关键规则和验收标准，可以记录为开发执行阶段补充确认项。

---

### 第四步：出现问题时，记录关键问题

评审通过后，不需要额外做问题记录和问题分类。

只有出现下面情况时，才做轻量问题记录：

* PRD 被打回；
* 评审中发现关键问题；
* 问题影响研发评估或开工；
* 同类问题反复出现。

最小记录字段：

| 字段       | 说明                    |
| -------- | --------------------- |
| 需求名称     | 当前评审的需求               |
| 评审结论     | 通过 / 有条件通过 / 需修改 / 打回 |
| 主要问题     | 本次主要卡在哪里              |
| 问题影响     | 是否影响产品判断、研发评估或开工      |
| 修改动作     | 后续怎么补                 |
| 负责人      | 谁来补                   |
| 是否需要二次确认 | 是否需要老板、产品或研发负责人再确认    |

这里不写复杂报告，只记录事实、影响和修改动作。

---

### 第五步：有复用价值时，做简单分类

问题分类不做复杂分析，也不是追责，只是为了知道下次要在哪里提前检查。

常见分类：

| 问题类型        | 说明                        |
| ----------- | ------------------------- |
| 目标不清        | 为什么做没讲清楚                  |
| 主流程不清       | 功能怎么走没讲清楚                 |
| 大章节遗漏       | 用户端、管理后台、配置表、其他系统等涉及范围没说明 |
| 关键规则不清      | 核心业务规则、权限、边界没讲清楚          |
| 验收标准不清      | 不知道什么情况算完成                |
| 复杂规则缺少例子    | 抽象规则没有典型例子，研发无法准确理解       |
| 多模块输入输出不清   | 模块之间输入、输出、依赖关系没说明         |
| 核心对象 / 状态不清 | 对象、状态、状态下表现或操作没说明         |
| 异常分支缺失      | 主要异常或执行时需要确认的异常没标出        |
| 研发风险未暴露     | 技术依赖、改造成本、兼容风险没有提前说明      |

如果只是一次性细节问题，可以只记录，不进入 Checklist 更新。

---

### 第六步：高频或关键问题才更新 Checklist

不是每个问题都补进 Checklist。

只有某类问题重复出现，或者明显影响研发开工，才补回宣讲前 Checklist。

是否补进 Checklist，由模板维护人整理，研发负责人确认，只补高频或关键问题，避免 Checklist 越来越重。

更新规则：

| 情况                | 处理方式                |
| ----------------- | ------------------- |
| 同类问题出现多次          | 补进 Checklist        |
| 问题导致 PRD 被打回      | 补进 Checklist        |
| 问题影响研发开工          | 补进 Checklist        |
| 复杂或关键规则经常缺少例子     | 补进 Checklist        |
| 多模块输入输出、核心对象状态经常漏 | 补进 Checklist        |
| 只是一次性的细节问题        | 先记录，不一定补进 Checklist |
| 异常分支执行时补充即可       | 记录为开发确认项，不强制产品提前写全  |

更新时只补关键检查项，不把每个细节都加进去，避免 Checklist 越来越重。

## 5. 5 份文档的使用场景

| 文档                     | 谁主要使用         | 什么时候用         | 输出结果                             |
| ---------------------- | ------------- | ------------- | -------------------------------- |
| 开发可开工的产品设计最低标准模板       | 产品、研发         | PRD 准备阶段      | 判断 PRD 是否达到研发可评估标准，并识别开工前必须确认的问题 |
| 产品设计文档进入宣讲前的 Checklist | 产品            | 宣讲前           | 提前发现 PRD 明显缺口                    |
| 产品评审后的复盘模板             | 产品 / 研发       | 评审被打回或发现关键问题后 | 记录问题和修改动作                        |
| 评审问题归因分析模板             | 产品 / 研发       | 问题有复用价值时      | 判断问题类型                           |
| 复盘结果反哺 Checklist 的更新流程 | 模板维护人 / 研发负责人 | 高频问题或关键问题出现后  | 更新 Checklist，减少重复问题              |

## 6. 第一版先不做什么

第一版先不做以下内容：

1. 不做复杂审批流；
2. 不做完整流程制度；
3. 不做考核或追责；
4. 不要求产品把所有异常分支一次性写全；
5. 不要求小改动、小配置都套模板；
6. 不把问题记录和问题分类做成复杂报告；
7. 不追求 PRD 细节完全覆盖；
8. 不要求产品为所有规则都写大量例子，只要求复杂或关键规则至少有清晰例子；
9. 不要求产品写完整数据模型、技术方案或接口设计。

---

## 7. 第一版真正要做到什么

第一版真正要做到 4 件事：

1. **主流程和功能范围清楚**
   研发能看懂功能怎么走、要解决什么问题、涉及哪些模块。

2. **大章节和影响范围清楚**
   用户端、管理后台、配置表、服务端接口、其他系统、已有流程和已有数据是否涉及，需要提前说明。

3. **关键规则、验收标准和待确认项清楚**
   研发能判断怎么实现、做到什么程度算完成；不明确的地方要标出来，并说明确认节点。

4. **复杂需求按需补充必要信息**
   对复杂规则、多模块输入输出、核心对象状态，补充能支持研发理解和评估的信息。

---

## 8. 一句话总结

这 5 份文档第一版不追求大而全，只保证 PRD 的主流程、涉及范围、关键规则、验收标准和待确认项清楚；复杂需求按需补规则例子、多模块输入输出、核心对象状态；异常分支允许不完全覆盖，但开发执行时需要补齐并和产品确认最终效果。
