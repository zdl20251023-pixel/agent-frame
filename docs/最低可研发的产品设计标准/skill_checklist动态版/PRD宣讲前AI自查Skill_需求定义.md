# PRD 宣讲前 AI 自查 Skill 需求定义

## 1. 一句话定位

实现一个「PRD 宣讲前 AI 自查 Skill」。

用户输入 PRD 文档和宣讲前 Checklist。Skill 先从 Checklist 中识别检查项、确认问题和判断选项，再基于这些检查项审查 PRD，判断该 PRD 是否已经达到产品设计宣讲前的最低可交付标准。

该 Skill 的目标不是检查 PRD 是否“看起来填完整”，而是判断研发是否能够基于该 PRD 理解需求、评估工作量、拆解任务、识别风险并完成验收。

---

## 2. 需求本质

这是一个 **PRD 宣讲前质量门禁 Skill**。

它以 Checklist 为规则来源，以 PRD 为被检查对象，自动完成以下检查：

1. 结构完整性检查；
2. 研发可评估性检查；
3. 内容一致性和反证检查；
4. 宣讲阻塞项识别；
5. 修改补充建议生成。

最终输出该 PRD 是否可以进入产品设计宣讲，以及哪些问题必须在宣讲前补齐。

本质上，它是把产品宣讲前的人肉评审经验，固化成一个可复用的 PRD 质量门禁，用来减少研发会上因目标、范围、流程、规则、验收不清导致的返工。

---

## 3. 核心目标

该 Skill 需要帮助产品或需求负责人在宣讲前回答一个核心问题：

> 这个 PRD 现在能不能拿去给研发宣讲？

具体目标包括：

- 判断 PRD 是否覆盖 Checklist 中的全部检查项；
- 判断每个检查项是否真正满足研发理解和评估需要；
- 发现 PRD 中的明显缺口、歧义、矛盾和未确认风险；
- 输出是否可以宣讲的整体结论；
- 给出宣讲前必须补充的内容；
- 给出可复制进 PRD 的补充建议草案；
- 避免产品在研发会上被反复追问基础信息；
- 提升需求进入研发评估前的确定性。

---

## 4. 输入范围

### 4.1 第一版支持输入

第一版 Skill 重点支持以下输入：

1. PRD 文档文本或 Markdown；
2. 宣讲前 Checklist 文档文本或 Markdown 表格。

Checklist 中至少应包含：

- 检查项；
- 宣讲前确认问题；
- 判断选项。

PRD 可以不完全使用标准模板标题，但内容需要能够被识别到对应模块。

### 4.2 第一版暂不重点支持

第一版暂不重点处理以下复杂场景：

- 图片型 PDF；
- 扫描件；
- 多个 PRD 批量审查；
- 飞书、Notion、Confluence 等外部链接直接读取；
- 复杂格式表格或大量图片说明；
- 自动改写完整 PRD。

---

## 5. 核心检查逻辑

Skill 需要先解析 Checklist，再用 Checklist 反向检查 PRD。

### 5.1 Checklist 解析

Skill 需要从 Checklist 中识别：

- 检查项名称；
- 每个检查项对应的确认问题；
- 每个检查项允许的判断值；
- 是否存在“不涉及”“待确认”“需补充”等特殊判断选项；
- 是否存在 AI 检查这类系统性检查项。

Checklist 不应被写死在 Skill 中。后续 Checklist 如果发生变化，Skill 应优先以用户输入的 Checklist 为准。

### 5.2 PRD 审查

Skill 需要基于 Checklist 审查 PRD，并至少完成四类判断：

1. **结构完整性**  
   判断 PRD 是否包含对应章节或相关内容。

2. **内容有效性**  
   判断内容是否具体、明确、可理解，而不是只有空泛描述。

3. **研发可评估性**  
   判断研发是否能据此评估影响范围、技术方案、工作量、边界和验收方式。

4. **一致性 / 反证检查**  
   主动检查 PRD 前后是否存在矛盾、遗漏或相互冲突的信息。

---

## 6. 重点检查项

第一版默认围绕以下 PRD 宣讲前关键项进行检查。

### 6.1 需求目标

检查 PRD 是否说明：

- 目标用户或使用对象；
- 当前问题；
- 目标结果；
- 本期不包含内容。

通过标准不是“有标题”，而是研发能够理解为什么做、解决谁的问题、本期边界在哪里。

常见不通过情况：

- 只有“提升体验”“优化流程”等空泛表述；
- 没有目标用户；
- 没有明确当前问题；
- 没有说明本期不做什么；
- 目标结果无法验证。

### 6.2 主流程

检查 PRD 是否说明：

- 整体流程；
- 模块流程；
- 关键节点；
- 会影响研发实现的流程分支。

常见不通过情况：

- 只有功能点，没有流程顺序；
- 没有说明用户从哪里进入、如何完成、何时结束；
- 模块之间关系不清；
- 关键判断节点没有说明。

### 6.3 涉及范围

检查 PRD 是否说明本次需求影响哪些对象，例如：

- 用户端；
- 管理后台；
- 配置项或配置表；
- 服务端逻辑；
- 第三方系统；
- 已有数据或历史流程。

常见不通过情况：

- 只写了页面改动，没有说明服务端和数据影响；
- 说“不涉及”，但后文规则明显涉及；
- 范围表为空；
- 改动类型不清楚；
- 历史数据是否兼容没有说明。

### 6.4 关键规则

检查 PRD 是否说明：

- 业务范围；
- 功能模块；
- 具体对象；
- 主规则；
- 子规则；
- 特殊情况；
- 处理结果。

常见不通过情况：

- 只有结果，没有判断条件；
- 规则散落在多个地方，无法形成完整判断链；
- 特殊情况缺失；
- 处理结果不明确；
- 规则和流程、范围存在冲突。

### 6.5 验收标准

检查 PRD 是否说明：

- 验收范围；
- 验收场景；
- 操作或条件；
- 预期结果；
- 不通过情况。

常见不通过情况：

- 只写“功能正常”；
- 没有具体场景；
- 没有预期结果；
- 没有不通过情况；
- 验收标准和需求目标不对应。

### 6.6 待确认点

检查 PRD 中不明确的问题是否说明：

- 待确认问题；
- 影响范围；
- 当前建议或默认处理；
- 负责人；
- 确认节点。

常见不通过情况：

- 有不明确内容但没有放入待确认点；
- 只写“待确认”，没有影响范围；
- 没有负责人；
- 没有确认时间节点；
- 待确认点会影响开发启动但没有标注风险。

### 6.7 异常处理

检查 PRD 是否说明：

- 异常发生位置；
- 异常情况；
- 处理方式；
- 用户或系统表现；
- 未覆盖异常的后续确认机制。

常见不通过情况：

- 完全没有异常处理；
- 只写“报错提示”；
- 没有说明系统如何兜底；
- 没有说明用户看到什么；
- 没有说明研发发现新异常时如何确认。

### 6.8 AI 检查

Checklist 中的 AI 检查属于系统性检查项。

Skill 应根据本次检查结果判断：

- 如果已完成完整自查且无明显缺口，可标记为通过；
- 如果完成了自查但存在明显缺口，应标记为需补充；
- 如果没有完成检查，应标记为未检查。

---

## 7. 输出要求

Skill 输出不能只给“是 / 否”。输出需要服务宣讲前决策。

### 7.1 整体结论

整体结论必须从以下类型中选择：

1. **可以宣讲**  
   无明显阻塞，研发可基本理解和评估。

2. **可宣讲但需补充**  
   有缺口，但不严重阻塞宣讲，可在宣讲前补齐或宣讲中确认。

3. **暂不建议宣讲**  
   存在关键缺口，研发大概率无法有效评估。

4. **无法判断**  
   输入文档不足，无法完成有效检查。

### 7.2 分项检查表

每个检查项都需要输出：

- 检查项；
- 判断结果；
- 依据说明；
- 发现的问题；
- 风险等级；
- 补充建议。

判断结果建议使用：

- 通过；
- 需补充；
- 不通过；
- 不涉及；
- 待确认。

### 7.3 风险等级

问题风险建议分为：

- **P0 阻塞宣讲**：目标、范围、主流程、关键规则、验收标准等关键内容缺失，研发无法有效评估；
- **P1 影响评估**：异常处理、待确认点、边界说明不清，会影响技术方案或开发拆解；
- **P2 表达优化**：表达不够清晰，但不严重影响理解和评估。

### 7.4 宣讲前补充清单

Skill 需要按优先级输出宣讲前补充清单：

1. 必须补齐的 P0 项；
2. 建议补齐的 P1 项；
3. 可优化的 P2 项。

### 7.5 可复制补充建议

对于缺失或不完整内容，Skill 可以给出可复制进 PRD 的补充建议草案。

但所有补充草案必须标注：

> 以下为建议草案，需产品负责人确认后再写入 PRD。

---

## 8. 一致性和反证检查

Skill 需要主动检查 PRD 中是否存在前后不一致的问题。

重点包括：

- 需求目标和验收标准是否一致；
- 涉及范围和关键规则是否一致；
- 主流程和异常处理是否一致；
- 本期不包含内容是否和后文描述冲突；
- 范围表中写“不涉及”的对象，后文是否又出现相关逻辑；
- 待确认点是否实际影响当前开发启动；
- 验收场景是否覆盖关键规则；
- 异常处理是否覆盖主流程中的关键失败节点。

发现矛盾时，不能强行判断通过，必须标记为“需补充”或“待确认”。

---

## 9. AI 行为边界

Skill 必须遵守以下限制：

- 不替产品编造业务规则；
- 不把推测内容当成事实；
- 不擅自补充未经确认的范围、流程、规则或验收标准；
- 对缺失内容只能提出补充方向或建议草案；
- 所有影响开发的未知点必须进入待确认点；
- 不追求文档完美，只判断是否满足宣讲前最低可评估标准；
- 不替代正式研发评审，只做宣讲前自查。

---

## 10. 推荐 Skill 结构

第一版 Skill 可以采用以下结构：

```text
prd-pre-briefing-checker/
├── SKILL.md
├── references/
│   ├── review-rubric.md
│   ├── output-template.md
│   └── examples.md
└── agents/
    └── openai.yaml
```

### 10.1 SKILL.md

负责说明：

- Skill 什么时候触发；
- 输入要求；
- 检查流程；
- 输出要求；
- 风险分级；
- 禁止脑补规则；
- 最终宣讲建议判断方式。

### 10.2 review-rubric.md

负责沉淀：

- 每个检查项的通过条件；
- 不通过条件；
- 常见风险；
- 反证检查点；
- 补充建议原则。

### 10.3 output-template.md

负责沉淀固定输出格式：

- 总体结论；
- 分项检查表；
- P0 / P1 / P2 问题清单；
- 宣讲前补充清单；
- 可复制补充建议。

### 10.4 examples.md

负责提供样例：

- 一个可以宣讲的案例；
- 一个可宣讲但需补充的案例；
- 一个暂不建议宣讲的案例。

## 11. 推荐使用流程

该 Skill 的典型使用链路如下：

1. 产品写完 PRD；
2. 上传 PRD 和宣讲前 Checklist；
3. 运行 PRD 宣讲前 AI 自查 Skill；
4. Skill 输出宣讲前检查报告；
5. 产品按 P0 / P1 问题补充 PRD；
6. 再次运行 Skill；
7. 通过后进入产品设计宣讲。

该 Skill 应支持二次检查。第二次检查时，需要重点判断上一次的问题是否已经修复，以及是否还存在新的阻塞项。

---

## 12. 第一版验收标准

第一版 Skill 需要满足以下标准：

1. 能从 Checklist 中识别检查项、确认问题和判断选项；
2. 能基于 Checklist 对 PRD 逐项检查；
3. 能区分章节缺失、内容空泛、研发不可评估、前后矛盾等不同问题；
4. 能输出整体宣讲建议；
5. 能输出每个检查项的判断结果和原因；
6. 能识别 P0 / P1 / P2 风险；
7. 能给出宣讲前优先补充清单；
8. 能提供建议草案，但不会把建议草案当成事实；
9. 能处理“不涉及”“待确认”等非简单通过/失败状态；
10. 能在输入不足时明确说明无法判断，而不是强行给结论。

---

## 13. 最终目标

最终目标不是让 AI 替产品写 PRD，而是让 AI 在宣讲前帮产品完成一次高质量自查。

它要解决的是：

- 产品自己以为讲清楚了，但研发听不懂；
- PRD 看起来完整，但无法评估；
- 规则写了，但验收标准对不上；
- 范围表写了不涉及，但后文又出现相关逻辑；
- 待确认点没有负责人和确认节点；
- 异常处理缺失，研发只能靠猜。

因此，这个 Skill 的核心判断标准是：

> 研发能否基于这份 PRD 开始有效评估和讨论。

而不是：

> PRD 是否形式上填满了模板。
