# PRD 宣讲前 AI 自查 Skill 需求定义

## 1. 一句话定位

实现一个「PRD 宣讲前 AI 自查 Skill」。

用户只需输入 PRD 文档。宣讲前 Checklist 已内置集成在 Skill 中，Skill 直接使用内置 Checklist 中的检查项、确认问题和判断选项审查 PRD，判断该 PRD 是否已经达到产品设计宣讲前的最低可交付标准。

该 Skill 的目标不是检查 PRD 是否“看起来填完整”，而是判断研发是否能够基于该 PRD 理解需求、评估工作量、拆解任务、识别风险并完成验收。

---

## 2. 需求本质

这是一个 **PRD 宣讲前质量门禁 Skill**。

它以内置 Checklist 为规则来源，以 PRD 为被检查对象，自动完成以下检查：

1. 结构完整性检查；
2. 研发可评估性检查；
3. 内容一致性和反证检查；
4. 宣讲阻塞项识别；
5. 修改补充建议生成。

最终输出该 PRD 是否可以进入产品设计宣讲，以及哪些问题必须在宣讲前补齐。

本质上，它是把产品宣讲前的人肉评审经验，固化成一个可复用的 PRD 质量门禁，用来减少研发会上因目标、范围、流程、规则、验收不清导致的返工。

---

## 3. 核心目标

该 Skill 需要帮助产品或需求负责人在宣讲前回答一个核心问题：

> 这个 PRD 现在能不能拿去给研发宣讲？

具体目标包括：

- 判断 PRD 是否覆盖内置 Checklist 中的全部检查项；
- 判断每个检查项是否真正满足研发理解和评估需要；
- 发现 PRD 中的明显缺口、歧义、矛盾和未确认风险；
- 输出「通过 / 不通过」的整体结论及一句话说明；
- 给出宣讲前必须补齐的内容与可选优化建议；
- 给出可复制进 PRD 的补充建议草案；
- 避免产品在研发会上被反复追问基础信息；
- 提升需求进入研发评估前的确定性。

---

## 4. 输入范围

### 4.1 第一版支持输入

第一版 Skill 重点支持以下输入：

1. PRD 文档文本或 Markdown。

宣讲前 Checklist 不再作为用户输入，而是内置集成在 Skill 中。内置 Checklist 至少应包含：

- 检查项；
- 宣讲前确认问题；
- 判断选项。

PRD 可以不完全使用标准模板标题，但内容需要能够被识别到对应模块。

### 4.2 第一版暂不重点支持

第一版暂不重点处理以下复杂场景：

- 图片型 PDF；
- 扫描件；
- 多个 PRD 批量审查；
- 飞书、Notion、Confluence 等外部链接直接读取；
- 复杂格式表格或大量图片说明；
- 自动改写完整 PRD。

---

## 5. 核心检查逻辑

Skill 直接加载内置 Checklist，再用内置 Checklist 反向检查 PRD。

### 5.1 内置 Checklist

Skill 内置 Checklist 中已定义：

- 检查项名称；
- 每个检查项对应的确认问题；
- 每个检查项允许的判断值；
- 是否存在“不涉及”“待确认”“需补充”等特殊判断选项；
- 是否存在 AI 检查这类系统性检查项。

Checklist 作为 Skill 的规则来源被集成在 Skill 内（例如以独立的规则/参考文件形式随 Skill 一起维护），由 Skill 统一管理和升级，用户无需也无法在运行时替换。后续 Checklist 发生变化时，应通过更新 Skill 内置规则文件来调整，而不是依赖用户输入。

### 5.2 PRD 审查

Skill 需要基于内置 Checklist 审查 PRD，并至少完成四类判断：

1. **结构完整性**  
   判断 PRD 是否包含对应章节或相关内容。

2. **内容有效性**  
   判断内容是否具体、明确、可理解，而不是只有空泛描述。

3. **研发可评估性**  
   判断研发是否能据此评估影响范围、技术方案、工作量、边界和验收方式。

4. **一致性 / 反证检查**  
   主动检查 PRD 前后是否存在矛盾、遗漏或相互冲突的信息。

---

## 6. 重点检查项

第一版默认围绕以下 PRD 宣讲前关键项进行检查。

### 6.1 需求目标

检查 PRD 是否说明：

- 目标用户或使用对象；
- 当前问题；
- 目标结果；
- 本期不包含内容。

通过标准不是“有标题”，而是研发能够理解为什么做、解决谁的问题、本期边界在哪里。

常见不通过情况：

- 只有“提升体验”“优化流程”等空泛表述；
- 没有目标用户；
- 没有明确当前问题；
- 没有说明本期不做什么；
- 目标结果无法验证。

### 6.2 主流程

检查 PRD 是否说明：

- 整体流程；
- 模块流程；
- 关键节点；
- 会影响研发实现的流程分支。

常见不通过情况：

- 只有功能点，没有流程顺序；
- 没有说明用户从哪里进入、如何完成、何时结束；
- 模块之间关系不清；
- 关键判断节点没有说明。

### 6.3 涉及范围

检查 PRD 是否说明本次需求影响哪些对象，例如：

- 用户端；
- 管理后台；
- 配置项或配置表；
- 服务端逻辑；
- 第三方系统；
- 已有数据或历史流程。

常见不通过情况：

- 只写了页面改动，没有说明服务端和数据影响；
- 说“不涉及”，但后文规则明显涉及；
- 范围表为空；
- 改动类型不清楚；
- 历史数据是否兼容没有说明。

### 6.4 关键规则

检查 PRD 是否说明：

- 业务范围；
- 功能模块；
- 具体对象；
- 主规则；
- 子规则；
- 特殊情况；
- 处理结果。

常见不通过情况：

- 只有结果，没有判断条件；
- 规则散落在多个地方，无法形成完整判断链；
- 特殊情况缺失；
- 处理结果不明确；
- 规则和流程、范围存在冲突。

### 6.5 验收标准

检查 PRD 是否说明：

- 验收范围；
- 验收场景；
- 操作或条件；
- 预期结果；
- 不通过情况。

常见不通过情况：

- 只写“功能正常”；
- 没有具体场景；
- 没有预期结果；
- 没有不通过情况；
- 验收标准和需求目标不对应。

### 6.6 待确认点

检查 PRD 中不明确的问题是否说明：

- 待确认问题；
- 影响范围；
- 当前建议或默认处理；
- 负责人；
- 确认节点。

常见不通过情况：

- 有不明确内容但没有放入待确认点；
- 只写“待确认”，没有影响范围；
- 没有负责人；
- 没有确认时间节点；
- 待确认点会影响开发启动但没有标注风险。

### 6.7 异常处理

检查 PRD 是否说明：

- 异常发生位置；
- 异常情况；
- 处理方式；
- 用户或系统表现；
- 未覆盖异常的后续确认机制。

常见不通过情况：

- 完全没有异常处理；
- 只写“报错提示”；
- 没有说明系统如何兜底；
- 没有说明用户看到什么；
- 没有说明研发发现新异常时如何确认。

### 6.8 AI 检查

内置 Checklist 中的 AI 检查属于系统性检查项。

Skill 应根据本次检查结果判断：

- 如果已完成完整自查且无明显缺口，可标记为通过；
- 如果完成了自查但存在明显缺口，应标记为需补充；
- 如果没有完成检查，应标记为未检查。

---

## 7. 输出要求

Skill 必须按内置 `output-template.md` 固定格式输出报告，顺序与字段不可省略。输出不能只给「是 / 否」，必须服务宣讲前决策。

报告固定包含五个部分，顺序如下：

1. 整体结论；
2. 分项检查表；
3. 一致性 / 反证检查结果；
4. 宣讲前补充清单；
5. 可复制补充建议。

### 7.1 整体结论

整体结论只允许填写以下两种之一：

- **通过**：PRD 已能支持研发理解需求、评估范围、拆解任务、识别主要风险并判断验收口径，可以进入研发宣讲。
- **不通过**：PRD 存在会影响核心主流程、研发评估、技术方案、工作量拆解或验收口径的问题，不建议进入研发宣讲。

补充说明：

- 必须附一句话说明：为什么是这个结论；是否可以进入研发宣讲；如果不通过，说明关键阻塞或缺口。
- 输入不足以完成检查时，也填写「不通过」，并在一句话说明中写明缺少什么信息，不得强行给「通过」。
- 二次检查时，需标注检查轮次（第 N 轮），并对比上一轮：上一轮不通过项是否已修复；若从「不通过」变为「通过」，说明主要修复了哪些阻塞项；若仍为「不通过」，说明还剩哪些必须补齐项。

### 7.2 分项检查表

分项检查表以表格形式输出，检查项来自内置 Checklist（7 项 + AI 检查项）：

| 需求目标 | 主流程 | 涉及范围 | 关键规则 | 验收标准 | 待确认点 | 异常处理 | AI 检查 |

每个检查项必须输出以下字段：

- **检查项**：上表 8 项之一；
- **判断结果**：通过 / 不通过 / 不涉及 / 待确认（AI 检查项额外允许「未检查」）；
- **依据说明**：说明判断依据，引用 PRD 中相关内容或说明缺失点；
- **发现的问题**：具体问题描述；判断为「通过」时可填「无」；
- **是否阻塞宣讲**：是 / 否。

判断结果填写规则：

- **通过**：内容满足研发理解和评估需要；「是否阻塞宣讲」填「否」。
- **不通过**：内容缺失、空泛、矛盾或不可评估；若影响宣讲判断，「是否阻塞宣讲」填「是」。
- **不涉及**：本需求确实不涉及该检查项；必须说明为什么不涉及；「是否阻塞宣讲」填「否」。
- **待确认**：存在未明确内容；需继续判断是否影响宣讲：
  - 影响核心主流程、研发评估、技术方案、工作量拆解或验收口径 → 「是否阻塞宣讲」填「是」，整体结论为「不通过」；
  - 不影响核心主流程，只是后续完善项 → 「是否阻塞宣讲」填「否」，整体结论可以为「通过」，问题放入「可选优化建议」。

### 7.3 是否阻塞宣讲

「是否阻塞宣讲」是分项检查与整体结论之间的核心判断维度。

判断标准：只看该问题是否影响研发进入有效评估和讨论。以下任一情况成立时，标记为「是」：

1. 研发无法理解为什么做、做给谁、做到什么程度；
2. 研发无法看懂核心主流程；
3. 研发无法判断涉及哪些端、系统、数据、接口或历史流程；
4. 研发无法理解关键业务规则和边界；
5. 研发无法拆解任务、评估工作量或识别主要风险；
6. 测试或验收无法判断什么算通过、什么算不通过。

以下情况标记为「否」：不影响以上六项，仅为表达、示例、边缘场景、结构或可读性优化。

规则：

- 任一检查项「是否阻塞宣讲」为「是」时，整体结论必须为「不通过」。
- 所有检查项「是否阻塞宣讲」均为「否」时，整体结论可以为「通过」。

### 7.4 一致性 / 反证检查结果

单独输出一节，列出 PRD 前后发现的矛盾、遗漏或冲突。

重点检查：

- 需求目标与验收标准是否一致；
- 涉及范围与关键规则是否一致；
- 主流程与异常处理是否一致；
- 本期不包含内容是否与后文冲突。

填写规则：

- 无影响宣讲判断的矛盾时，写「未发现影响宣讲判断的明显矛盾」。
- 会影响宣讲判断的矛盾，必须进入「必须补齐」清单。
- 仅为表达或结构问题、不影响宣讲判断的，可进入「可选优化建议」。

### 7.5 宣讲前补充清单

补充清单只分两类：

1. **必须补齐（否则不建议宣讲）**  
   会影响核心主流程、研发评估、技术方案、工作量拆解或验收口径的问题；对应分项检查表中「是否阻塞宣讲」为「是」的项。不补齐则整体结论为「不通过」。

2. **可选优化建议（不影响是否宣讲）**  
   不影响是否宣讲的问题，可由产品负责人根据时间和必要性选择是否补充。对应「是否阻塞宣讲」为「否」的改进项。

无对应项时写「无」。

### 7.6 可复制补充建议

对于缺失或不完整内容，Skill 可以给出可直接粘贴进 PRD 的补充建议草案。

填写规则：

- 必须带声明：「以下为建议草案，需产品负责人确认后再写入 PRD。」
- 不得编造业务规则。
- 必须区分是针对「必须补齐项」还是「可选优化项」。
- 对于必须补齐项，建议草案要能帮助产品负责人补到可宣讲程度。
- 对于可选优化项，建议草案不能反向影响整体结论。

---

## 8. 一致性和反证检查

Skill 需要主动检查 PRD 中是否存在前后不一致的问题。

重点包括：

- 需求目标和验收标准是否一致；
- 涉及范围和关键规则是否一致；
- 主流程和异常处理是否一致；
- 本期不包含内容是否和后文描述冲突；
- 范围表中写“不涉及”的对象，后文是否又出现相关逻辑；
- 待确认点是否实际影响当前开发启动；
- 验收场景是否覆盖关键规则；
- 异常处理是否覆盖主流程中的关键失败节点。

发现矛盾时，不能强行判断通过，必须标记为“需补充”或“待确认”。

---

## 9. AI 行为边界

Skill 必须遵守以下限制：

- 不替产品编造业务规则；
- 不把推测内容当成事实；
- 不擅自补充未经确认的范围、流程、规则或验收标准；
- 对缺失内容只能提出补充方向或建议草案；
- 所有影响开发的未知点必须进入待确认点；
- 不追求文档完美，只判断是否满足宣讲前最低可评估标准；
- 不替代正式研发评审，只做宣讲前自查。

## 10. 推荐 Skill 结构

第一版 Skill 可以采用以下结构：

```text
prd-pre-briefing-checker/
├── SKILL.md
├── references/
│   ├── review-rubric.md
│   ├── output-template.md
│   └── examples.md
└── agents/
    └── openai.yaml
```

### 10.1 SKILL.md

负责说明：

- Skill 什么时候触发；
- 输入要求；
- 检查流程；
- 输出要求；
- 是否阻塞宣讲判断规则；
- 禁止脑补规则；
- 最终宣讲建议判断方式。

### 10.2 review-rubric.md

负责沉淀：

- 每个检查项的通过条件；
- 不通过条件；
- 常见风险；
- 反证检查点；
- 补充建议原则。

### 10.3 output-template.md

负责沉淀固定输出格式（顺序与字段不可省略）：

- 整体结论（通过 / 不通过 + 一句话说明 + 检查轮次）；
- 分项检查表（含是否阻塞宣讲）；
- 一致性 / 反证检查结果；
- 宣讲前补充清单（必须补齐 / 可选优化建议）；
- 可复制补充建议。

### 10.4 examples.md

负责提供样例：

- 一个整体结论为「通过」的案例；
- 一个整体结论为「不通过」、含必须补齐项的案例；
- 一个输入不足、结论为「不通过」并说明缺口的案例。

## 11. 推荐使用流程

该 Skill 的典型使用链路如下：

1. 产品写完 PRD；
2. 上传 PRD（无需上传 Checklist，Skill 已内置）；
3. 运行 PRD 宣讲前 AI 自查 Skill；
4. Skill 输出宣讲前检查报告；
5. 产品按「必须补齐」项补充 PRD；
6. 再次运行 Skill；
7. 通过后进入产品设计宣讲。

该 Skill 应支持二次检查。第二次检查时，需要重点判断上一次的问题是否已经修复，以及是否还存在新的阻塞项。

---

## 12. 第一版验收标准

第一版 Skill 需要满足以下标准：

1. 内置 Checklist 已定义检查项、确认问题和判断选项，并能被 Skill 正确加载；
2. 能基于内置 Checklist 对 PRD 逐项检查；
3. 能区分章节缺失、内容空泛、研发不可评估、前后矛盾等不同问题；
4. 能输出「通过 / 不通过」的整体结论及一句话说明；
5. 能输出每个检查项的判断结果和原因；
6. 能正确判断每项「是否阻塞宣讲」，并区分「必须补齐」与「可选优化建议」；
7. 能输出一致性 / 反证检查结果，并将影响宣讲的矛盾归入必须补齐清单；
8. 能提供建议草案，但不会把建议草案当成事实；
9. 能处理“不涉及”“待确认”等非简单通过/失败状态；
10. 输入不足时输出「不通过」，并在说明中写明缺少什么信息，而不是强行给「通过」。

---

## 13. 最终目标

最终目标不是让 AI 替产品写 PRD，而是让 AI 在宣讲前帮产品完成一次高质量自查。

它要解决的是：

- 产品自己以为讲清楚了，但研发听不懂；
- PRD 看起来完整，但无法评估；
- 规则写了，但验收标准对不上；
- 范围表写了不涉及，但后文又出现相关逻辑；
- 待确认点没有负责人和确认节点；
- 异常处理缺失，研发只能靠猜。

因此，这个 Skill 的核心判断标准是：

> 研发能否基于这份 PRD 开始有效评估和讨论。

而不是：

> PRD 是否形式上填满了模板。
