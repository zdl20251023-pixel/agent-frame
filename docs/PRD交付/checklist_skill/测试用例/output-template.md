# 输出模板（output-template）

Skill 必须按本模板输出报告，顺序与字段不可省略。输出不能只给「是 / 否」，必须服务宣讲前决策。

---

## 模板

```markdown
# PRD 宣讲前自查报告

## 一、整体结论

- 结论：通过 / 不通过
- 一句话说明：（为什么是这个结论；是否可以进入研发宣讲；如果不通过，说明关键阻塞或缺口）
- 检查轮次：第 N 轮（二次检查时填写）

## 二、分项检查表

| 检查项   | 判断结果                        | 依据说明 | 发现的问题 | 是否阻塞宣讲 |
| -------- | ------------------------------- | -------- | ---------- | ------------ |
| 需求目标 | 通过 / 不通过 / 不涉及 / 待确认 |          |            | 是 / 否      |
| 主流程   |                                 |          |            |              |
| 涉及范围 |                                 |          |            |              |
| 关键规则 |                                 |          |            |              |
| 验收标准 |                                 |          |            |              |
| 待确认点 |                                 |          |            |              |
| 异常处理 |                                 |          |            |              |
| AI 检查  | 通过 / 不通过 / 未检查          |          |            | 否           |

> 检查项来自内置 Checklist（checklist.md），即上表 7 项 + AI 检查项。

## 三、一致性 / 反证检查结果

- 列出发现的矛盾、遗漏或冲突；
- 无影响宣讲判断的矛盾时写「未发现影响宣讲判断的明显矛盾」。

## 四、宣讲前补充清单

### 必须补齐（否则不建议宣讲）

1.

### 可选优化建议（不影响是否宣讲）

1.

## 五、可复制补充建议

> 以下为建议草案，需产品负责人确认后再写入 PRD。

- 针对【必须补齐项 / 可选优化项】给出可直接粘贴进 PRD 的草案文本。
```

---

## 填写要求

- **整体结论**：只允许填写「通过 / 不通过」。
  - **通过**：PRD 已能支持研发理解需求、评估范围、拆解任务、识别主要风险并判断验收口径，可以进入研发宣讲。
  - **不通过**：PRD 存在会影响核心主流程、研发评估、技术方案、工作量拆解或验收口径的问题，不建议进入研发宣讲。
  - 输入不足以完成检查时，也填写「不通过」，并在一句话说明中写明缺少什么信息。
- **分项检查表**：每项都要有判断结果、依据说明、发现的问题、是否阻塞宣讲。
  - 判断为「通过」时，「是否阻塞宣讲」填「否」，发现的问题可填「无」。
  - 判断为「不涉及」时，需要说明为什么不涉及。
  - 判断为「待确认」时，必须继续判断该问题是否影响宣讲：
    - 如果影响核心主流程、研发评估、技术方案、工作量拆解或验收口径，则「是否阻塞宣讲」填「是」，整体结论为「不通过」。
    - 如果不影响核心主流程，只是后续完善项，则「是否阻塞宣讲」填「否」，整体结论可以为「通过」，并放入「可选优化建议」。
- **是否阻塞宣讲**：只看该问题是否影响研发进入有效评估和讨论。
  - 会影响以下任一内容时，标记为「是」：
    1. 研发无法理解为什么做、做给谁、做到什么程度；
    2. 研发无法看懂核心主流程；
    3. 研发无法判断涉及哪些端、系统、数据、接口或历史流程；
    4. 研发无法理解关键业务规则和边界；
    5. 研发无法拆解任务、评估工作量或识别主要风险；
    6. 测试或验收无法判断什么算通过、什么算不通过。
  - 不影响以上内容，只是表达、示例、边缘场景、结构或可读性优化时，标记为「否」。
- **补充清单**：只分两类：
  - **必须补齐**：会影响核心主流程、研发评估、技术方案、工作量拆解或验收口径的问题；不补齐则不建议宣讲。
  - **可选优化建议**：不影响是否宣讲的问题，可由产品负责人根据时间和必要性选择是否补充。
  - 无对应项时写「无」。
- **一致性 / 反证检查结果**：
  - 重点检查需求目标与验收标准是否一致、涉及范围与关键规则是否一致、主流程与异常处理是否一致、本期不包含内容是否与后文冲突。
  - 如果发现会影响宣讲判断的矛盾，必须进入「必须补齐」。
  - 如果只是表达或结构问题，不影响宣讲判断，可进入「可选优化建议」。
- **可复制补充建议**：
  - 必须带「以下为建议草案，需产品负责人确认后再写入 PRD。」声明。
  - 不得编造业务规则。
  - 必须区分是针对「必须补齐项」还是「可选优化项」。
  - 对于必须补齐项，建议草案要能帮助产品负责人补到可宣讲程度。
  - 对于可选优化项，建议草案不能反向影响整体结论。
- **二次检查**：
  - 在「整体结论」中对比上一轮，标明上一轮不通过项是否已修复。
  - 如果从「不通过」变为「通过」，说明主要修复了哪些阻塞项。
  - 如果仍为「不通过」，说明还剩哪些必须补齐项。

