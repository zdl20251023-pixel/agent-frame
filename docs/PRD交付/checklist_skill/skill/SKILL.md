# PRD 宣讲前 AI 自查 Skill

## 1. 这个 Skill 做什么

以内置的「宣讲前 Checklist」为规则来源，以「PRD」为被检查对象，自动完成结构完整性、研发可评估性、内容一致性与反证、宣讲阻塞项识别、补充建议生成五类检查，最终回答一个核心问题：

> 这个 PRD 现在能不能拿去给研发宣讲？

判断标准是「研发能否基于这份 PRD 开始有效评估和讨论」，**不是**「PRD 是否形式上填满了模板」。

## 2. 触发场景

满足任一情况时使用本 Skill：

- 用户提供了 PRD 文档；
- 用户要求做 PRD 宣讲前自查、宣讲前评审、需求质量门禁；
- 用户问「这个 PRD 能不能宣讲 / 能不能给研发讲」；
- 用户要求检查 PRD 是否达到最低可评估标准。

## 3. 输入要求

第一版只需以下输入：

1. PRD 文档（文本或 Markdown）。

关于 Checklist：

- **Checklist 已内置在 Skill 中**，见 [references/checklist.md](references/checklist.md)，包含检查项、宣讲前确认问题与判断选项。用户无需也无法在运行时替换；需变更规则时更新该文件。
- PRD 可以不使用标准模板标题，但需要能把内容识别到对应模块。

第一版暂不重点处理：图片型 PDF、扫描件、多个 PRD 批量审查、飞书/Notion/Confluence 外链直读、复杂图表、自动改写完整 PRD。遇到这些输入时，说明限制并就可读取部分检查。

## 4. 检查流程

复制以下清单并跟踪进度：

```
检查进度：
- [ ] 步骤 1：加载内置 Checklist（references/checklist.md），明确检查项 / 确认问题 / 判断选项
- [ ] 步骤 2：将 PRD 内容映射到各检查项
- [ ] 步骤 3：逐项做四类判断（结构 / 内容 / 可评估 / 一致性反证）
- [ ] 步骤 4：跨章节一致性与反证检查
- [ ] 步骤 5：判断每项「是否阻塞宣讲」
- [ ] 步骤 6：得出整体结论（通过 / 不通过）
- [ ] 步骤 7：按模板输出报告
```

**步骤 1：加载内置 Checklist**
读取 `references/checklist.md`，明确检查项名称、每项的确认问题、每项允许的判断值、「不涉及 / 待确认」等特殊选项，以及「AI 检查」这类系统性检查项。

**步骤 2：映射 PRD**
把 PRD 内容对应到各检查项，允许标题不一致时按语义归类；找不到对应内容记为「章节缺失」。

**步骤 3：逐项四类判断**
对每个检查项，依据 `references/review-rubric.md` 完成：

1. 结构完整性——是否包含对应章节或相关内容；
2. 内容有效性——内容是否具体明确，而非空泛描述；
3. 研发可评估性——研发能否据此评估影响范围、技术方案、工作量、边界与验收方式；
4. 一致性 / 反证——是否与 PRD 其它部分矛盾、遗漏或冲突。

**步骤 4：一致性与反证**
按 `references/review-rubric.md` 的反证清单主动找矛盾，例如范围表写「不涉及」但后文出现相关逻辑、验收标准与需求目标不对应、异常处理未覆盖主流程关键失败节点。发现矛盾时，**不得强行判断通过**，必须标记为「不通过」或「待确认」。

**步骤 5：是否阻塞宣讲**

对每项检查判断「是否阻塞宣讲」（是 / 否），标准见 `references/output-template.md`。核心原则：只看该问题是否影响研发进入有效评估和讨论。任一检查项为「是」时，整体结论必须为「不通过」。

**步骤 6：整体结论**（二选一）

1. **通过**——PRD 已能支持研发理解需求、评估范围、拆解任务、识别主要风险并判断验收口径，可以进入研发宣讲；
2. **不通过**——存在会影响核心主流程、研发评估、技术方案、工作量拆解或验收口径的问题，不建议进入研发宣讲。输入不足以完成检查时，也判「不通过」，并在一句话说明中写明缺少什么信息。

**步骤 7：输出**
严格按 `references/output-template.md` 的格式输出报告。

## 5. AI 检查项的判断

内置 Checklist 中的「AI 检查」是系统性检查项，根据本次检查结果判断：

- 已完成完整自查且无明显缺口 → 通过；
- 完成自查但存在明显缺口 → 不通过；
- 没有完成检查 → 未检查。

## 6. 二次检查

支持二次检查。用户提供修订后 PRD 时，重点判断上一轮问题是否已修复，以及是否出现新的阻塞项，并在报告中对比上一轮结论。

## 7. AI 行为边界（必须遵守）

- 不替产品编造业务规则；
- 不把推测内容当成事实；
- 不擅自补充未经确认的范围、流程、规则或验收标准；
- 对缺失内容只能提出补充方向或建议草案；
- 所有影响开发的未知点必须进入待确认点；
- 不追求文档完美，只判断是否满足宣讲前最低可评估标准；
- 不替代正式研发评审，只做宣讲前自查；
- 所有补充草案必须标注：「以下为建议草案，需产品负责人确认后再写入 PRD。」

## 9. 在 ChatGPT 中使用

本 Skill 同时提供 ChatGPT 自定义 GPT 版本：

- GPT 配置（名称/描述/开场白/知识文件清单）：见 [agents/openai.yaml](agents/openai.yaml)
- 可直接粘贴到 ChatGPT 指令框的自包含指令：见 [agents/chatgpt-instructions.md](agents/chatgpt-instructions.md)

搭建步骤：在 ChatGPT「创建 GPT → 配置」中，把 `agents/chatgpt-instructions.md` 的指令整段粘贴到 Instructions 框，再把 `references/` 下四份文件（含内置 `checklist.md`）上传到 Knowledge，即可使用。用户只需发 PRD，无需再发 Checklist。
