# 检查示例（examples）

提供三类结论的样例，帮助 Skill 校准判断尺度。示例为节选，实际输出请用完整模板。

---

## 示例 1：通过

**输入特征**：以「优惠券发放与使用」PRD 为例，需求目标含目标用户/当前问题/目标结果/本期不包含；主流程含整体流程、4 个模块流程、关键节点；涉及范围表 6 行齐全且标注改动类型；关键规则按完整判断链书写；验收标准含范围、5 个场景、不通过情况；待确认点 5 项含影响范围/负责人/确认节点；异常处理含已知异常表与未覆盖异常机制。

**报告节选**：

```markdown
## 一、整体结论
- 结论：通过
- 一句话说明：七项检查均通过，范围、规则、验收闭环一致，未发现阻塞性矛盾，可以进入研发宣讲。

## 二、分项检查表（节选）
| 检查项 | 判断结果 | 依据说明 | 发现的问题 | 是否阻塞宣讲 |
|---|---|---|---|---|
| 需求目标 | 通过 | 目标用户/问题/结果/边界齐全且可验证 | 无 | 否 |
| 验收标准 | 通过 | 含范围+5 场景+不通过情况，与目标对应 | 无 | 否 |
| AI 检查 | 通过 | 已完成完整自查，无明显缺口 | 无 | 否 |
```

---

## 示例 2：不通过（含必须补齐项）

**输入特征**：需求目标只写「优化下单体验」，无目标用户与可验证结果；无主流程；涉及范围表为空；关键规则只有结果无判断条件；验收标准只写「功能正常」。

**报告节选**：

```markdown
## 一、整体结论
- 结论：不通过
- 一句话说明：目标空泛、缺主流程、范围表为空、规则与验收不可评估，研发无法据此评估，不建议进入研发宣讲。

## 二、分项检查表（节选）
| 检查项 | 判断结果 | 依据说明 | 发现的问题 | 是否阻塞宣讲 |
|---|---|---|---|---|
| 需求目标 | 不通过 | 仅「优化体验」，无用户/可验证结果 | 目标无法验证 | 是 |
| 主流程 | 不通过 | 未提供任何流程 | 缺整体/模块/节点 | 是 |
| 涉及范围 | 不通过 | 范围表为空 | 无法判断影响面 | 是 |
| 验收标准 | 不通过 | 仅「功能正常」 | 无场景/预期结果 | 是 |

## 四、宣讲前补充清单
### 必须补齐（否则不建议宣讲）
1. 需求目标：补目标用户、当前问题、可验证目标结果、本期不包含。
2. 主流程：补整体流程、模块流程、关键节点。
3. 涉及范围：补范围表与改动类型。
4. 验收标准：补验收范围、场景、不通过情况。

## 五、可复制补充建议
> 以下为建议草案，需产品负责人确认后再写入 PRD。
- 【必须补齐项】需求目标：目标用户「待确认」/ 当前问题「待确认」/ 目标结果「待确认」/ 本期不包含「待确认」。
```

## 示例 3：不通过（输入不足）

**输入特征**：用户未提供 PRD，或 PRD 为图片型 PDF / 扫描件无法读取文本。

**报告节选**：

```markdown
## 一、整体结论
- 结论：不通过
- 一句话说明：未获得可读取的 PRD 文本（仅扫描件），无法完成有效检查，不建议进入研发宣讲。请提供文本或 Markdown 版 PRD。
```

---

## 补充参考：通过 + 可选优化建议

**输入特征**：核心章节齐全且研发可评估，但异常处理只覆盖主流程，未说明「支付中优惠券刚好过期」的处理；待确认点缺确认节点。上述缺口不影响核心主流程评估。

**报告节选**：

```markdown
## 一、整体结论
- 结论：通过
- 一句话说明：目标/范围/流程/规则/验收可支撑评估，可以进入研发宣讲；异常处理与待确认点有非阻塞缺口，建议宣讲前或宣讲中补齐。

## 二、分项检查表（节选）
| 检查项 | 判断结果 | 依据说明 | 发现的问题 | 是否阻塞宣讲 |
|---|---|---|---|---|
| 异常处理 | 待确认 | 已知异常表有，但漏关键失败节点 | 未覆盖「支付中优惠券过期」 | 否 |
| 待确认点 | 待确认 | 问题与影响范围有，缺确认节点 | 退款是否退券未标确认节点 | 否 |

## 四、宣讲前补充清单
### 必须补齐（否则不建议宣讲）
无

### 可选优化建议（不影响是否宣讲）
1. 异常处理补充「支付过程中优惠券过期」场景。
2. 待确认点补齐确认节点。
```
