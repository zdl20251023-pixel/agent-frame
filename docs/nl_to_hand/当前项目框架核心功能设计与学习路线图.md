# 当前项目框架核心功能设计与学习路线图

> 更新时间：2026-06-07  
> 适用范围：`apps/api`、`apps/web`、`packages/shared`、`apps/api/evals` 当前实现。  
> 阅读目标：帮助开发者系统理解 `agent-frame` 的核心框架能力、自然语言转牌谱业务如何接入框架，以及后续学习和二次开发的推荐路径。

---

## 1. 项目总体定位

`agent-frame` 是一个面向多 Agent 应用的运行时框架。它不是单一聊天 Demo，而是把一次用户请求抽象成可追踪、可恢复、可扩展的 `Run`，再用 `Step`、`AgentEvent`、`ToolInvocation`、`Artifact`、`Workflow`、`A2A` 和 `Plugin` 等模型组织 Agent 应用的完整生命周期。

当前仓库最核心的产品目标可以概括为：

1. 提供通用 Agent 后端框架，支持不同 Agent 统一接入。
2. 支持 Agent 之间通过 A2A 协议互相调用。
3. 支持长流程 Workflow 编排。
4. 支持结构化产物 Artifact 及多版本管理。
5. 支持 Session 级别状态投影和实时事件同步。
6. 支持自然语言转牌谱这类复杂业务作为专用 Agent 能力接入。
7. 支持基础生产化能力，包括持久化、恢复、调度、观测、质量门禁和插件化扩展。

## 3. 一次请求的完整执行链路

从用户在前端发送消息，到后端 Agent 执行，再到前端展示结果，主链路如下：

```txt
用户输入
  → apps/web ChatPage
  → POST /runs
  → RunsService
  → SessionsService / ConversationContextBuilder
  → CapabilityRouter
  → RunManager.createRun()
  → Scheduler.schedule()
  → AgentExecutorRouter
  → 目标 Agent
  → ModelClient / ToolRegistry / A2AClient
  → Step / AgentEvent / ToolInvocation
  → Artifact / ArtifactVersion
  → Run SSE / Session SSE / SessionProjection
  → 前端 RunMessageItem / ArtifactViewer / HandHistoryPanel
```

这条链路体现了框架的核心设计思想：

- HTTP 层只负责接收请求和返回入口响应，不直接执行业务细节。
- `RunsService` 负责业务入口编排，包括会话、上下文、幂等键和能力路由。
- `RunManager` 负责 Run 生命周期，不关心具体 Agent 内部业务。
- `Scheduler` 负责并发控制和队列调度。
- `AgentExecutorRouter` 负责把 Run 分发给具体 Agent。
- Agent 通过 `ModelClient` 调模型，通过 `ToolRegistry` 调工具，通过 `A2AClient` 调其他 Agent。
- 所有执行过程都落到 `Step`、`AgentEvent`、`ToolInvocation` 和 `Artifact`，便于追踪、恢复和前端展示。

## 4. 后端核心模块设计

### 4.1 服务入口与应用装配

关键文件：

- `apps/api/src/server.ts`
- `apps/api/src/app.ts`
- `apps/api/src/container.ts`

`server.ts` 是 Bun 启动入口，负责调用 `validateEnv()` 校验环境变量，然后创建 Elysia 应用并监听端口。

`app.ts` 负责注册：

- CORS
- traceId 链路追踪
- rate limit
- 请求日志
- 统一错误处理
- `/health`
- `/metrics`
- runs、sessions、artifacts、workflows、agents、plugins 等业务路由

`container.ts` 是当前后端最重要的装配中心，主要职责包括：

1. 根据环境选择 `MySQLRunStore` 或 `MemoryRunStore`。
2. 创建 ArtifactStore、WorkflowStore、MemoryStore。
3. 注册内置插件。
4. 从插件中收集 Agent Runtime、Capability Hints、A2A Policy 和 Workflow Runtime。
5. 创建 `CapabilityRouter`、`A2APolicy`、`A2ARouter`、`A2AClient`。
6. 创建 `AgentExecutorRouter` 并注册入口 Agent。
7. 创建 `RunManager`。
8. 启动后台 Worker：`AgentTaskWorker`、`NlToHandRepairWorker`、`ToolInvocationRecoveryWorker`、`RunRecoveryWorker`。

学习建议：先读 `container.ts`，因为它能把分散模块串成一张完整依赖图。

### 4.2 Run 生命周期

关键文件：

- `apps/api/src/runtime/run-manager.ts`
- `apps/api/src/runtime/scheduler.ts`
- `apps/api/src/runtime/step-manager.ts`
- `apps/api/src/runtime/event-emitter.ts`
- `apps/api/src/runtime/stores/run-store.ts`
- `packages/shared/src/models/run.ts`

`Run` 是框架的顶层执行单位。一次用户请求、一次 Agent 任务或一次业务执行都应该落到一个 Run 上。

`Run` 主要包含：

- `id`：Run 唯一 ID。
- `traceId`：链路追踪 ID。
- `userId` / `projectId` / `sessionId`：归属信息。
- `agentId`：本次 Run 目标 Agent。
- `status`：`queued`、`running`、`completed`、`failed`、`cancelled` 等状态。
- `input` / `output` / `error`：输入、输出和错误。
- `idempotencyKey`：客户端幂等键，避免重复创建 Run。
- `checkpointPayload`：恢复时定位最后安全步骤。

`RunManager` 的核心职责：

1. 创建 Run。
2. 创建取消信号。
3. 发出 `run.started` 事件。
4. 把 Run 提交给 Scheduler。
5. 执行目标 Agent。
6. 根据结果更新 Run 状态。
7. 发出 `run.completed`、`run.failed` 或 `run.cancelled` 事件。
8. 支持 `resumeRun()` 从持久化记录恢复执行。

`Scheduler` 的核心职责：

- 控制并发执行数量。
- 维护优先级队列。
- 支持等待超时。
- 在 Redis 存在时通过 `RedisRunLease` 做多实例全局并发租约。

### 4.3 Step 与 AgentEvent

关键文件：

- `apps/api/src/runtime/step-manager.ts`
- `apps/api/src/runtime/event-emitter.ts`
- `packages/shared/src/events/agent-event.ts`
- `packages/shared/src/constants/event-types.ts`

`Step` 记录 Run 内部的结构化执行步骤，例如：

- 模型调用
- 工具调用
- A2A 调用
- Workflow Stage

`AgentEvent` 记录前端和观测系统关心的事件流，例如：

- `run.started`
- `message.delta`
- `tool.call`
- `tool.result`
- `tool.invocation.updated`
- `agent.call.started`
- `agent.call.completed`
- `artifact.created`
- `artifact.version.created`
- `workflow.started`
- `workflow.completed`

设计重点：

- `Step` 偏执行审计和调用树。
- `AgentEvent` 偏前端实时展示和事件订阅。
- 两者都写入 `RunStore`，共同构成 Run 的可观测执行轨迹。

### 4.4 Agent 与 ModelClient

关键文件：

- `apps/api/src/ai/agents/supervisor.agent.ts`
- `apps/api/src/ai/agents/nl-to-hand.agent.ts`
- `apps/api/src/ai/agents/research.agent.ts`
- `apps/api/src/ai/agents/summary.agent.ts`
- `apps/api/src/ai/agents/agent-executor-router.ts`
- `apps/api/src/ai/model-client/model-client.ts`
- `apps/api/src/ai/model-client/vercel-ai-model-client.ts`
- `apps/api/src/ai/tools/index.ts`

Agent 是具体能力执行者。框架通过统一的 `AgentExecutor` 接口调用不同 Agent：

```txt
AgentExecutor
  agentId
  execute(input, context) → AgentOutput
```

`AgentExecutorRouter` 是入口执行器，它根据 `RunContext.agentId` 或默认 Agent，把 Run 分发给具体 Agent。

`ModelClient` 是模型访问抽象层。业务 Agent 不应该直接依赖某个模型 SDK，而是通过 `ModelClient` 发起流式调用。当前实现中 `VercelAIModelClient` 封装了 Vercel AI SDK，并向框架输出统一的模型流事件。

设计收益：

- 替换模型供应商时影响范围更小。
- Agent 逻辑与底层 SDK 解耦。
- 便于统一记录 usage、cost、traceId 和错误。

### 4.5 ToolInvocation 与工具恢复

关键文件：

- `packages/shared/src/models/tool-invocation.ts`
- `packages/shared/src/constants/tool-invocation-constants.ts`
- `apps/api/src/runtime/tool-invocation-recovery.worker.ts`
- `apps/api/src/runtime/tool-replay.registry.ts`
- `apps/api/src/features/agent-tools/tool_nl_to_hand.ts`
- `apps/api/src/features/agent-tools/nl-to-hand-repair.worker.ts`

`ToolInvocation` 是工具调用状态源。它记录一次工具执行的关键状态：

- 工具名
- 输入哈希
- 幂等键
- 当前状态
- 当前 phase
- heartbeat
- retryCount
- outputRef
- recoveryPayload
- errorCode / errorMessage

对复杂工具来说，单纯记录 `tool.call` 和 `tool.result` 不够。因为工具可能包含多个阶段，例如 `nl_to_hand`：

```txt
pre_parse_autofix
  → schema_validate
  → post_parse_autofix
  → simulate_hand
  → artifact_write
  → waiting_repair / succeeded / failed
```

`ToolInvocationRecoveryWorker` 的作用是扫描 stale 工具调用，并尽量恢复：

- 对可重放 phase，使用 `ToolReplayRegistry` 做确定性重放。
- 对 Artifact 写入，依赖幂等键避免重复产物。
- 对不可恢复状态，进入 `failed` 或 `timed_out` 终态。

### 4.6 A2A：Agent 调 Agent

关键文件：

- `apps/api/src/a2a/a2a-client.ts`
- `apps/api/src/a2a/a2a-router.ts`
- `apps/api/src/a2a/a2a-policy.ts`
- `packages/shared/src/a2a/a2a-protocol.ts`

A2A 是 Agent-to-Agent 的缩写，用于让一个 Agent 调用另一个 Agent。

当前核心对象：

- `A2AClient`：Agent 调用其他 Agent 的唯一入口。
- `A2ARouter`：根据目标 Agent ID 找到对应适配器。
- `A2APolicy`：控制哪个 Agent 可以调用哪个 Agent。
- `A2ARequest` / `A2AResponse`：共享协议类型。

当前同步调用链路：

```txt
Agent
  → A2AClient.callSync()
  → A2APolicy.assertCanCall()
  → StepManager.startStep(agent_call)
  → emit agent.call.started
  → A2ARouter.resolve(toAgentId)
  → targetAgent.execute()
  → completeStep / failStep
  → emit agent.call.completed / failed
```

学习重点：

- A2A 不是简单函数调用，而是带权限、事件、Step、超时、traceId 的框架级调用。
- 后续如果扩展异步 A2A，需要重点理解 `AgentTaskWorker` 和 `agentTaskStore`。

### 4.7 Workflow 编排

关键文件：

- `packages/shared/src/workflow/workflow-definition.ts`
- `apps/api/src/workflow/workflow-runner.ts`
- `apps/api/src/workflow/stage-executor.ts`
- `apps/api/src/workflow/workflow-registry.ts`
- `apps/api/src/workflow/human-gate.ts`
- `apps/api/src/features/workflows/workflows.route.ts`

Workflow 用于把多个 Agent 或人工节点按顺序编排成一个长流程。

核心概念：

- `WorkflowDefinition`：流程定义。
- `WorkflowRun`：一次流程运行实例。
- `Stage`：流程阶段。
- `StageExecutor`：执行单个阶段。
- `HumanGate`：人工审批或等待节点。
- `RetryPolicy`：Stage 失败后的重试策略。

当前执行逻辑：

```txt
WorkflowRunner.startWorkflowRun()
  → 创建 WorkflowRun
  → 异步 executeWorkflow()
  → 按 stages 顺序执行
  → 每个 stage 通过 StageExecutor 执行
  → 成功则把输出传给后续 stage
  → 失败则 workflow.failed
```

### 4.8 Artifact 与版本管理

关键文件：

- `packages/shared/src/models/artifact.ts`
- `apps/api/src/artifacts/artifact-store.ts`
- `apps/api/src/artifacts/artifact-version.ts`
- `apps/api/src/artifacts/artifact-events.ts`
- `apps/api/src/features/artifacts/artifacts.route.ts`
- `apps/web/src/features/artifacts/ArtifactViewer.tsx`
- `apps/web/src/features/artifacts/HandHistoryPanel.tsx`

Artifact 是结构化业务产物。它不是普通聊天文本，而是可继续编辑、可版本化、可回滚、可渲染的结果。

当前典型 Artifact：

- `hand_history`：自然语言转牌谱生成的结构化牌谱。
- 写作类 Artifact：由 creative-writing 插件生成。

`ArtifactVersionManager` 负责：

- 给 Artifact 追加新版本。
- 更新 `currentVersionId`。
- 记录 parentVersionId。
- 生成 diffSummary。
- 支持回滚到历史版本。

设计重点：

- Agent 输出文本是一次回答。
- Artifact 是可长期保存、继续修改和展示的业务状态。
- 对复杂 Agent 产品来说，Artifact 通常比聊天消息更重要。

### 4.9 SessionProjection 与实时同步

关键文件：

- `packages/shared/src/models/session-projection.ts`
- `apps/api/src/features/sessions/session-projection.service.ts`
- `apps/api/src/features/sessions/sessions.route.ts`
- `apps/api/src/features/sessions/session-event-emitter.ts`
- `apps/api/src/shared/realtime/sse.handler.ts`
- `apps/web/src/features/sessions/useSessionProjection.ts`
- `apps/web/src/features/chat/ChatPage.tsx`

SessionProjection 是会话级统一状态视图。它把前端需要关注的异步状态聚合到一个对象里：

- activeRuns
- toolInvocations
- artifacts
- pendingTasks
- activeHandHistory
- generatedAt

为什么需要它：

- 单个 Run SSE 只能覆盖 Run 生命周期。
- 后台修复任务可能在 Run 结束后继续执行。
- Artifact 版本可能由 Worker 后台追加。
- 前端如果只轮询单个接口，会出现状态分散和不同步。

当前前端通过 `useSessionProjection()`：

1. 请求 `/sessions/:sessionId/projection` 获取当前快照。
2. 订阅 `/sessions/:sessionId/events`。
3. 收到 Session SSE 后刷新 projection。
4. 对 `artifact.version.created` 等事件广播给 Artifact 面板刷新内容。

### 4.10 Plugin Runtime

关键文件：

- `apps/api/src/plugins/plugin.types.ts`
- `apps/api/src/plugins/plugin-runtime.types.ts`
- `apps/api/src/plugins/plugin-context.ts`
- `apps/api/src/plugins/plugin-registry.ts`
- `apps/api/src/plugins/builtin-plugins.ts`
- `apps/api/src/plugins/builtin-agent-runtimes.ts`
- `apps/api/src/plugins/creative-writing/creative-writing-plugin.ts`

插件系统用于把 Agent、Tool、Workflow、ArtifactType、CapabilityHints 和生命周期钩子注册到框架。

当前插件可以注册：

- Agent 元数据
- Agent Runtime
- Tool 定义和 runtimeFactory
- Workflow 定义和 Runtime
- ArtifactType
- CapabilityHints
- 生命周期 hook

设计收益：

- 新能力不需要硬编码到 `container.ts` 的每个分支。
- CapabilityRouter 可以从插件获取能力描述。
- A2A Policy 可以从插件 Agent Runtime 中生成。
- WorkflowRegistry 可以自动收集插件 Workflow。

学习重点：

- `PluginContextFactory` 如何给插件提供注册 API。
- `PluginRegistry` 如何保存和查询注册结果。
- `container.ts` 如何把插件注册结果装配成运行时对象。

### 4.11 CapabilityRouter

关键文件：

- `apps/api/src/capabilities/capability-router.ts`
- `apps/api/src/capabilities/capability-route-decision.store.ts`
- `packages/shared/src/models/capability-hints.ts`

`CapabilityRouter` 负责判断用户输入应该交给哪个 Agent。它解决的问题是：不要把所有能力识别都塞进 `SupervisorAgent`，否则随着业务增长，入口 Agent 会越来越臃肿。

当前能力：

- 根据输入和 `requestedAgentId` 决定目标 Agent。
- 支持插件提供 `CapabilityHints`。
- 支持低置信度时返回 `ask_clarification`。
- 持久化路由决策，便于后续审计和调优。

自然语言转牌谱就是通过能力路由进入 `nl-to-hand-agent` 的典型例子。

## 5. 自然语言转牌谱如何接入框架

自然语言转牌谱不是孤立工具，而是一个完整的框架能力样板。

### 5.1 业务入口

前端在 `ChatPage` 中根据模式构造输入：

```txt
普通聊天
  → agentId: supervisor-agent

牌谱生成
  → agentId: nl-to-hand-agent
  → command.type: create_from_nl

继续修改牌谱
  → agentId: nl-to-hand-agent
  → command.type: patch_from_nl
  → artifactId + baseVersionId + patchText
```

后端 `RunsService` 会结合 `CapabilityRouter` 确认最终 Agent。

### 5.2 Agent 执行

`NlToHandAgent` 的核心流程：

```txt
resolveCommandContext()
  → buildPrompt()
  → startStep(model_call)
  → ModelClient.stream({ tools: [nl_to_hand] })
  → 处理 text_delta
  → 处理 tool_call
      → create ToolInvocation
      → 记录 idempotencyKey / inputHash / recoveryPayload
  → 处理 tool_result
      → 更新 ToolInvocation phase
      → 写 Artifact / ArtifactVersion
      → emit artifact events
  → 返回 AgentOutput
```

### 5.3 工具内部校验

`nl_to_hand` 工具不是简单 JSON 生成器，而是多阶段结构化校验链路：

```txt
自然语言或候选 JSON
  → pre-parse autofix
  → LatestHandSchema.safeParse
  → post-parse autofix
  → simulateHand
  → 生成 valid ArtifactVersion
  → 或生成 draft ArtifactVersion 并进入后台 repair
```

### 5.4 后台修复

当工具生成 draft 但未完全通过校验时，会进入异步修复：

```txt
ToolInvocation: waiting_repair
  → 创建 AgentTask
  → NlToHandRepairWorker 扫描任务
  → inner repair
  → 追加新的 ArtifactVersion
  → emit artifact.repair.completed
  → Session SSE 通知前端刷新
```

这个链路体现了一个重要设计：Run 可以结束，但业务产物的修复和状态推进可以继续通过 SessionProjection 和 Session SSE 更新给用户。

## 7. Eval 与 CI 质量门禁

关键文件：

- `apps/api/evals/runner/eval-runner.ts`
- `apps/api/evals/runner/thresholds.ts`
- `apps/api/evals/nl_to_hand/golden_cases.jsonl`

当前 eval 覆盖：

- 路由准确率：`route_accuracy`
- 工具调用率：`tool_call_rate`

- 校验成功率：`validation_success_rate`
- Artifact 成功率：`artifact_success_rate`
- Patch 保留率：`patch_preservation_rate`

常用命令：

```bash
bun run eval:nl-to-hand
```

- `eval:nl-to-hand:ci` 使用 FakeModel 和 `--fail-on-regression`，适合 PR 门禁。
- `eval:nl-to-hand` 可以用于真实模型评测，适合 nightly 或发布前质量对比。

当前 CI 中已经支持通过 `ENABLE_NL_TO_HAND_EVAL=false` 跳过 NL to Hand Eval job。

## 12. 当前学习重点总结

这个项目最值得学习的不是某一个 Agent，而是以下框架设计能力：

1. **Run 驱动架构**：把每次执行变成可追踪、可恢复、可审计的运行单元。
2. **事件驱动展示**：用 AgentEvent 和 SSE 支撑前端实时体验。
3. **结构化产物模型**：用 Artifact/ArtifactVersion 管理可继续编辑的业务结果。
4. **工具状态化**：用 ToolInvocation 管理复杂工具的 phase、幂等和恢复。
5. **多 Agent 协作**：用 A2AClient、A2ARouter 和 A2APolicy 管理 Agent 调用关系。
6. **插件化扩展**：用 PluginRegistry 把 Agent、Tool、Workflow、CapabilityHints 纳入统一注册。
7. **生产化治理**：通过 Scheduler、RecoveryWorker、Store、Metrics、Eval/CI 控制长期质量。

如果只从业务角度看，`nl_to_hand` 是一个自然语言转牌谱功能；如果从框架角度看，它是当前项目中最完整的复杂 Agent 应用样板，贯穿了能力路由、专用 Agent、模型调用、工具校验、Artifact 版本、后台修复、SessionProjection 和 Eval 门禁。
