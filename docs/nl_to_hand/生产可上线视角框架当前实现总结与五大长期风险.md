# 生产可上线视角：框架当前实现总结与五大长期风险

> 更新时间：2026-06-07  
> 范围：`apps/api`、`apps/web`、`packages/shared`、`apps/api/evals` 当前实现。  
> 分析立场：不以 MVP / Demo 为判断标准，而以 **正式可上线产品、长期可运营 Agent 后端框架** 为标准。  
> 结论：当前框架已经从“可演示 Agent 应用”升级为“具备生产化骨架的 Agent Runtime”，但从长期正式产品角度看，仍有 5 个高优先级设计风险需要继续治理。

---

## 1. 总体结论

当前 `agent-frame` 的主设计方向是正确的：

- 以 `Run` 作为一次 Agent 执行的顶层生命周期单位。
- 以 `Step`、`AgentEvent`、`ToolInvocation` 记录执行轨迹。
- 以 `Artifact / ArtifactVersion` 承载结构化业务产物。
- 以 `CapabilityRouter` 负责入口能力识别，避免 `SupervisorAgent` 膨胀。
- 以 `ToolRegistry` 和 `PluginRegistry` 逐步统一能力发现与运行时执行。
- 以 `RunRecoveryWorker`、`ToolInvocationRecoveryWorker`、`NlToHandRepairWorker` 补齐恢复与异步边界。
- 以 `SessionProjection` 和 Session SSE 改善前端异步状态同步。
- 以 `eval:nl-to-hand:ci` 建立 LLM 业务质量门禁雏形。

但如果目标是正式上线并长期迭代，当前最致命的 5 个问题已经不再是“链路有没有接通”，而是：

1. **Run / Scheduler 已可恢复，但还不是强一致、可审计、可水平扩展的任务调度系统。**
2. **异步状态已有投影和 SSE，但还没有事件溯源级的一致性投影模型。**
3. **Plugin Runtime 已自动装配，但插件生命周期、版本治理、隔离和灰度能力不足。**
4. **LLM Eval 已有 CI 门禁，但真实模型、线上回放、成本和质量漂移治理还不完整。**
5. **安全治理仍偏基础，Tool 权限、租户隔离、Prompt Injection 和高风险操作审批需要产品级体系化。**

---

## 2. 当前框架实现设计总结

### 2.1 当前核心运行链路

```txt
用户输入
  → RunsService
  → CapabilityRouter
  → RunManager
  → Scheduler / RedisRunLease
  → AgentExecutorRouter
  → Agent
  → ModelClient / ToolRegistry / A2A
  → Step / AgentEvent / ToolInvocation
  → Artifact / ArtifactVersion
  → Run SSE / Session SSE / SessionProjection
  → Web Artifact UI / HandHistoryPanel
```

### 2.2 当前核心模块状态

| 模块 | 当前实现 | 生产级意义 |
|---|---|---|
| `RunManager` | 创建、执行、取消、完成、失败、`resumeRun()` | 统一 Agent 执行生命周期 |
| `Scheduler` | 进程内优先级队列 + Redis 全局并发租约 | 控制并发，避免多实例各自跑满 |
| `RunRecoveryWorker` | 扫描 stale `queued/running` Run，优先重新入队 | 进程重启后避免永久悬挂 |
| `ToolInvocationRecoveryWorker` | 支持 `artifact_write` 幂等补写、部分 phase 重放、不可恢复终态化 | 工具调用恢复协议雏形 |
| `CapabilityRouter` | 插件 capability hints + 强制澄清 + 路由决策持久化 | 入口能力治理 |
| `PluginRegistry` | Agent runtime、Tool runtime、Workflow runtime、Capability hints、A2A policy 自动装配 | 平台化扩展基础 |
| `AgentTask` / Worker | 异步 A2A 任务与 `nl_to_hand` 内层修复任务 | 长任务异步边界 |
| `SessionProjection` | 聚合 active runs、ToolInvocation、Artifact、AgentTask | 前端统一状态视图 |
| Session SSE | 推送后台修复、Artifact 版本等异步事件 | Run 结束后的异步状态同步 |
| `apps/api/evals` | golden / patch / routing cases + fake eval runner + CI 门禁 | LLM 质量回归基础 |

### 2.3 自然语言转牌谱链路

```txt
普通入口 / 牌谱入口
  → CapabilityRouter 判断牌局意图
  → NlToHandAgent
  → ModelClient.stream({ tools: [nl_to_hand] })
  → nl_to_hand baseline:
      runPreParseAutoFix
      LatestHandSchema.safeParse
      runPostParseAutoFix
      simulateHand
  → 成功：写 valid hand_history ArtifactVersion
  → 失败：写 draft ArtifactVersion
        → 创建 AgentTask
        → NlToHandRepairWorker 后台 inner_repair
        → 追加 valid ArtifactVersion
        → Session SSE 通知前端刷新
```

### 2.4 当前验证状态

当前已经通过：

```bash

bun run build
bun test
bun run eval:nl-to-hand:ci
```

`eval:nl-to-hand:ci` 当前 fake 模式结果：

| 指标 | 结果 |
|---|---|
| 总用例 | 32 |
| 通过 | 32 |
| route_accuracy | 100% |
| tool_call_rate | 100% |
| schema_success_rate | 100% |

## 3. 五大长期风险与优化方案

---

## 问题一：Run / Scheduler 已可恢复，但还不是强一致任务调度系统

### 当前状态

当前已经补齐了几个关键能力：

- `RunManager.resumeRun()` 可以从持久化 Run 重新入队。
- `RunRecoveryWorker` 会扫描 stale 的 `queued/running` Run。
- `ToolInvocationRecoveryWorker` 支持部分工具 phase 恢复。
- `Scheduler` 在 Redis 存在时通过 `RedisRunLease` 做全局并发租约。
- `Run` 支持 `idempotencyKey` 和 `checkpointPayload`。

这已经解决了“进程重启后 Run 永久挂起”的早期致命问题。

### 为什么仍然致命

从正式产品角度看，当前恢复机制更接近 **“恢复到可继续执行”**，还不是严格意义上的 **“从精确 checkpoint 继续执行”**。

主要风险：

| 风险 | 说明 |
|---|---|
| 调度队列仍是本地闭包队列 | Redis 只负责并发租约，不保存完整待执行闭包和优先级队列 |
| Run resume 可能重新执行 Agent | 如果某些副作用没有幂等保护，可能造成重复模型调用、重复工具调用或重复成本 |
| checkpoint 语义较弱 | 目前记录最后完成 Step，但没有完整“可恢复状态机” |
| 缺少 worker ownership | 多实例恢复时，需要更明确的 claim / heartbeat / lease owner |
| 缺少 dead-letter 策略 | 连续恢复失败的 Run 需要进入人工诊断队列 |

### 优化方案

#### 方案 1：引入持久化 Run Queue

建议新增 `run_queue` 或复用 `runs` 表增强字段：

```txt
run_queue
  id
  run_id
  status: queued | claimed | running | completed | failed | dead_letter
  priority
  attempts
  max_attempts
  lease_owner
  lease_expires_at
  available_at
  last_error
  created_at
  updated_at
```

执行流程：

```txt
createRun
  → runs.status = queued
  → run_queue.status = queued

worker loop
  → claim due queued job
  → set lease_owner + lease_expires_at
  → execute run
  → completed / retry / dead_letter
```

#### 方案 2：把 checkpoint 升级为恢复状态机

`checkpointPayload` 不应只是最后 Step ID，建议演进为：

```ts
type RunCheckpoint = {
  runId: string
  currentNode: 'model_call' | 'tool_call' | 'artifact_write' | 'finalize'
  completedSteps: string[]
  pendingToolInvocationId?: string
  lastSafeResumePoint: string
  deterministicReplayInput?: unknown
  updatedAt: string
}
```

#### 方案 3：建立恢复策略表

| 阶段 | 策略 |
|---|---|
| before model call | 可重新执行 |
| after model output before tool | 可用持久化 model output 重放 |
| deterministic tool phase | 可重放 |
| LLM inner repair | 转异步任务 |
| artifact write | 幂等补偿 |
| finalize | 幂等补发事件或标记完成 |

#### 方案 4：增加混沌测试

需要补：

- `model_call` 后进程崩溃
- `tool_call` 中进程崩溃
- `artifact_write` 前后崩溃
- Redis lease 过期后另一个 worker 接管
- 同一个 Run 被两个 worker 同时尝试恢复

## 问题二：异步状态已有投影，但还不是事件溯源级一致性模型

### 当前状态

当前已经有：

- `SessionProjectionService`
- `GET /sessions/:sessionId/projection`
- `GET /sessions/:sessionId/events`
- Run SSE cursor
- Session SSE
- `artifact.version.created`
- `artifact.repair.completed`
- `agent.task.started / completed / failed`
- 前端 `useSessionProjection`
- `ArtifactViewer` 监听 `artifact:version-created` 自动刷新

这已经明显优于单纯 `ToolInvocation` 轮询。

### 为什么仍然致命

当前 `SessionProjection` 是 **读时聚合**，不是 **写时物化投影**。

它会临时查询：

- `runs`
- `tool_invocations`
- `artifacts`
- `artifact_versions`
- `agent_tasks`
- `session.metadata.activeHandHistory`

长期风险：

| 风险 | 说明 |
|---|---|
| 查询成本随会话增长 | 当前只截取最近 N 条 Run，长期会话会出现状态缺失或性能问题 |
| 事件顺序不全局一致 | Run SSE 和 Session SSE 之间缺少统一 sequence |
| 投影不可审计 | 前端看到的状态不是一条可追溯的物化记录 |
| 事件丢失后只能重查 | 没有 session_event_id / cursor 级别的强恢复 |
| 多端同步弱 | 多浏览器、多设备同时编辑同一 Artifact 时冲突处理不足 |

### 优化方案

#### 方案 1：引入物化投影表

```txt
session_projections
  session_id
  user_id
  active_runs_json
  tool_invocations_json
  artifacts_json
  pending_tasks_json
  active_hand_history_json
  version
  updated_at
```

所有 Run / Tool / Artifact / AgentTask 事件写入时同步更新 projection。

#### 方案 2：引入 session_events 表

```txt
session_events
  id bigint auto_increment
  session_id
  run_id
  event_type
  event_data
  created_at
```

前端订阅：

```txt
GET /sessions/:sessionId/events?after=<session_event_id>
```

这样 Session SSE 具备真正 cursor 续订能力。

#### 方案 3：Artifact 编辑冲突控制

多轮修改应支持：

```txt
baseVersionId
expectedCurrentVersionId
conflictPolicy: reject | merge | branch
```

当用户基于旧版本修改时，应明确提示：

```txt
当前牌谱已有新版本 v5，你正在基于 v3 修改，是否创建分支版本？
```

## 问题三：Plugin Runtime 已自动装配，但插件治理还不够产品化

### 当前状态

当前插件层已经支持：

- `registerAgent`
- `registerAgentRuntime`
- `registerCapabilityHints`
- `registerTool`
- `registerWorkflow`
- `registerWorkflowRuntime`
- `registerArtifactType`
- 从插件自动装配到：
  - `A2ARouter`
  - `AgentExecutorRouter`
  - `CapabilityRouter`
  - `A2APolicy`
  - `WorkflowRegistry`

这已经解决了“每加一个 Agent 都手写改核心容器”的主要问题。

### 为什么仍然致命

正式产品中的插件不是简单代码注册，而是一个平台治理问题。

当前还缺：

| 缺口 | 风险 |
|---|---|
| 插件版本管理 | 不能对单个插件做灰度、回滚、兼容性声明 |
| 插件启用/禁用 | 不支持按租户、项目、用户开启能力 |
| 插件权限边界 | 插件能注册 runtime，但缺少更细粒度工具权限沙箱 |
| 插件质量门禁 | 没有插件级 eval、测试、发布流水线 |
| 插件隔离 | 插件运行仍在主进程内，异常可能影响框架整体 |
| 插件依赖声明 | 没有声明依赖哪些模型、工具、Artifact 类型、数据库迁移 |

### 优化方案

#### 方案 1：插件 Manifest 化

建议每个插件提供：

```ts
type PluginManifest = {
  id: string
  version: string
  minFrameworkVersion: string
  agents: string[]
  tools: string[]
  workflows: string[]
  artifactTypes: string[]
  requiredEnv: string[]
  permissions: string[]
  evalSuites: string[]
}
```

#### 方案 2：插件启用表

```txt
plugin_installations
  id
  plugin_id
  version
  scope: global | tenant | project | user
  scope_id
  enabled
  rollout_percent
  config_json
  created_at
  updated_at
```

#### 方案 3：插件级发布流水线

每个插件必须具备：

```txt
unit tests
integration tests
eval cases
permission audit
cost baseline
latency baseline
rollback plan
```

#### 方案 4：插件运行隔离

高风险插件建议支持：

- 单独 Worker 进程
- 独立队列
- 独立超时
- 独立资源预算
- 崩溃不影响主 API

## 问题四：LLM Eval 已有 CI 门禁，但真实线上质量治理还不完整

### 当前状态

当前已经实现：

```txt
apps/api/evals/nl_to_hand/
  golden_cases.jsonl
  patch_cases.jsonl
  routing_cases.jsonl

apps/api/evals/runner/
  eval-runner.ts
  fake-model-client.ts
  markdown-reporter.ts
  json-reporter.ts
  thresholds.ts
```

CI fake 模式已经覆盖：

- `route_accuracy`
- `tool_call_rate`
- `schema_success_rate`
- `validation_success_rate`
- `artifact_success_rate`
- `patch_preservation_rate`

### 为什么仍然致命

LLM 线上质量退化通常不是 fake model 能发现的。

典型风险：

| 风险 | 示例 |
|---|---|
| 模型版本漂移 | 同样 prompt，真实模型输出字段开始漂移 |
| Prompt 小改导致质量下降 | tool call rate 降低或 patch 保留率下降 |
| 成本突然上升 | 内层 repair 频率升高但 CI fake 不可见 |
| 长尾输入失败 | golden case 覆盖不到真实用户表达 |
| 多轮编辑语义损坏 | patch 成功但悄悄覆盖未修改字段 |

### 优化方案

#### 方案 1：Nightly 真实模型评测

```txt
PR CI:
  fake model eval
  deterministic tests

Nightly:
  real model eval
  latency / token / cost
  route confusion matrix
  patch preservation diff

Release:
  compare with previous baseline
  regression > threshold blocks release
```

#### 方案 2：线上 Trace 回放

从真实生产数据抽样：

```txt
failed runs
repair_failed artifacts
manual edited artifacts
high latency runs
high token cost runs
user negative feedback runs
```

脱敏后进入 eval 集。

#### 方案 3：质量趋势看板

建议接入：

- `nl_to_hand_route_accuracy`
- `nl_to_hand_tool_call_rate`
- `nl_to_hand_validation_success_rate`
- `nl_to_hand_repair_rate`
- `nl_to_hand_repair_success_rate`
- `nl_to_hand_patch_preservation_rate`
- `nl_to_hand_p95_latency_ms`
- `nl_to_hand_avg_cost_usd`

#### 方案 4：Artifact 人工验收闭环

用户如果手动修正生成结果，应记录：

```txt
generated_version_id
edited_version_id
diff
reason
confirmed_by_user
```

这些数据是未来优化 prompt、autofix 和校验器的核心资产。

## 问题五：安全治理仍偏基础，距离正式产品级 Agent Governance 还有差距

### 当前状态

当前已经具备：

- JWT auth
- Run 归属校验
- A2A 调用白名单
- A2A 深度限制
- A2A 调用次数限制
- 基础 rate limit 中间件
- ToolInvocation 审计记录
- ArtifactVersion 版本记录

这些是生产化基础，但还不是完整 Agent 安全治理。

### 为什么致命

Agent 后端的风险不只来自普通 Web API，还来自模型自主决策和工具调用。

长期正式产品必须防：

| 风险 | 后果 |
|---|---|
| Prompt Injection | 用户诱导 Agent 绕过策略、泄露上下文或滥用工具 |
| Tool 越权调用 | Agent 调用不该调用的高风险工具 |
| 租户数据串用 | Memory、Artifact、Run、ToolInvocation 跨用户或跨租户污染 |
| 成本攻击 | 用户构造输入触发大量模型调用或 repair loop |
| 高风险操作误执行 | 删除、支付、外部 API 写入等操作被自动执行 |
| 日志泄密 | Tool input/output 或 prompt 中含敏感数据 |

### 优化方案

#### 方案 1：统一 Policy Engine

建议把策略从分散的 `A2APolicy`、Tool 内部校验、route 归属校验，升级为统一 Policy Engine：

```ts
type PolicyDecision = {
  allow: boolean
  reason: string
  riskLevel: 'low' | 'medium' | 'high'
  requireHumanApproval?: boolean
  budgetImpact?: {
    maxTokens?: number
    maxCostUsd?: number
  }
}
```

统一检查点：

```txt
before_run_start
before_model_call
before_tool_call
before_artifact_write
before_a2a_call
before_memory_write
before_external_side_effect
```

#### 方案 2：Tool 权限模型

```txt
tool_permissions
  tool_id
  risk_level
  required_scopes
  allowed_agents
  require_approval
  max_invocations_per_run
  max_cost_usd
```

#### 方案 3：Prompt Injection 防护

需要至少实现：

- system prompt 与 user input 严格分区
- tool description 中明确不信任用户输入
- RAG / Memory 召回内容加来源和可信等级
- 高风险工具调用前二次模型或规则审查
- 命中 injection pattern 时降级澄清或拒绝执行

#### 方案 4：租户隔离

所有核心表都应长期具备：

```txt
tenant_id
project_id
user_id
```

关键查询必须走 scope：

```txt
WHERE tenant_id = ? AND user_id = ?
```

并补充跨租户访问测试。

#### 方案 5：敏感数据治理

需要对以下内容做脱敏或加密：

- model input
- tool input
- tool output
- artifact content
- session summary
- memory content
- eval trace

## 4. 推荐后续路线

### P0：上线前必须完成

1. 持久化 Run Queue / Worker claim / dead-letter。
2. SessionProjection 物化表和 `session_events` cursor。
3. 真实模型 nightly eval。
4. Tool 权限模型和高风险工具审批。
5. 租户隔离字段和跨租户访问测试。

### P1：正式运营阶段

1. 插件版本、启用、灰度和回滚。
2. 生产质量看板。
3. Trace 回放评测。
4. Artifact 编辑冲突控制。
5. Run 恢复混沌测试。

### P2：规模化阶段

1. 独立 Worker 集群。
2. 独立插件运行沙箱。
3. 多租户计费和成本预算。
4. 多模型路由平台。
5. 独立 Eval 平台。

---

## 5. 最终判断

当前框架已经具备正式产品的核心骨架：

```txt
Run Runtime
  + ToolInvocation Recovery
  + ArtifactVersion
  + CapabilityRouter
  + Plugin Runtime
  + SessionProjection
  + Eval CI
```

但如果以“长期可上线、可运营、可扩展、可治理”的产品标准看，下一阶段重点不应继续堆业务 Agent，而应优先治理：

1. **任务调度强一致性**
2. **状态投影一致性**
3. **插件平台治理**
4. **真实模型质量闭环**
5. **Agent 安全治理**

这 5 个方向决定 `agent-frame` 是停留在“功能完整的 Agent 应用框架”，还是能继续演进为“生产级 Agent 后端平台”。
