# 以 Redis 为刃，切中高并发架构中的读写痛点（技术分享总结）

## 核心分享主旨
在进行 Redis 的技术分享（数据类型、适用场景、持久化机制）时，切忌做成“官方文档宣读”。高阶架构师/CTO 想听到的，是你能否**将 Redis 的底层特性与我们真实的业务架构痛点（如复式扑克表设计的推演）深度结合**。

分享的核心暗线应当是：
**“遇到什么业务痛点 -> 为什么 MySQL 扛不住或不适合 -> Redis 的什么特性刚好契合 -> 在持久化等机制上我们做出了什么工程妥协。”**

---

## 1. 讲数据类型：讲透“读写路径优化”与“读模型反范式”
*   **❌ 常规讲法**：String 用来存字符串，ZSET 用来做排行榜，Hash 用来存对象。
*   **✅ 升维讲法（结合业务）**：
    *   **读模型反范式（String/Hash）**：在复式扑克系统中，我们的底层 MySQL 坚守了三范式（单局成绩走独立表）。但面对前端高频的进度查询，MySQL 联表查会成为瓶颈。此时，**Redis 的 String 类型就是完美的“读模型反范式”载体**。我们把关联好的 JSON 进度快照塞进 Redis。**Redis 保护了 MySQL 的高并发读，MySQL 保护了 Redis 的绝对数据安全，两者各司其职。**
    *   **底层结构匹配访问模式（ZSET）**：为什么不用 MySQL `ORDER BY` 做实时排行榜？因为排行榜的业务特性是“高频写分数 + 高频查排位”。Redis ZSET 的底层结构（跳表 SkipList）天然契合这种场景，保证了插入和查询都是 `O(log N)` 的极速。**技术选型的本质，就是让底层数据结构匹配业务的访问模式。**

## 2. 讲适用场景：讲透“计划数据”与“事实数据”的落脚点
*   **❌ 常规讲法**：Redis 适合做高并发缓存、计数器、分布式锁。
*   **✅ 升维讲法（结合数据生命周期）**：
    *   **静态/计划数据**：比如活动的题库配置、给用户初始分配的牌单，生成后极少变动。这种数据极其适合用 Redis 做只读缓存，挡住大流量。
    *   **核心事实数据**：用户单局真正赢了多少分，这种数据是用户的核心资产（事实数据）。虽然它写入并发也高，但**绝对不能只写 Redis**，必须落入 MySQL 的 `user_hand_record` 表。
    *   **核心结论**：Redis 适用场景的边界，取决于**该数据是否能容忍丢失，以及它是否是系统的“绝对事实源”**。

## 3. 讲持久化机制：讲透“工程妥协”与“兜底策略”
*   **❌ 常规讲法**：RDB 是快照恢复快但会丢数据；AOF 是日志记录完整但文件大。
*   **✅ 升维讲法（结合架构兜底）**：
    *   持久化策略的选择，本质上是一种**基于架构兜底能力的工程妥协**。
    *   在我们的架构中，Redis 排行榜的数据，其实是可以由 MySQL 的 `user_entry.total_score` 推导出来的。这意味着，哪怕 Redis 机器全挂、数据全丢，只要跑个脚本扫一遍 MySQL，排行榜就能 100% 重建。
    *   **核心结论**：正因为 MySQL 做了最后的事实兜底，我们在配置 Redis 时，就完全不需要开启极其拖累性能的 `AOF always`（每次写入刷盘），只需配置普通的 `RDB` 或 `AOF everysec` 即可。**Redis 持久化策略不是越严越好，而是要看背后的持久层能不能为你兜底，以此来换取最大的内存读写性能。**
