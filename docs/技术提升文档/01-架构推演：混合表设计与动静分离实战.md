# 架构设计思考：从“合与分”的二元对立到“混合架构”的最佳实践

## 1. 业务背景与争论点

**业务背景**：
在复式扑克排名赛模块中，用户报名参加活动后，系统会为用户随机分配 10 手牌（`hand_id`）。用户打完这 10 手牌后，根据总成绩进行排名。同时，运营后台需要能够基于单手牌（`hand_id`）进行聚合统计（如计算某手牌的平均分、流失率），以用作复盘教学资产。

**早期的架构争论（极端的二元对立）**：
*   **极端方案 A（极度分开，1主 N从）**：
    *   *做法*：报名瞬间 `INSERT` 1 条总记录（`user_entry`）和 10 条空白的明细记录（`user_hand_record`）。
    *   *痛点*：高并发下写入开销大，且产生大量无用的“占位”数据（很多用户可能报名了但还没开始打）。
*   **极端方案 B（极度合并，全量 JSON）**：
    *   *做法*：取消明细表，把 10 手牌的成绩和状态全部作为 JSON 数组塞进 `user_entry` 表。
    *   *痛点*：每次打完一手牌更新 JSON 极易导致并发覆盖冲突（分布式环境下的“读-改-写”死锁），并且彻底破坏了后台通过 SQL 对单手牌（`hand_id`）进行聚合统计的能力。

## 2. 破局之道：CTO 敲定的混合架构（Hybrid）

面对上述僵局，CTO 最终采用了一个融合了两者优点的**“静态清单走 JSON，动态事实走独立表”**的混合方案：
1.  **静态分配走 JSON**：用户报名时，通过内存算法洗出 10 手牌的清单。将这个纯粹的分配清单（如 `[1001, 1024, 1008]`）一次性写入 `user_entry` 的 `assigned_hands` JSON 字段。写入后此字段**不再修改**。
2.  **动态事实走独立表**：用户真正开始打（或打完）某手牌时，才按需向独立的 `user_hand_record` 明细表 `INSERT` 或 `UPDATE` 一条真实的成绩事实记录。

**方案优势**：
完美规避了报名时的大量空记录插入，彻底避开了 JSON 的更新并发冲突，同时保全了关系型数据库强大的单据统计分析能力。

## 3. 架构提升方法论：如何快速推导出类似优化？

在日常开发中，我们很容易陷入类似“全分”或“全合”的盲区。要快速定位并推导出上述这种“看似简单却极具穿透力”的优化方案，资深架构师通常会进行以下 **4 个维度的灵魂拷问**：

### 3.1 拆解数据的“动静边界”（Immutable vs Mutable）
拿到一个复杂实体，第一步不是想表结构，而是问自己：**这里面哪些数据写完永远不变？哪些是会高频变化的？**
*   **静（不变的数据）**：10 手牌的分配清单。生成即固定。
*   **动（高频变的数据）**：每手牌的输赢成绩、进行状态。
*   **推导结论（动静分离）**：静态不变的数据可以打包压缩（JSON 存主表），高频变动的数据放入支持行锁的关系型子表中。既省空间，又保安全。

### 3.2 区分“计划数据”与“事实数据”（Plan vs Fact）
这是业务建模中最容易犯的错。
*   **计划数据**：系统“打算”让你打这 10 手牌（类似电商的购物车清单）。
*   **事实数据**：你“实际”打完了第 1 手牌赢了 5 分（类似电商的真实支付流水）。
*   **推导结论**：永远不要把“计划”和“事实”揉在一起。既然事实还没发生（用户还没开始打），就**根本不需要提前去 `INSERT` 空白的事实记录**。这就自然推导出了“报名时不批量写子表”的优化思路。

### 3.3 分离“读写痛点”，做极端假设
分别把两个极端方案的“最痛点”揪出来，尝试拼接两者的优势：
*   **分开方案痛点**：报名瞬间要 `INSERT` 11 条记录，怕数据库有压力。
*   **合并方案痛点**：打牌时更新 JSON 容易并发死锁，且后台没法做 SQL 统计。
*   **推导结论**：只要**不提前写空记录**，就能兼顾 A 的写入安全和 B 的轻量级报名。用 JSON 记住计划清单，打牌时再写单条事实记录，取其精华去其糟粕。

### 3.4 数据体积与查询扇出（Fan-out）评估
评估系统运行 1 个月后的数据盘块：
*   如果提前 `INSERT` 10 条空记录，假设 10 万人报名，数据库瞬间多出 100 万条全是 `status=pending`, `score=null` 的垃圾数据。这会严重污染 InnoDB 的 Buffer Pool（缓冲池）。
*   **推导结论**：采用**按需生成（Lazy Loading）**机制。真正发生交互时才落库，这是服务端极其经典且有效的数据延迟初始化策略。

## 4. 总结语
架构设计绝不仅是对 SQL 语法的选择，而是对业务事实发生规律、数据生命周期的深刻映射。跳出“合与分”的表象争论，以“动静分离”、“计划与事实隔离”、“按需延迟写入”的方法论去审视，就能迅速在复杂的业务约束中寻找出最优解。
